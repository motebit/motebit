# services/relay — the relay

The only function with a legitimate centralization premium (multi-device sync). Also: settlement, federation, discovery, rate limiting, disputes, credential anchoring.

Modules: `index`, `federation`, `task-routing`, `credentials`, `pairing`, `data-sync`, `accounts`, `a2a-bridge`, `logger`, `discovery`, `migration`, `disputes`, `p2p-verifier`, `transparency`, `settlement-rails/*`, `webhooks/*`.

## Rules

0. **The master token never leaves the relay.** `forwardTaskViaMcp` authenticates to a worker AS THE RELAY with the per-task dispatch token (`Authorization: Bearer motebit:<dispatch_token>`, verified by the worker under its pinned relay key); `apiToken` is never a bearer to any registered endpoint, and a forward without a dispatch token is refused. The reverse direction holds too: **no worker holds the master token** — a worker authenticates to this relay with its OWN key (per-audience signed tokens after a public `POST /api/v1/agents/bootstrap`), enforced by `check-worker-no-master-token`. See [`docs/doctrine/task-admission.md`](../../docs/doctrine/task-admission.md) §"The relay authenticates as itself" and §"The worker authenticates as itself".
1. **Outbound URL law.** Any URL the relay did not author and will contact — a registered agent `endpoint_url`, a federation peer `endpoint_url` — passes `@motebit/sdk` `checkOutboundUrl` (via `buildOutboundPolicy`) at persist time AND at connect time (`forwardTaskViaMcp`). Only globally-routable http(s); `MOTEBIT_ALLOW_PRIVATE_ENDPOINTS=1` is the local-dev allowance and is never set on Fly. See [`docs/doctrine/security-boundaries.md`](../../docs/doctrine/security-boundaries.md) §"Outbound URLs".

2. **Never inline protocol plumbing.** Audit the package layer first: `@motebit/protocol` → `@motebit/crypto` → `@motebit/encryption` → `@motebit/mcp-client` → `@motebit/mcp-server` → `@motebit/runtime` → `@motebit/core-identity` → `@motebit/identity-file`. If none match, a primitive is missing — add it to the right package, consume here. `check-service-primitives` catches inline `fetch` to motebit endpoints, JSON-RPC strings, direct `signExecutionReceipt` calls, and `canonicalJson`/`sha256` constructing protocol-shaped payloads.
3. **`SettlementRailRegistry.register()` accepts only `GuestRail`.** The registry and the three concrete guest rails (`StripeSettlementRail` fiat, `X402SettlementRail` protocol, `BridgeSettlementRail` orchestration) live in `@motebit/settlement-rails` (Layer 1); the `@ts-expect-error` negative proof is in that package's `__tests__/custody-boundary.test.ts`. The `/health/ready` rail manifest advertises only guest rails. Sovereign rails are agent-custody and live in `@motebit/wallet-solana`. Rails accept an injected `logger` — the relay supplies its module-scoped `createLogger` adapter at construction.
4. **Structured logging.** `createLogger(module)` emits JSON with `x-correlation-id` propagated through request lifecycles. Never `console.log` in production paths.
5. **Rate limiting is per-IP, per-connection, per-peer.** 5-tier fixed window (auth 30/min, read 60/min, write 30/min, public 20/min, expensive 10/min). WebSocket 100 msg/10s per connection. Federation 30 req/min per peer. Task queue hard-capped at 100K. Per-submitter queue limit 1000/agent (HTTP 429).
6. **Fail-closed on auth.** Signed bearer tokens require `aud` audience binding. The closed registry of canonical audiences lives in `@motebit/protocol`'s `TokenAudience` literal union (see `packages/protocol/src/audience.ts`); `check-audience-canonical` enforces every signing site against `ALL_TOKEN_AUDIENCES`. Today's set: `sync`, `device:auth`, `pair`, `rotate-key`, `push:register`, `task:{submit,query,result}`, `task:dispatch` (relay-signed per-task admission artifact — `mid` = worker, `sub` = relay task id — attached to every MCP forward and returned to the submitter; verified by `@motebit/mcp-server` `taskAdmission` against the pinned relay key before `motebit_task` runs, one execution per `sub`; the relay never accepts it inbound; see [`docs/doctrine/task-admission.md`](../../docs/doctrine/task-admission.md)), `admin:query`, `proposal`, `receipts:read`, `market:{listing,query}`, `credentials`, `credentials:present`, `account:{balance,deposit,withdraw,withdrawals,checkout}`, `proxy:token` (caller===`:motebitId`-authed mint of a cloud-inference billing token that carries the agent balance — least-privilege so a generic read token cannot be replayed to mint a spending credential; 2026-07-07. The token's `models` ceiling is keyed on FUNDING SOURCE — `modelsForAccount`: a free-credit-only account gets the Sonnet/Haiku-class list, any real ledger credit unlocks `DEPOSIT_MODELS`; the proxy enforces the list and, since 2026-09-13, per-token spend / per-identity rate / concurrency controls before any provider call) (`account:deposit` reserved — the self-declared deposit route was removed as a treasury-drain vector; balance is credited only by verified funding), `browser-sandbox-grant`, `browser-sandbox`, `runtime:attach` (local runtime-host attach handshake — verified by `@motebit/runtime-host` on the machine-local socket only; the relay never accepts it). Cross-endpoint replay defense: a token bound to one audience is rejected by an endpoint expecting another (each route configures its own `expectedAudience` via `dualAuth`/`verifySignedTokenForDevice`); a signing-side typo would have been a runtime 401 pre-registry, now a compile error. `InboundCredentialVerifier` adapter takes precedence over static `authToken`. **Every master-token presentation and every refused signed token is recorded** in `relay_auth_events` (`auth-events.ts`; kind, method, path, claimed `mid`, audience, reason, correlation id — never token bytes, never IP; 30-day window) and readable at `GET /api/v1/admin/auth-events` — posture is proven from the relay's own record, not a log tail (2026-09-14: Fly's buffer ended before the deploys an audit needed). A new auth decision site MUST call `recordAuthEvent` beside its log line.
7. **Relay is a convenience layer, not a trust root.** Every truth the relay asserts (credential anchor proofs, revocation memos, settlement receipts) is independently verifiable onchain without relay contact. If you add a relay-only assertion, justify why it is not protocol-shaped.
8. **Federation circuit breaker.** Per-peer forward tracking; automatic suspension at 50% failure rate over ≥6 samples. Heartbeat handles liveness (3 missed → suspend, 5 → remove). The three-state engine lives in `@motebit/circuit-breaker` (Layer 1) — `services/relay` instantiates it in `task-routing.ts` and injects a module-scoped logger. Adding a second caller (MCP client retry, webhook delivery) means a second `new CircuitBreaker({ logger })` at the consumer, not a wrapper here.
9. **P2P settlement path** is policy-based (`evaluateSettlementEligibility` in `task-routing.ts`): both parties opt in via `settlement_modes`, worker declares `settlement_address`, trust ≥ 0.6, interaction count ≥ 5, no active disputes between pair. **Identity binding is an additive eligibility signal, never a gate:** a sovereign-bound worker (offline `verifySovereignBinding` over the registry `public_key`) qualifies at a reduced cold-start bar (`first_contact` + 2 interactions) because its `motebit_id` commits to its key and so cannot be a throwaway sybil. The branch sits _after_ the strict branch, so unbound/legacy workers are unaffected; it never fabricates trust. Same shape as the additive `HardwareAttestationSemiring` (rule on hardware attestation) — see [`docs/doctrine/identity-binding-verification.md`](../../docs/doctrine/identity-binding-verification.md) § "Binding strength feeds settlement". P2p tasks skip virtual-account allocation; money moves onchain in a **single atomic Solana multi-output transaction** composing two SPL Transfer instructions — delegator→worker (the worker's listing unit_cost, recorded as `amount_settled`) and delegator→relay_treasury (the 5% platform fee, recorded as `platform_fee`). Treasury address is the relay's identity-derived Solana wallet (`deriveSolanaAddress(relayIdentity.publicKey)` — same address used by `OperatorSolanaTransfer` for Path 0 and `SolanaMemoSubmitter` for anchoring). Relay records audit with `settlement_mode='p2p'`. Async `startP2pVerifierLoop` in `p2p-verifier.ts` polls Solana RPC, walks `transfers[]` for both legs, transitions state to `verified` only when both legs match the declared amounts + addresses (mismatch → `failed` + trust downgrade). Arc 2 of the off-ramp arc landed this fee-on-P2P composition; the sibling-doc contradiction the settlement_mode arc surfaced (top-level "5% applies through both lanes" vs this rule's pre-Arc-2 "Fee: zero on P2P") is now closed. Pre-Arc-2 zero-fee P2P rows remain verifiable via the verifier's backward-compat branch (skips fee-leg check when `platform_fee === 0`). Doctrine: [`docs/doctrine/off-ramp-as-user-action.md`](../../docs/doctrine/off-ramp-as-user-action.md) § "What Arc 1 did NOT close" + the Arc 2 close. **Arc 3.5 P2P-by-default gate (LIVE):** the pure predicate `requiresP2pProof` (`tasks.ts`) gates a submission with `TASK_P2P_PROOF_REQUIRED` (402) when `settlementMode === "relay" && x402TxHash == null && unitCostAtSubmission > 0 && submittedBy != null && submittedBy !== motebitId` — paid direct delegation to a different worker without a P2P proof. Submission carve-outs (do NOT reach the gate): self-delegation, zero-cost, x402-paid. **Multi-hop is NOT a submission carve-out** — a paid sub-delegation is a real `POST /agent/:worker/task` and is gated like any direct delegation; only `settleSubReceipt`'s relay-mode write is a deferred residual (the multi-hop-as-P2P arc). `arc-3.5-gate.test.ts` locks the gate two ways — four carve-outs through the live route, and all five conditions (incl. the x402-paid branch, whose SUBMISSION is unreachable from the harness because `x402TxHash` is set only by the real `onAfterSettle` payment hook) as a pure `requiresP2pProof` truth table. The `dispute-cycle-e2e` fund-refund tests are LIVE again (2026-07-12): `seedX402PaidTask` (`__tests__/test-helpers.ts`) seeds the exact post-submission state of an x402-paid delegation — the facilitator round-trip is the only faked step — and the tests drive the real receipt → settlement → dispute → claw-back → withdrawal path over live routes. Only the `settlement-safety` multi-hop tests remain `it.skip`'d until the multi-hop-as-P2P arc (they need `settleSubReceipt`'s relay-write reconciliation, not the x402 seam). See [`docs/doctrine/off-ramp-as-user-action.md`](../../docs/doctrine/off-ramp-as-user-action.md) § "Arc 3.5 gate scope". **Cross-operator federated P2P (federation funding arc, LIVE):** a PAID delegation to a REMOTE worker (discovered on a peer operator) is a client-pinned direct delegation carrying a **3-leg** `payment_proof` — the delegator's single atomic Solana tx pays the worker net + origin-relay (A) fee + executor-relay (B) fee per spec §7.1 fee-from-budget ($1.00 → worker $0.9025 / A $0.05 / B $0.0475). Submission with `target_agent` + `payment_proof` where the target is NOT local routes to the dedicated `federatedP2pIntent` branch in `tasks.ts`: A resolves the worker's `settlement_address` + the peer relay's treasury (`deriveSolanaAddress(relay_peers.public_key)`) via discovery, validates all three legs, and forwards the proof inside the SIGNED `/federation/v1/task/forward` body. B verifies its own legs + dispatches. BOTH relays record a `settlement_mode='p2p'` audit row (A the origin-fee leg, B the worker + executor-fee leg) — each relay's `platform_fee` equals the leg landing in its OWN treasury, so the p2p-verifier (worker leg verified only when the worker is local; fee leg always) and the Solana treasury reconciler both key correctly per-operator. **No relay-custody credit anywhere; the cross-operator transmitter surface is structurally zero** — this REPLACES the PHASE 2 `relay_federation_settlements` chain + PR1's interim relay-custody charge for the funded path. A proofless PAID federated forward is rejected (402) at the forward site; FREE federated tasks still forward without a proof.
10. **Withdrawal hold during dispute window** — `AccountStore.getUnwithdrawableHold` (Layer-1 `@motebit/virtual-accounts`, implemented by `account-store-sqlite.ts`) sums recent relay settlements < 24h not yet disputed. `requestWithdrawal` pre-checks available balance before atomic debit. P2p settlements explicitly excluded. `accounts.ts` is a deprecation shim that routes the legacy functional API through a per-db `SqliteAccountStore`; new code consumes `@motebit/virtual-accounts` directly.
11. **Operator transparency declaration is the source of truth** (`transparency.ts` + `PRIVACY.md`). The signed JSON at `/.well-known/motebit-transparency.json` and the committed `PRIVACY.md` both derive from `DECLARATION_CONTENT`. Any code change that adds a processor, a retained field, or a retention window must update `DECLARATION_CONTENT` in the same PR — the sibling-boundary test in `__tests__/transparency.test.ts` enforces sync, but a code-vs-declaration drift (e.g., adding Sentry without naming it) the test cannot catch. Manual review for the doctrine in `docs/doctrine/operator-transparency.md`.
12. **`relay_receipts.receipt_json` is append-only and byte-identical.** The column must equal `canonicalJson(receipt)` at write time; any mutation breaks the auditor's signature reverification path (the whole point of the archive — `spec/execution-ledger-v1.md` §11.1 Storage). Persist through `persistReceiptChain` in `receipts-store.ts`; read through `getStoredReceiptJson` and return the bytes verbatim. Never `JSON.parse` + re-serialize through a non-JCS path on the way out.
13. **Aggregated withdrawals debit at enqueue time.** `enqueuePendingWithdrawal` in `batch-withdrawals.ts` debits the virtual account before inserting the `relay_pending_withdrawals` row; the fire path (serial or `withdrawBatch`) does NOT re-debit. A rail failure parks the row as `failed` with the debit still in place — the debit is the audit trail that funds were claimed. Never short-circuit the debit-before-insert order; doing so opens a double-spend window against concurrent sweeps. See `spec/settlement-v1.md` §11.2.
14. **Native SQLite driver is mandatory — no silent sql.js fallback.** The relay is the only centralized, durability-sensitive node; it MUST run on `better-sqlite3` (native, WAL-enabled, per-commit fsync) and NEVER on `sql.js` (WASM, WAL no-op, 1-second-debounced full-file rewrites). `services/relay/package.json` declares `better-sqlite3` as a direct dependency so `pnpm deploy --prod` flattens it into the runtime image — without this, the binding is dropped (it's an `optionalDependency` of `@motebit/persistence` for the CLI scaffold's exotic-platform fallback) and the service silently degrades. Boot path uses strict `createMotebitDatabase` (throws if missing), not fallback-friendly `openMotebitDatabase`. The `relay.starting` log includes `driver` so every boot prints the driver identity. Enforced by `check-deploy-parity` rule 4 (drift-defenses #42); historical incident in `docs/drift-defenses.md` §42.

15. **External medium plumbing speaks motebit vocabulary, not provider vocabulary.** Provider-native types — webhook schemas (`Stripe.Event`, `Bridge.*`), SDK calls, chain JSON-RPC envelopes (`eth_getLogs`, `eth_blockNumber`) — never leak into the relay's business logic. Each external boundary ships an adapter that (a) owns the wire format and signature/error primitives and (b) maps to a closed motebit-shaped type before handing to the consumer. Webhook adapters live under `webhooks/*`, return `null` on signature failure, and surface unknown events as `{ kind: "ignored", type }` so the switch stays exhaustive. Chain-RPC adapters live next to their consumer (e.g., `deposit-detector/rpc-adapter.ts`) and collapse every wire-level failure (network / non-2xx / JSON-RPC error / malformed body) to a single thrown `Error` — the state-machine's try/catch already handles that shape. Concrete today: `StripeSubscriptionEventAdapter` in `webhooks/stripe-webhook-adapter.ts` (consumed by `registerProxyTokenRoutes`); `HttpJsonRpcEvmAdapter` in `deposit-detector/rpc-adapter.ts` (consumed by the deposit-detector state machine). The medium-plumbing extraction mirrors the guest-rail pattern in rule 2: external APIs churn on their own cadence and must not couple to account-crediting logic.

16. **x402 facilitator construction goes through `x402-facilitator.ts` — never inline `new HTTPFacilitatorClient(...)`.** The single canonical adapter chooses CDP-authed mainnet vs. unauthenticated testnet based on env shape, and **fails fast with `X402ConfigError` when `X402_TESTNET=false` is set without `CDP_API_KEY_ID` + `CDP_API_KEY_SECRET`**. The default `https://x402.org/facilitator` is testnet-only and silently passes startup health checks while rejecting mainnet networks at route-registration time — a half-mainnet trap the centralized constructor closes. Two consumers today: `index.ts` (settlement-rail registration) and `tasks.ts` (x402 HTTP middleware). Adding a third consumer means a third call to `createX402FacilitatorClient`, never a fresh inline construction. Mainnet credentials (CDP) are JWT-bearer signed per-request via `@coinbase/x402`'s exported `facilitator` config; testnet uses the structural `{ url }` shape with no auth.

17. **Treasury reconciliation is a sibling-but-distinct primitive to the deposit-detector, with EVM and Solana sides both wired.** Both reconcilers (EVM and Solana) are "internal-ledger ↔ onchain" reconciliation pipes; the canonical doctrine on why they must NOT be unified with the deposit-detector — privilege-escalation surface (any in-database `agent_id` is potentially exposed to client-API paths) + circular-fee surface (treasury must never appear as a settlement counterparty) — lives in [`packages/treasury-reconciliation/CLAUDE.md`](../../packages/treasury-reconciliation/CLAUDE.md) Rule 1. Don't duplicate the reasoning here. **EVM side:** algebra in `@motebit/treasury-reconciliation`, relay-side wiring in `services/relay/src/treasury-reconciliation.ts`; loop runs only when `X402_TESTNET=false` AND `X402_PAY_TO_ADDRESS` is set AND the chain has a registered USDC contract + RPC URL (otherwise emits `treasury-reconciliation.disabled` log line); audits x402 facilitator settlements. **Solana side:** algebra in `@motebit/wallet-solana` (`OperatorSolanaTreasuryReconciler`, sibling of `OperatorSolanaTransfer`), relay-side wiring in `services/relay/src/solana-treasury-reconciliation.ts`; loop runs whenever `SOLANA_RPC_URL` is set (alongside the P2P verifier; pairing enforced by drift gate #104 `check-solana-treasury-reconciliation`); audits Arc 2 P2P fee-leg accumulation in the relay's identity-derived Solana treasury wallet. Both write to the same `relay_treasury_reconciliations` table, discriminated by canonical CAIP-2 `chain` column (per CAIP-30 — `eip155:8453` for EVM-Base, `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` for Solana mainnet; the same identifiers the credential-anchor + consolidation-receipt schemas use, so cross-table joins by chain compose). Admin surface: `GET /api/v1/admin/treasury-reconciliation` returns `chains[]` (one entry per chain) + cross-chain `records[]` audit feed (master-token gated per drift gate #61). Conservative phase-1 invariant: `consistent = onchain >= recordedFeeSum`; positive drift covers direct deposits + manual operator sweeps (which produce false-positive negative drift until phase 2's per-movement ledger lands — known limitation, documented in [`docs/doctrine/treasury-custody.md`](../../docs/doctrine/treasury-custody.md) § Phase 1 step 6 + § "Solana p2p-fee reconciliation"). Cite `feedback_settlement_architecture` memory.

18. **Every `app.get(...)` in `state-export.ts` routes through `emitSignedExport(c, "<artifact-type>", body)`.** The closure-scope helper JCS-canonicalizes the response body, signs it via `signContentArtifact` with `relayIdentity`, and emits the outer `ContentArtifactManifest` in the `X-Motebit-Content-Manifest` HTTP header. Witness-composition: the relay attests "this is what I assembled at time T," signed by the same identity that signs `/.well-known/motebit-transparency.json` — so a third party who pins the relay's key from the transparency declaration can verify every state-export bundle offline (`motebit-verify content-artifact <body> --producer-key <hex>`). The 12 closed-registry `ContentArtifactType` values live in `@motebit/protocol/src/artifact-type.ts` (drift-locked by `check-artifact-type-canonical` #85); the wiring requirement is drift-locked by `check-state-export-signed` (#86) — every new `app.get(...)` in `state-export.ts` MUST consume the helper or fail CI. Layered model on `execution-ledger`: the spec-1.0-compliant inner body keeps its agent-signature omission (spec §6 — relay does not hold the agent's private key); the outer envelope attests only to bundle assembly. Doctrine: [`docs/doctrine/nist-alignment.md`](../../docs/doctrine/nist-alignment.md) §8 + [`docs/doctrine/self-attesting-system.md`](../../docs/doctrine/self-attesting-system.md). The `app.delete(...)` (memory tombstone) is a mutation, not an export — out of scope for the gate; would need its own signing decision if added.

19. **Background loops are supervised — money-movement loops route through `superviseInterval` (`loop-supervisor.ts`).** `setInterval` does NOT die on a thrown callback, so the relay's ~15 background loops can fail invisibly: a tick that throws/rejects every cycle, a tick that hangs forever, or a loop never started by a config branch. The `LoopSupervisor` makes all three observable — `superviseInterval(supervisor, name, intervalMs, tick, { isFrozen })` owns the interval, awaits the (sync-or-async) tick, and records start/ok/error/skip per loop; it also captures the async error that the old `void asyncWork()` shape leaked as an unhandled rejection. Surfaced at `GET /api/v1/admin/health` under `loops` (master-token gated, in-process/in-memory by design — a restart re-registers). **Phase 1 (2026-06-10) supervised the money-MOVEMENT loops** (a silent wedge strands or stops money): `settlement-retry`, `p2p-verifier`, `batch-withdrawal`, `sweep`. **Phase 2 (2026-06-11) adopted everything else** — both settlement-anchor loops (`federation-anchor`, `agent-settlement-anchor`), `identity-log-anchor`, `credential-anchor`, `federation-heartbeat`, `federation-query-cache-prune`, both treasury reconcilers, `deposit-detector`, `revocation-horizon`, `dispute-orchestration`, `task-cleanup` — via the mechanical change Phase 1 prescribed: each `start*Loop` gains an optional trailing `supervisor?: LoopSupervisor` (backward-compatible, loop unit tests unaffected) and ticks log-then-rethrow so structured logging is preserved AND the supervisor records the error. `check-loops-supervised` (drift-defenses #125) now locks the end state: a raw `setInterval(` call in this service outside `loop-supervisor.ts` fails CI, with exactly two narrowly-anchored non-loop exemptions (deposit-detector's disabled-path no-op handle; index.ts's bounded WS-drain waiter).

20. **Commitment bonds are RPC-verified, never custodied — phase 1 is an anti-sybil _signal_, not recourse.** A `BondCommitment` (`@motebit/protocol`, signed via `@motebit/crypto`'s `verifyBondCommitment`) is an agent's own-sovereign-capital proof-of-funds; the relay reads the backing balance via Solana RPC (`getUsdcBalanceOf` on `@motebit/wallet-solana`, the arbitrary-address read distinct from own-ATA `getUsdcBalance`) in the supervised `startBondVerifierLoop` (`bond-verifier.ts`, mirror of `startP2pVerifierLoop` — `superviseInterval`, records `last_checked_at`) — it NEVER holds, transmits, or seizes the bond. The relay's user-funds transmitter surface stays structurally zero (rule 8, rule 2; the deleted `DirectAssetRail` must not return). The bond is an **additive eligibility input** in `evaluateSettlementEligibility` — a branch placed AFTER the strict + sovereign-binding branches, byte-identical for unbonded agents, tiered WITH sovereign-binding never below, never fabricating trust — exactly the additive shape of rule 8's `verifySovereignBinding` branch. It is NOT a new `SettlementMode` (`["relay","p2p"]` stays closed). **Ingestion:** an agent self-submits its signed bond via `POST /api/v1/agents/:id/bond` (mirror of `credentials/submit` — a self-verifying signed artifact recorded by `recordBondCommitment` after `verifyBondCommitment` + the relay's separate registered-key→`motebit_id` binding; **no new `TokenAudience`** — security is in the artifact, not the transport); `GET …/bond` reports status with the §6 as-of timestamp. Two orthogonal anti-reuse defenses, both required: the identity-address binding (`bonded_address === deriveSolanaAddress(bonded_public_key)`, gate `check-bond-address-binding`) defeats cross-**identity** reuse; subtracting the worker's in-flight (pending) p2p value from available backing (`workerInFlightP2pCostMicro`) defeats cross-**ticket** reuse within one identity — a **conservative live read** over the existing settlement state machine (over-counts, never under; self-releasing; a precise per-bond reservation ledger is deferred with the recourse half), NOT a stored reservation ledger. **Staleness is an adversarial window:** eligibility re-verifies backing at task-acceptance time via the read-only `getBondBackingAdapter` (fresh cached read within the spec staleness bound, else a synchronous `getUsdcBalanceOf`; `null` when `SOLANA_RPC_URL` is unset → cached-only, stale fails closed), never accepts on a stale "backed". **Surface-honesty is a gate** (`check-bond-surface-honesty`, sibling of `check-public-fee-claims`): no bond surface may frame the signal as secured funds / guaranteed recourse; the word-list gate is necessary-not-sufficient, so any bond surface also needs a recorded human design-review sign-off. The recourse half (`BondCall`/`BondDefault` + the call on `executeFundAction`'s P2P no-op in `disputes.ts`) is deferred-with-trigger (volume + disputes). Doctrine: [`docs/doctrine/commitment-bond.md`](../../docs/doctrine/commitment-bond.md).
21. **A key record is a credential, so a succession is recorded only from a key this relay already holds.** A device row's `public_key` is what `verifySignedTokenForDevice` verifies an owner token against. The signed succession payload names two keys and no `motebit_id`, so the route supplies the binding: (a) an ordinary succession is refused under any other identity's token — a guardian RECOVERY is exempt, because it exists for an owner who lost the key and is carried by someone else, and its guardian lookup needs a registry row anyway; (b) the record must depart from the key on file, in precedence order — the registry key, else the head of the chain this relay has ALREADY RECORDED, else a key one of the identity's device rows holds — refusing when it holds none. That rule is ONE function (`departureFrom` in `succession-apply.ts`) and the public `GET /succession` route SERVES its answer (`held_public_key`, and `departable` for `?from=<key>`): a client must ask before it mints, and a client that re-derives the answer from the served chain and registry key alone cannot see device rows (a daemon that shut down leaves its key only there) and inverts the precedence whenever registry and chain disagree — it read a routine state as "unregistered" and rotated locally into the split a rotation exists to prevent. The chain head is load-bearing: the registry UPDATE writes no rows once the row is gone, so without it a deregistered identity could rotate exactly once and was then stuck, and rotating twice worked before this rule. It cannot bootstrap anything, being reachable only after a rotation that already passed. Comparison is EXACT, because the spelling is inside the signed payload. That check used to be SKIPPED on a falsy stored key, and both states are routine: the daemon deregisters on every shutdown, and a master-token registration with no key writes `''`. A planted chain is served from the public succession route and the identity bundle (`spec/identity-v1.md` §7.6), so the damage is to what external verifiers read, not only to takeover. Sibling: pairing's bearer-less `update-key` writes only the key the transfer was APPROVED to carry (`identity_pubkey_check`, captured at approve, matched exactly), and refuses outright where no transfer was approved — clients write the seed to their keyring BEFORE calling, so a refusal resting on live rows would strand the device, and a fallback to "any key this identity holds" let the approving device's key be written over the approved device's row (a bearer-less lockout). Bounded to one predetermined key, the pairing id stops being a standing credential with no single-use flag: re-presenting it writes the same key again. A flag would have to live in `status`, whose published values the clients switch on, and would turn a retry after a lost response into a refusal. Every refusal on this route — including the signature refusals in BOTH branches, since `recovery: true` skips the caller check and would otherwise be a way to probe unrecorded — is logged and recorded, naming the PRESENTER as subject; the recorder is a REQUIRED dep. Tests: `__tests__/succession-authority.test.ts`, each check severed and seen red. **An identity's key history never repeats a key, on either side of a link** (#775, `spec/identity-v1.md` §7.5 obligation 3): `applySuccession` refuses (`SuccessionRefused`, before any write, inside its transaction) a link whose pair is recorded but is not the head (`replays_recorded_link`), whose old key the recorded chain names anywhere but as the head's new key (`departs_from_retired_key` — a holder-less identity's registry can be re-filled with a retired key, so departure alone cannot see it), or whose new key is on either side of any recorded link or is the holder or registry key (`reuses_key`); the head re-presented stays a no-op retry. Both doors map it to a recorded 409. **A retired key also stops holding the sockets it admitted** (#767): `applySuccession` takes a REQUIRED `RetireKeyConnections` port (bound once in `index.ts` to `closeSocketsAuthenticatedUnder` over `connections`) and after commit retires every socket of the identity whose token verified under the retired key (`ConnectedDevice.authenticatedUnder` — device row or registry fallback, declared device id or not) — never one admitted under another key (a K_d device) or by the master token. Retiring is synchronous, because `ws.close()` only starts a handshake and a CLOSING socket still delivers frames: the peer is marked `retired`, removed from `connections`, handed to `onRemoved` for its one close-time roster observation, then closed 4010; `onMessage` acts on no frame from a socket that is not OPEN or is retired. A rotation that lands mid-verification is refused at registration and recorded (`key_retired_during_verification`) (`__tests__/key-retirement-sockets.test.ts`, `websocket-route.test.ts`). **Every other door that ends a credential closes what it admitted too** (#776; the door table is in `connection-ports.ts`, and each port is a REQUIRED dep called after the door's writes). The doors that move a key without naming one retired key are accept-migration (registry and holder key overwritten), the receipt heal (registry fallback moved) and pairing's `update-key` (one device row rewritten). They call `ReconcileKeyConnections`, which closes 4010 every socket whose token would no longer verify under the key that admitted it. The check is resolved per (`authenticatedDid`, key), the way the verifier resolves it. It is never per key alone, because claim accepts any canonical key and another device's row may hold the same one. Identity revocation (`/revoke`, migration departure, and the operator's `revoke-listing`, all of which make the verifier refuse with `agent_revoked`) calls `CloseIdentityConnections`, which closes 4011 every socket an identity credential admitted, under ANY key. `/revoke-tokens` calls `CloseTokenConnections`, which closes 4012 the sockets whose `authenticatedJti` it blacklists. A token revocation is an identity's act over its OWN tokens: `relay_token_blacklist` has been keyed `(motebit_id, jti)` since migration v44, and `isTokenBlacklisted(jti, motebitId)` reads both. Keyed by jti alone, identity X naming V's jti denied V's token relay-wide while leaving V's socket open, and X could pre-plant V's jti so that V's own revocation was dropped. A non-string jti is refused before any write. Master-token and no-auth sockets stay open, because none of these doors refuses them. A revocation or token revocation mid-verification is refused at registration like a rotation (`agent_revoked_during_verification`, `jti_blacklisted_during_verification`) (`__tests__/credential-end-sockets.test.ts`). Known residual: for an identity holding NO key at all, `register-self` is first-come (`device-registration-guard.ts` enforces only when a key is held), so a stranger can plant the very key it then departs from — tracked, and to be closed at that door. NOT closed here: desktop, web and mobile still sign their rotate-key bearer with the NEW key, which no relay can verify, or post to routes that do not exist (#709; the CLI reaches this route correctly since the #702 client half — `apps/cli/src/rotation.ts`, built to `docs/proposals/key-rotation-client-v1.md`, reads the public succession route first and submits signed by the retiring key), deregistration deletes the guardian with the discovery row, federation's `key_rotated` writes a registry key from a payload its signature does not cover, and a record's self-asserted `timestamp` is bounded only by the 15-minute freshness window — two rotations inside it can be recorded out of order, which the chain is SERVED in (`ORDER BY timestamp`), so a verifier sees a broken link. That last one is reachable on any registered identity and predates this rule.
22. **An `agent_registry` row is delisted, never deleted.** The row holds two facts with two lifetimes — discoverability, which leaves on departure or a lapsed lease, and identity key state, which leaves only by revocation (and revocation keeps the row, marked). Leaving the shelf goes through `registry-delist.ts` (`delistRegistration` / `delistExpired`; the two terminal revocation doors — `/revoke`, migration departure — spell the same clause out, and the operator's revoke-listing (a reversible hold that keeps the discovery fields) spells its `delisted_at` half, so rule 21's gate can see `revoked = 1`; a test pins the spellings to `DELIST_SET`), and every discoverability reader carries `ON_SHELF` (`delisted_at IS NULL`). A reader whose question is "what is this identity's key" must NOT carry it. `check-registry-never-deleted` (#162) locks the DELETE; #703, `docs/proposals/identity-key-state-v1.md`.
23. **What the relay SERVES as an identity's key is the holder, and only EVIDENCE writes it; what a rotation departs from is the holder, else exactly main's rule.**
    - `identity_keys` (`identity-keys.ts`) answers the §7.6 bundle, the identity log and `GET /api/v1/agents/:id/succession` (`current_public_key`). Nothing else is served.
    - Evidence kinds, and nothing else, write the holder:
      - E-sov: the id is EXACTLY the sovereign commitment to the key AND the request proved current possession (register-self's signature, or an `/agents/register` bearer verified by the device row holding it, keyed or keyless); `recordFirstIdentityKey`, one transaction.
      - E-link: `applySuccession`, only from the key the holder holds.
      - E-mig: accept-migration.
      - E-op: an operator registration of a bare service identity.
      - E-main: the v42 transplant of main's registry key only.
    - `departureFrom`, the `/agents/register` succession check, and every signature reader (`verificationKeyFor`) use the holder when there is one, else EXACTLY main's read. The keyless registration writes main's exact registry value, because departure's inputs must be main's too.
    - New keys must be canonical lowercase hex (`admitKey`; a stored key is admitted in its exact spelling). Retire statements match case-insensitively.
    - A door that writes the holder without evidence, a reader that SERVES the registry or chain, or a departure rule that differs from main's for an unfilled identity, is the #747/#750/#753 class. #703 Inc 2; `docs/proposals/identity-key-state-v1.md` §5e–§5j.

24. **The machine roster: the relay stores and observes, and never reduces.** `host-roster-store.ts` + `host-roster-routes.ts` (`spec/machine-roster-v1.md` §8/§11; [`docs/doctrine/machine-roster.md`](../../docs/doctrine/machine-roster.md); design `docs/proposals/machine-roster-relay-v1.md`).
    - **No relay code evaluates the roster law** (`verifyHostRoster`), decides membership, or computes a quantity over a motebit's machines — a relay that cannot compute a roster cannot compute a wrong one (the #698 class). `host-roster.test.ts` scans every relay source for a call or import of the reduction.
    - **Membership** (`relay_host_roster_entries`): entries held verbatim, keyed by the law's id, `INSERT OR IGNORE` is the idempotent union. Ingest is integrity only — strict guard + wire schema, path `motebit_id`, signature under the key the entry NAMES, verified before held — and deliberately has no `untrusted_key` check. Caps are partitioned by a STORED `bucket`, decided at ingest: `own` iff the entry's signer is the key the presenting caller's token verified under (auth.ts `onVerified`; cap 512 enrolments / 2048 retirements per signer key), else `foreign` (one shared cap, 256). Never a comparative count against the current caller — that let a thief's full own bucket block the sovereign's replication of superseded lines. Already-held is a no-op before any cap. Never pruned; no removal path (declared).
    - **Liveness** (`relay_host_liveness`): one overwritten `last_seen_at` per `(motebit_id, device_id, bound_under)`, where `bound_under` is `ConnectedDevice.boundUnder` — captured from the device row that verified the socket's token, never re-read (rotation rewrites device rows; the sockets the old key admitted are retired separately — rule 21). Persisted only for `deviceIdVerified` sockets announcing `unattended_runtime`, only through `observeHostConnection` (bind, close, five-minute flush, shutdown flush). `last_seen_at` = the last time the relay held a socket bound as that pair open; `sockets_open` = sockets it believes open, computed from `connections` at GET, never persisted. No heartbeat yet (#691): a half-open socket counts as open. Only an OPEN socket is ever registered (`finalizeConnection` checks `readyState` after the verification await — a client that closed mid-verification was a zombie peer served as open forever, #769 round 2) and the GET join, flush and sweep live-skip count only OPEN sockets. Entries over 4096 bytes are refused `too_large`; the POST body is capped. 90-day TTL on `last_seen_at`, skipping rows with a live bound socket.
    - **Routes** are first-person as "caller PRESENT and EQUAL" to the path id, verified under a DEVICE row's key (audience `device:auth`); the master token and service-mode (agent-registry) tokens get 403. `DECLARATION_CONTENT.retention.machine_roster` declares both tables.
