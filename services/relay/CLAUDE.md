# services/relay — the relay

The only function with a legitimate centralization premium (multi-device sync). Also: settlement, federation, discovery, rate limiting, disputes, credential anchoring.

Modules: `index`, `federation`, `task-routing`, `credentials`, `pairing`, `data-sync`, `accounts`, `a2a-bridge`, `logger`, `discovery`, `migration`, `disputes`, `p2p-verifier`, `transparency`, `settlement-rails/*`, `webhooks/*`.

## Rules

0. **The master token never leaves the relay.** `forwardTaskViaMcp` authenticates to a worker AS THE RELAY with a relay-signed `mcp:call` token bound to that worker (`mintRelayMcpBearer`, fresh per HTTP request, verified by the worker under its pinned relay key and accepted once per worker replay store — its own store, never the callers'); `apiToken` is never a bearer to any registered endpoint, and a forward without a dispatch token or a bearer minter is refused. **The dispatch token is never the bearer** (#981): it is an admission record the relay also hands to a submitter that presents the task itself, so a worker serving it as the relay served the submitter as the relay; it travels only as the `motebit_task` `dispatch_token` argument, and `@motebit/mcp-server` refuses it at the transport with a reason (`__tests__/dispatch-presenter-981.test.ts`). The reverse direction holds too: **no worker holds the master token** — a worker authenticates to this relay with its OWN key (per-audience signed tokens after a public `POST /api/v1/agents/bootstrap`), enforced by `check-worker-no-master-token`. See [`docs/doctrine/task-admission.md`](../../docs/doctrine/task-admission.md) §"The relay authenticates as itself" and §"The worker authenticates as itself".
1. **Outbound URL law.** Any URL the relay did not author and will contact — a registered agent `endpoint_url`, a federation peer `endpoint_url` — passes `@motebit/sdk` `checkOutboundUrl` (via `buildOutboundPolicy`) at persist time AND at connect time (`forwardTaskViaMcp`). Only globally-routable http(s); `MOTEBIT_ALLOW_PRIVATE_ENDPOINTS=1` is the local-dev allowance and is never set on Fly. See [`docs/doctrine/security-boundaries.md`](../../docs/doctrine/security-boundaries.md) §"Outbound URLs".

2. **Never inline protocol plumbing.** Audit the package layer first: `@motebit/protocol` → `@motebit/crypto` → `@motebit/encryption` → `@motebit/mcp-client` → `@motebit/mcp-server` → `@motebit/runtime` → `@motebit/core-identity` → `@motebit/identity-file`. If none match, a primitive is missing — add it to the right package, consume here. `check-service-primitives` catches inline `fetch` to motebit endpoints, JSON-RPC strings, direct `signExecutionReceipt` calls, and `canonicalJson`/`sha256` constructing protocol-shaped payloads.
3. **`SettlementRailRegistry.register()` accepts only `GuestRail`.** The registry and the three concrete guest rails (`StripeSettlementRail` fiat, `X402SettlementRail` protocol, `BridgeSettlementRail` orchestration) live in `@motebit/settlement-rails` (Layer 1); the `@ts-expect-error` negative proof is in that package's `__tests__/custody-boundary.test.ts`. The `/health/ready` rail manifest advertises only guest rails. Sovereign rails are agent-custody and live in `@motebit/wallet-solana`. Rails accept an injected `logger` — the relay supplies its module-scoped `createLogger` adapter at construction.
4. **Structured logging.** `createLogger(module)` emits JSON with `x-correlation-id` propagated through request lifecycles. Never `console.log` in production paths.
5. **Rate limiting is per-IP, per-connection, per-peer.** 5-tier fixed window (auth 30/min, read 60/min, write 30/min, public 20/min, expensive 10/min). WebSocket 100 msg/10s per connection. Federation 30 req/min per peer. Task queue hard-capped at 100K. Per-submitter queue limit 1000/agent (HTTP 429).
6. **Fail-closed on auth.** Signed bearer tokens require `aud` audience binding. The closed registry of canonical audiences lives in `@motebit/protocol`'s `TokenAudience` literal union (see `packages/protocol/src/audience.ts`); `check-audience-canonical` enforces every signing site against `ALL_TOKEN_AUDIENCES`. Today's set: `sync`, `device:auth`, `pair`, `rotate-key`, `push:register`, `task:{submit,query,result}`, `task:dispatch` (relay-signed per-task admission artifact — `mid` = worker, `sub` = relay task id — attached to every MCP forward and returned to the submitter; verified by `@motebit/mcp-server` `taskAdmission` against the pinned relay key before `motebit_task` runs, one execution per `sub`; the relay never accepts it inbound; see [`docs/doctrine/task-admission.md`](../../docs/doctrine/task-admission.md)), `admin:query`, `proposal`, `receipts:read`, `market:{listing,query}`, `credentials`, `credentials:present`, `account:{balance,deposit,withdraw,withdrawals,checkout}`, `proxy:token` (caller===`:motebitId`-authed mint of a cloud-inference billing token that carries the agent balance — least-privilege so a generic read token cannot be replayed to mint a spending credential; 2026-07-07. The token's `models` ceiling is keyed on FUNDING SOURCE — `modelsForAccount`: a free-credit-only account gets the Sonnet/Haiku-class list, any real ledger credit unlocks `DEPOSIT_MODELS`; the proxy enforces the list and, since 2026-09-13, per-token spend / per-identity rate / concurrency controls before any provider call) (`account:deposit` reserved — the self-declared deposit route was removed as a treasury-drain vector; balance is credited only by verified funding), `browser-sandbox-grant`, `browser-sandbox`, `runtime:attach` (local runtime-host attach handshake — verified by `@motebit/runtime-host` on the machine-local socket only; the relay never accepts it), `mcp:call` (a caller's own bearer to a motebit MCP server — caller→MCP-server, bound to the target via `sub` = the server's `motebit_id`, single-use per `jti`, minted fresh per request; verified by `@motebit/mcp-server`, never accepted by the relay; #957 — and the relay's OWN forward bearer, `mid` = the relay, signed by the relay key, verified under the worker's pinned relay key; #981). Cross-endpoint replay defense: a token bound to one audience is rejected by an endpoint expecting another (each route configures its own `expectedAudience` via `dualAuth`/`verifySignedTokenForDevice`); a signing-side typo would have been a runtime 401 pre-registry, now a compile error. `InboundCredentialVerifier` adapter takes precedence over static `authToken`. **Every master-token presentation and every refused signed token is recorded** in `relay_auth_events` (`auth-events.ts`; kind, method, path, claimed `mid`, audience, reason, correlation id — never token bytes, never IP; 30-day window) and readable at `GET /api/v1/admin/auth-events` — posture is proven from the relay's own record, not a log tail (2026-09-14: Fly's buffer ended before the deploys an audit needed). A new auth decision site MUST call `recordAuthEvent` beside its log line. A refusal made before any token verifies — no credential, a bearer that does not parse, a legacy plain-UUID device token — is recorded too, with a null subject (`recordRefusalBeforeVerify`; `missing_token` / `unparseable_token` / `legacy_token`) at `dualAuth`, the agent-route and proposal middleware and `/sync/*` (#846 v3). The subject of a rejection is always the CLAIMED `mid`, never a verified one.
7. **Relay is a convenience layer, not a trust root.** Every truth the relay asserts (credential anchor proofs, revocation memos, settlement receipts) is independently verifiable onchain without relay contact. If you add a relay-only assertion, justify why it is not protocol-shaped.
8. **Federation circuit breaker.** Per-peer forward tracking; automatic suspension at 50% failure rate over ≥6 samples. Heartbeat handles liveness (3 missed → suspend, 5 → remove). The three-state engine lives in `@motebit/circuit-breaker` (Layer 1) — `services/relay` instantiates it in `task-routing.ts` and injects a module-scoped logger. Adding a second caller (MCP client retry, webhook delivery) means a second `new CircuitBreaker({ logger })` at the consumer, not a wrapper here.
9. **P2P settlement path** is policy-based (`evaluateSettlementEligibility` in `task-routing.ts`): worker declares `settlement_address`, no active disputes between pair, and either an established pair (trust ≥ 0.6, interaction count ≥ 5) or the delegator's cold-start acknowledgment (`settlement_modes` is vestigial for eligibility since Arc 3). **Identity binding is an additive eligibility signal, never a gate:** a sovereign-bound worker (offline `verifySovereignBinding` over the registry `public_key`) qualifies at a reduced cold-start bar (`first_contact` + 2 interactions) because its `motebit_id` commits to its key and so cannot be a throwaway sybil. The branch sits _after_ the strict branch, so unbound/legacy workers are unaffected; it never fabricates trust. Same shape as the additive `HardwareAttestationSemiring` (rule on hardware attestation) — see [`docs/doctrine/identity-binding-verification.md`](../../docs/doctrine/identity-binding-verification.md) § "Binding strength feeds settlement". P2p tasks skip virtual-account allocation; money moves onchain in a **single atomic Solana multi-output transaction** composing two SPL Transfer instructions — delegator→worker (the worker's listing unit_cost, recorded as `amount_settled`) and delegator→relay_treasury (the 5% platform fee, recorded as `platform_fee`). Treasury address is the relay's identity-derived Solana wallet (`deriveSolanaAddress(relayIdentity.publicKey)` — same address used by `OperatorSolanaTransfer` for Path 0 and `SolanaMemoSubmitter` for anchoring). Relay records audit with `settlement_mode='p2p'`. Async `startP2pVerifierLoop` in `p2p-verifier.ts` polls Solana RPC, walks `transfers[]` for both legs, and resolves each row to `verified` / `failed` / `unverifiable` (#959). **Payee law:** a P2P record's payee (column and signed body) is the worker the payment PAID — the admitted `target_agent` (`p2pPayeeOf`, `p2p-payee.ts`), never the submission-path agent (the runtime submits to the DELEGATOR's own endpoint); a P2P receipt signed by anyone else records nothing, in all three writers (parent, `settleSubReceipt`, federated origin). **Legs:** the fee leg (exact `platform_fee` to this relay's treasury) is always checked; the worker leg is checked when the row's `p2p_worker_leg` is `local` (NULL legacy = local). That scope is declared by ADMISSION (`P2pAdmission` on the queue entry), never inferred from the payer-supplied proof or from a missing registered address: branch selection reads the row's shelf state and the proof's shape — on the discovery shelf (`ON_SHELF` and not revoked) ⇒ local whatever the proof; delisted but not revoked (a daemon that shut down and deregistered, or a worker that moved) ⇒ local for a 2-leg proof, the federated plan for a 3-leg one; revoked ⇒ never local — and a local worker is paid at its registered address (no registered address ⇒ not P2P-eligible; the derived-address check in the local branch is only a defensive floor), and a local proof carrying `b_fee_*` is refused 400; `remote` is recorded only from a BUILT federated plan, with the plan's executor recorded as `planned_peer` at admission BEFORE the forward (a lost 5xx/timeout response keeps it, and so does a 409 `{status:"duplicate"}` — the executor already holds the task; only another 4xx refusal clears it — `p2pWorkerLegScope`), and `onTaskResultReceived` accepts a P2P task's result only from that planned peer; `presenter: "submitter"` on a cross-operator task is refused 400 (the relay's forward is the only presenter); a P2P admission with neither a local binding nor a built plan is refused. The executor relay's admission is always `local`. The worker leg matches only an exact-`amount_settled` transfer to the payee's derived-bound address or its OWN locally registered `settlement_address` AS ADMITTED (`p2p_worker_address` + `p2p_worker_address_rung`, so a mid-flight re-registration cannot fail a correctly paid payer; write-authorized — settlement-authority-binding § "Where binding is enforced"); a peer-asserted string never counts. `unverifiable` (never `verified`, names no one): a local worker leg with no bound address, a `remote` row with no fee leg, or a pre-#959 row naming its own payer with no archived self-signed receipt (a self-delegation admitted now verifies normally). **Attribution:** every leg is the PAYER's obligation; a failure is recorded on the settlement row (`failed`, the leg, the reason) and a warn log — NO trust edge moves (`[worker, delegator].failed_tasks` is a competence signal about the delegator as a worker, and the relay may not write payer-side facts into the worker's first-person ledger), and no `settlement_modes` change. A refused P2P receipt never overwrites the delivered result (the result route and the MCP forward give the entry a receipt only after ingestion accepts it, and the federated origin refuses before mutating the entry — #961, #890 r6). Pre-#959 rows are corrected beside the signed record (`relay_settlement_payee_corrections`, migration v48), never rewritten; a pre-#959 federated-origin row is backfilled `remote` only where durable data shows it (no archived receipt + the queued forward shape), else it fails closed. The state-export settlement summary counts neither `failed` nor `unverifiable` rows. Pre-Arc-2 zero-fee P2P rows remain verifiable via the verifier's backward-compat branch (skips fee-leg check when `platform_fee === 0`). 10. **Withdrawal hold during dispute window** — `AccountStore.getUnwithdrawableHold` (Layer-1 `@motebit/virtual-accounts`, implemented by `account-store-sqlite.ts`) sums recent relay settlements < 24h not yet disputed. `requestWithdrawal` pre-checks available balance before atomic debit. P2p settlements explicitly excluded. `accounts.ts` is a deprecation shim that routes the legacy functional API through a per-db `SqliteAccountStore`; new code consumes `@motebit/virtual-accounts` directly.
11. **Operator transparency declaration is the source of truth** (`transparency.ts` + `PRIVACY.md`). The signed JSON at `/.well-known/motebit-transparency.json` and the committed `PRIVACY.md` both derive from `DECLARATION_CONTENT`. Any code change that adds a processor, a retained field, or a retention window must update `DECLARATION_CONTENT` in the same PR — the sibling-boundary test in `__tests__/transparency.test.ts` enforces sync, but a code-vs-declaration drift (e.g., adding Sentry without naming it) the test cannot catch. Manual review for the doctrine in `docs/doctrine/operator-transparency.md`.
12. **`relay_receipts.receipt_json` is append-only and byte-identical.** The column must equal `canonicalJson(receipt)` at write time; any mutation breaks the auditor's signature reverification path (the whole point of the archive — `spec/execution-ledger-v1.md` §11.1 Storage). Persist through `persistReceiptChain` in `receipts-store.ts`; read through `getStoredReceiptJson` and return the bytes verbatim. Never `JSON.parse` + re-serialize through a non-JCS path on the way out.
13. **Aggregated withdrawals debit at enqueue time.** `enqueuePendingWithdrawal` in `batch-withdrawals.ts` debits the virtual account before inserting the `relay_pending_withdrawals` row; the fire path (serial or `withdrawBatch`) does NOT re-debit. A rail failure is decided by the money rule — refund ONLY what provably never left: a `PayoutNotSentError` (`@motebit/settlement-rails`; thrown only before anything is signed or broadcast) or a MANUAL rail's failure is refunded through the ledger in one transaction with the row's `refund_owed → refunded` compare-and-set (at most once; a refund the emergency freeze refuses stays `refund_owed` until the first tick after unfreeze); every other failure (any other throw, a per-item batch failure, a send the process died in) is NEVER refunded — the row goes `unknown` and a `processing` relay_withdrawals row with the payout's horizon is recorded in the same transaction, so the #921 reconcile door settles it. A `firing` row is recovered (never re-sent) only when no send can be running for it. Rows parked `failed` before this rule are left to the operator (some may have been paid). Harness: `__tests__/batch-withdrawal-failed-refund.test.ts`. Never short-circuit the debit-before-insert order; doing so opens a double-spend window against concurrent sweeps. See `spec/settlement-v1.md` §11.2.
14. **Native SQLite driver is mandatory — no silent sql.js fallback.** The relay is the only centralized, durability-sensitive node; it MUST run on `better-sqlite3` (native, WAL-enabled, per-commit fsync) and NEVER on `sql.js` (WASM, WAL no-op, 1-second-debounced full-file rewrites). `services/relay/package.json` declares `better-sqlite3` as a direct dependency so `pnpm deploy --prod` flattens it into the runtime image — without this, the binding is dropped (it's an `optionalDependency` of `@motebit/persistence` for the CLI scaffold's exotic-platform fallback) and the service silently degrades. Boot path uses strict `createMotebitDatabase` (throws if missing), not fallback-friendly `openMotebitDatabase`. The `relay.starting` log includes `driver` so every boot prints the driver identity. Enforced by `check-deploy-parity` rule 4 (drift-defenses #42); historical incident in `docs/drift-defenses.md` §42.

15. **External medium plumbing speaks motebit vocabulary, not provider vocabulary.** Provider-native types — webhook schemas (`Stripe.Event`, `Bridge.*`), SDK calls, chain JSON-RPC envelopes (`eth_getLogs`, `eth_blockNumber`) — never leak into the relay's business logic. Each external boundary ships an adapter that (a) owns the wire format and signature/error primitives and (b) maps to a closed motebit-shaped type before handing to the consumer. Webhook adapters live under `webhooks/*`, return `null` on signature failure, and surface unknown events as `{ kind: "ignored", type }` so the switch stays exhaustive. Chain-RPC adapters live next to their consumer (e.g., `deposit-detector/rpc-adapter.ts`) and collapse every wire-level failure (network / non-2xx / JSON-RPC error / malformed body) to a single thrown `Error` — the state-machine's try/catch already handles that shape. Concrete today: `StripeSubscriptionEventAdapter` in `webhooks/stripe-webhook-adapter.ts` (consumed by `registerProxyTokenRoutes`); `HttpJsonRpcEvmAdapter` in `deposit-detector/rpc-adapter.ts` (consumed by the deposit-detector state machine). The medium-plumbing extraction mirrors the guest-rail pattern in rule 2: external APIs churn on their own cadence and must not couple to account-crediting logic.

16. **x402 facilitator construction goes through `x402-facilitator.ts` — never inline `new HTTPFacilitatorClient(...)`.** The single canonical adapter chooses CDP-authed mainnet vs. unauthenticated testnet based on env shape, and **fails fast with `X402ConfigError` when `X402_TESTNET=false` is set without `CDP_API_KEY_ID` + `CDP_API_KEY_SECRET`**. The default `https://x402.org/facilitator` is testnet-only and silently passes startup health checks while rejecting mainnet networks at route-registration time — a half-mainnet trap the centralized constructor closes. Two consumers today: `index.ts` (settlement-rail registration) and `tasks.ts` (x402 HTTP middleware). Adding a third consumer means a third call to `createX402FacilitatorClient`, never a fresh inline construction. 29. **Allocation money moves through ONE function.** `moveAllocationMoney` (`allocation-escrow.ts`) is the only writer of allocation money — hold, settlement fee / credit / release, federated forward and its return, retry-exhaustion refund, stale sweep, dispute claw-back / worker / delegator legs. 30. **The emergency freeze holds where money moves, not only at entry.** The middleware 503s a mutating request at ENTRY. Allocation money moves only through `moveAllocationMoney` (rule 29), and the freeze sits AT that chokepoint: its first act is `assertNotFrozen` (`freeze.ts`, reading the PERSISTED freeze row in the caller's transaction), and the forward lifecycle's per-send claim `beginForwardSend` refuses the same way — called immediately before EVERY POST of `/federation/v1/settlement/forward` (the first send and each retry), so a freeze that lands during one send stops every later one, and a forward already `delivered`/`failed` is never re-sent. `installFreezeMoneyGuards` (called at boot after EVERY schema mutation — schema, migrations, the task queue's `receipt_signature` column; it throws if a declared money column is missing) is the second layer: TEMP `BEFORE INSERT/UPDATE/DELETE` triggers on every money table refuse every other money writer (withdrawals, deposits, x402 credit, inbound federated credit) and any raw write past the chokepoint. Guards are on money COLUMNS, declared (`FREEZE_MONEY_COLUMNS`) so a first boot and a restart install the same guard: a settlement row's `anchor_batch_id` and P2P verification record (`FREEZE_NON_MONEY_COLUMNS`) and a forward's `pending → delivered` acknowledgement commit while frozen; every other column change is refused (an unclassified live column fail-closed). A multi-write that a refusal could split is one transaction: each anchoring cut (signed batch row + leaf assignments, `AND anchor_batch_id IS NULL`), horizon cert + truncation. Exhaustion of a forward's retries checks the freeze in the same turn as failing the retry and refunding. The abort (`EMERGENCY_FROZEN`) maps to `EmergencyFrozenError` (503), never a 500 or a 200: a withdrawal whose payout claim the freeze refused (after its debit) answers 503 and stays `pending`, amount held; an x402 payment settled onchain whose credit was refused answers 503 naming its record (do not pay again); a round-2 dispute verdict whose fund action was refused is kept and finalized by the first read after unfreeze. A provider webhook is retried only on a non-2xx: the Stripe subscription and deposit webhooks answer a refused credit 503 (any other processing failure 500), each event's writes one transaction, so the replay after unfreeze credits once. A Path 0 payout that landed and failed on-chain whose refund the freeze refused answers 503 and stays `processing` with the proven outcome recorded (the operator's `not_paid` reconcile refunds it); the operator's x402 resolve answers a refused credit 503, never a 200 `read_error`. Claims and queue rows are not guarded, so a refused write leaves its work where a crash between claim and settle would and it resumes once after unfreeze; a claimed-but-unsettled entry is never swept while frozen, nor for the claim hold after an unfreeze (`claimHoldFloor`). Every money-shaped table is in `FREEZE_GUARDED_MONEY_TABLES` or `FREEZE_EXEMPT_TABLES` with its reason, and the relay opens its database only in `index.ts` (TEMP triggers are per connection).
