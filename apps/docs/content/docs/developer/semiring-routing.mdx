Agent network routing is algebraic, not ad-hoc. The `@motebit/protocol` package provides a generic `Semiring<T>` interface, concrete semirings for different routing concerns, a `WeightedDigraph<T>`, and two traversal algorithms that answer every routing query the system needs. Most trusted path, cheapest pipeline, reachability, and all of the above simultaneously — by swapping the semiring.

## What a semiring is

A semiring `(S, +, *, 0, 1)` is an algebraic structure with two operations:

- **`add` (+)** — aggregates parallel alternatives. Commutative, associative. "Which of these routes is better?"
- **`mul` (\*)** — composes sequential edges. Associative. "What happens when I chain these two edges?"
- **`zero`** — additive identity. The "worst" or "impossible" value. No route.
- **`one`** — multiplicative identity. Passthrough edge. No effect on composition.

The key property: `mul` distributes over `add`. This means the graph traversal algorithm can compose edges and aggregate alternatives in any order and get the same answer. One algorithm works for every routing concern.

Two further preconditions make the traversal below terminate with that answer. `add` must be **idempotent** (`add(a, a) = a` — combining a route with itself changes nothing), and weights must be **0-closed**: going around a cycle never improves a path (`add(one, x) = one`). Every scalar semiring in the table is in fact **selective** (`add(a, b)` is always one of `a` or `b` — a choice, not a sum), which is stronger than idempotent; the frontier semiring below is idempotent but _not_ selective (the union of two frontiers is neither operand), and the traversal is correct for it all the same. Trust and reliability are ≤ 1 under `*`, costs and latencies are ≥ 0 under `+`, so a loop can only make a route worse. A weight outside its domain (a trust edge above 1, a negative cost) breaks the guarantee, which is why edge weights are validated at the boundary.

## Concrete semirings

Each semiring models a different routing concern over the same graph:

| Semiring                 | `(add, mul, zero, one)`  | What it computes                                                |
| ------------------------ | ------------------------ | --------------------------------------------------------------- |
| `TrustSemiring`          | `(max, *, 0, 1)`         | Most trusted delegation chain                                   |
| `CostSemiring`           | `(min, +, Inf, 0)`       | Cheapest agent pipeline                                         |
| `LatencySemiring`        | `(min, +, Inf, 0)`       | Fastest sequential path                                         |
| `ReliabilitySemiring`    | `(max, *, 0, 1)`         | Most reliable chain (probability product)                       |
| `BottleneckSemiring`     | `(max, min, 0, Inf)`     | Widest bottleneck path (capacity)                               |
| `BooleanSemiring`        | `(or, and, false, true)` | Reachability                                                    |
| `RegulatoryRiskSemiring` | `(min, +, Inf, 0)`       | Lowest regulatory risk path                                     |
| `MaxProductLogSemiring`  | `(max, +, -Inf, 0)`      | Most likely path in log space (avoids underflow on long chains) |

Trust and reliability compose multiplicatively — chaining two 80% trust edges yields 64% effective trust. That is a modeling choice, not a law of nature: the product treats each hop as an independent chance of failure. It guarantees only that a chain is never more trustworthy than any one of its own links; it says nothing about how a chain compares with a _separate_ direct edge (a 0.9 × 0.9 chain outranks a 0.1 direct edge), and independence is an assumption a correlated failure would violate. Cost, latency, and regulatory risk compose additively — chaining a $0.01 edge and a $0.02 edge costs $0.03. Bottleneck composes via `min` — the capacity of a chain is its weakest link.

```typescript
import {
  TrustSemiring,
  CostSemiring,
  BooleanSemiring,
  RegulatoryRiskSemiring,
} from "@motebit/protocol";

// Trust: best alternative (max), chains multiply
TrustSemiring.add(0.8, 0.6); // 0.8  (max — pick the better route)
TrustSemiring.mul(0.8, 0.9); // 0.72 (product — trust degrades along chains)

// Cost: cheapest alternative (min), chains add
CostSemiring.add(5, 3); // 3    (min — pick the cheaper route)
CostSemiring.mul(5, 3); // 8    (sum — costs accumulate along chains)

// Boolean: reachability
BooleanSemiring.add(true, false); // true  (either route works)
BooleanSemiring.mul(true, false); // false (both edges must exist)
```

## Product and record combinators

To optimize multiple concerns simultaneously, combine semirings:

### Product semiring

Pairs two semirings into a tuple. Operations apply component-wise.

```typescript
import { productSemiring, TrustSemiring, CostSemiring } from "@motebit/protocol";

const TrustCost = productSemiring(TrustSemiring, CostSemiring);
// Semiring<readonly [number, number]>

TrustCost.mul([0.8, 5], [0.9, 3]); // [0.72, 8] — trust * trust, cost + cost
TrustCost.add([0.8, 5], [0.6, 3]); // [0.8, 3]  — max trust, min cost
```

### Record semiring

Named fields instead of nested tuples. This is how `RouteWeightSemiring` is built:

```typescript
import {
  recordSemiring,
  TrustSemiring,
  CostSemiring,
  LatencySemiring,
  ReliabilitySemiring,
  RegulatoryRiskSemiring,
} from "@motebit/protocol";

const RouteWeightSemiring = recordSemiring({
  trust: TrustSemiring,
  cost: CostSemiring,
  latency: LatencySemiring,
  reliability: ReliabilitySemiring,
  regulatory_risk: RegulatoryRiskSemiring,
});
// Semiring<{ trust: number; cost: number; latency: number; reliability: number; regulatory_risk: number }>
```

One graph traversal computes trust, cost, latency, reliability, and regulatory risk in a single pass.

Read the result for what it is. Because `add` is component-wise, the value a record semiring assigns to a node reachable by two routes is the best trust of one route beside the best cost of the other — a true summary of the optima achievable **per dimension**, not a route. `{ trust: 0.81, cost: 1 }` can come back for a node whose only routes are `(0.81, 10)` and `(0.2, 1)`. Ranking on that summary, or reporting it as the hire's metrics, describes a route that does not exist. Ranking therefore runs over the [Pareto frontier semiring](#path-preserving-ranking-the-pareto-frontier-semiring) below, which keeps the pairs together.

### Mapped semiring

Transform a semiring through an isomorphism — a pair of maps that are exact inverses of each other. The semiring laws survive only if nothing is lost in either direction, so a rounding step is not a valid map (`round(x * 100) / 100 ≠ x` breaks `add(a, a) = a` and associativity in the last digit). The intended uses are branded types and lossless unit changes:

```typescript
import { mappedSemiring, CostSemiring } from "@motebit/protocol";

// Branded micro-units over the same integer arithmetic (1 USD = 1_000_000).
// The maps are identities on the value — only the type changes — so every
// semiring law holds exactly. Money enters the graph already in micro-units.
type Micro = number & { readonly __brand: "Micro" };
const MicroCostSemiring = mappedSemiring(
  CostSemiring,
  (micro: Micro) => micro as number,
  (n: number) => n as Micro,
);
```

## Graph and traversal

### WeightedDigraph

A directed graph parameterized by a semiring. Nodes are string IDs (typically `motebit_id` values). Edges carry semiring-typed weights.

```typescript
import { WeightedDigraph, TrustSemiring } from "@motebit/protocol";

const graph = new WeightedDigraph(TrustSemiring);
graph.addNode("alice");
graph.addNode("bob");
graph.addNode("carol");

graph.setEdge("alice", "bob", 0.9); // Alice trusts Bob at 0.9
graph.setEdge("bob", "carol", 0.8); // Bob trusts Carol at 0.8
graph.setEdge("alice", "carol", 0.5); // Alice trusts Carol directly at 0.5
```

### Bellman-Ford: single-source optimal paths

`optimalPaths` computes the optimal semiring value from a source to every reachable node. This is generalized Bellman-Ford — relax edges using `add` (choice) and `mul` (composition).

```typescript
import { optimalPaths } from "@motebit/protocol";

const paths = optimalPaths(graph, "alice");
// paths.get("bob")   → 0.9   (direct)
// paths.get("carol") → 0.72  (max of 0.5 direct, 0.9 * 0.8 = 0.72 via Bob)
```

Over `TrustSemiring`, this finds the most trusted delegation chain. Over `CostSemiring`, the cheapest pipeline. Over `BooleanSemiring`, the reachable set. Same algorithm, different semiring, different answer.

Complexity: O(V \* E) semiring operations for the scalar semirings, under the idempotent and 0-closed preconditions above. Early termination when no values change. For the frontier semiring each operation is itself O(frontier size), which `maxPaths` bounds.

### Floyd-Warshall: all-pairs transitive closure

`transitiveClosure` computes the optimal semiring value between every pair of nodes. Used to pre-compute the entire trust network.

```typescript
import { transitiveClosure } from "@motebit/protocol";

const closure = transitiveClosure(graph);
// closure.get("alice")?.get("carol") → 0.72
// closure.get("bob")?.get("alice")   → 0 (no path)
```

Complexity: O(V^3). Use `optimalPaths` for single-source queries on large graphs.

### Path tracing

`optimalPathTrace` returns both the optimal value and the actual path (sequence of node IDs):

```typescript
import { optimalPathTrace } from "@motebit/protocol";

const result = optimalPathTrace(graph, "alice", "carol");
// result.value → 0.72
// result.path  → ["alice", "bob", "carol"]
```

Returns `null` if no path exists.

## Provenance tracking

The provenance semiring answers "why did the system produce this result?" — not as a separate logging system, but as a first-class semiring query over the same graph.

Provenance models derivation as sets of paths:

- `add` (parallel) = union of derivation sets — "either route works"
- `mul` (sequential) = cross-product of paths — "both edges used"
- `zero` = empty set (no derivation)
- `one` = `{[]}` (trivial derivation)

### Annotated semiring

Combine any value semiring with provenance tracking:

```typescript
import { TrustSemiring, WeightedDigraph, optimalPaths } from "@motebit/protocol";
```

The protocol-floor symbols above are Apache-2.0 public surface. The `annotatedSemiring` combinator itself is reference-implementation judgment:

<ReferenceExample pkg="@motebit/semiring" source="packages/semiring/src/provenance.ts">

```typescript
import { annotatedSemiring } from "@motebit/semiring";
import type { Annotated } from "@motebit/semiring";

const AnnotatedTrust = annotatedSemiring(TrustSemiring);
// Semiring<{ value: number; why: Provenance }>

const graph = new WeightedDigraph(AnnotatedTrust);
graph.addNode("alice");
graph.addNode("bob");
graph.addNode("carol");

graph.setEdge("alice", "bob", { value: 0.9, why: [["bob"]] });
graph.setEdge("bob", "carol", { value: 0.8, why: [["carol"]] });
graph.setEdge("alice", "carol", { value: 0.5, why: [["carol"]] });

const paths = optimalPaths(graph, "alice");
const carol = paths.get("carol");
// carol.value → 0.72
// carol.why   → [["carol"], ["bob", "carol"]]
//                 direct      via Bob
```

</ReferenceExample>

Every query returns the per-dimension optimal value together with the set of paths that were **considered** in reaching it — the union of every route that survived the component-wise `add`. That set explains the derivation; it does not say which one route yields `value`, and under a record semiring no single route may. When the question is "which route was chosen, and what were its metrics?", ask the frontier semiring instead.

### Bounded provenance

Provenance can grow exponentially in graphs with many parallel paths. `boundedProvenanceSemiring(maxPaths)` caps the number of tracked derivations, keeping the shortest paths (fewest hops = simplest explanation):

<ReferenceExample pkg="@motebit/semiring" source="packages/semiring/src/provenance.ts">

```typescript
import { boundedProvenanceSemiring } from "@motebit/semiring";

const bounded = boundedProvenanceSemiring(10); // keep top 10 shortest derivations
```

</ReferenceExample>

The `annotatedSemiring` function uses bounded provenance by default (cap of 100 paths).

## Path-preserving ranking: the Pareto frontier semiring

Change what "best path" means by changing the semiring — the routing doctrine applied to its own weak spot. When several routes reach the same agent and no single route is best in every dimension, the honest value of that node is the **set** of routes nothing else dominates. That set is a semiring element:

- `add` (parallel) = union of the two frontiers, then drop every pair some other pair beats in **every** dimension — "either route works; keep only the ones a policy could pick"
- `mul` (sequential) = compose weight **and** path pairwise, then drop dominated pairs
- `zero` = the empty frontier (unreachable)
- `one` = `{ (identity weight, []) }` (the empty route)

Each element a query returns is a route that exists, carrying exactly the metrics its own edges compose to. A policy then chooses **among** real routes, and the chosen route's metrics are the chosen route's metrics.

<ReferenceExample pkg="@motebit/semiring" source="packages/semiring/src/pareto.ts">

```typescript
import { frontierPaths, chooseFromFrontier, ROUTE_WEIGHT_DIMENSIONS } from "@motebit/semiring";

// graph: self → worker (trust 0.2, cost 1) and self → helper → worker (trust 0.81, cost 10)
const frontiers = frontierPaths(graph, ROUTE_WEIGHT_DIMENSIONS, "self");
frontiers.get("worker");
// [
//   { weight: { trust: 0.2,  cost: 1,  … }, path: ["worker"] },
//   { weight: { trust: 0.81, cost: 10, … }, path: ["helper", "worker"] },
// ]
// — never { trust: 0.81, cost: 1 }, which is what the record semiring reports.

const trustFirst = chooseFromFrontier(frontiers.get("worker")!, (w) => w.trust);
// trustFirst.chosen.path   → ["helper", "worker"]
// trustFirst.chosen.weight → { trust: 0.81, cost: 10, … }   (its own edges, composed)
// trustFirst.ordered       → chosen first, then the alternatives the policy weighed
```

</ReferenceExample>

`paretoPathSemiring(dims, { maxPaths })` is the semiring itself, for callers that want to run `optimalPaths` over it directly. Dominance is judged per dimension by that dimension's own `add` (max for trust-like, min for cost-like), so adding a routing concern to the dimension record extends the frontier with no new code.

What is exact and what is not — the contract a caller is relying on:

1. **Unbounded, the frontier is exact.** It equals the Pareto set of simple paths from the source (ties on weight resolve to the fewest-hop path), independent of edge insertion order. The reference tests check this against brute-force enumeration on random graphs.
2. **A policy must be monotone in the frontier's dimensions.** Pruning discards a route only when another is at least as good in _every_ dimension, so a policy that could still prefer the discarded route — one that reads an input outside the dimensions — is unsound. The market ranks on six dimensions, not five, for exactly this reason: chain hardware attestation multiplies trust after the frontier is formed, so it is lifted into the weight (`min` along the route) rather than applied afterwards.
3. **The bound is an approximation with no optimality-gap guarantee.** `maxPaths` (default 32) keeps the fewest-hop pairs; it can drop the pair a policy would have chosen, nothing bounds how far the policy's pick can then fall below its optimum, and addition under it is order-sensitive in the tail. Reported metrics stay honest — a surviving pair is still a real route with its own metrics. Same discipline and same caveat as bounded provenance.

## Agent network bridge

The `@motebit/semiring` package includes a bridge layer that connects the generic algebra to Motebit's agent types.

### RouteWeight

The multi-dimensional edge weight used for agent routing:

```typescript
interface RouteWeight {
  trust: number; // [0,1] — multiplicative composition
  cost: number; // [0,Inf) — additive composition
  latency: number; // [0,Inf) — additive composition (ms)
  reliability: number; // [0,1] — multiplicative composition
  regulatory_risk: number; // [0,Inf) — additive composition
}
```

`ROUTE_WEIGHT_DIMENSIONS` names the five per-dimension semirings; `RouteWeightSemiring` is the `recordSemiring` over them (one traversal, five per-dimension optima — a summary), and `frontierPaths(graph, ROUTE_WEIGHT_DIMENSIONS, source)` is the path-preserving traversal ranking uses.

### Building an agent graph

<ReferenceExample pkg="@motebit/semiring" source="packages/semiring/src/agent-network.ts">

```typescript
import {
  buildAgentGraph,
  mostTrustedPath,
  cheapestPath,
  rankReachableAgents,
} from "@motebit/semiring";

const graph = buildAgentGraph(selfId, agents);

// Single-dimension queries via graph projection
const trusted = mostTrustedPath(graph, selfId, targetId);
// { trust: 0.72, path: ["self", "relay-a", "agent-xyz"] }

const cheap = cheapestPath(graph, selfId, targetId);
// { cost: 0.015, path: ["self", "agent-xyz"] }

// Multi-dimensional ranking over each agent's frontier of real routes
const ranked = rankReachableAgents(graph, selfId, {
  trust: 0.3,
  cost: 0.2,
  latency: 0.15,
  reliability: 0.15,
  regulatory_risk: 0.2,
});
// [{ motebit_id, score, route, path, alternatives }, ...]
//   route = the CHOSEN route's own composed metrics; path = that route's hops
```

</ReferenceExample>

### Graph projection

`projectGraph` projects a multi-dimensional graph down to a single semiring dimension — the functorial projection from `RouteWeight` to `T`:

```typescript
import { TrustSemiring } from "@motebit/protocol";
```

`TrustSemiring` is on the Apache-2.0 floor; the `projectGraph` combinator that consumes it is reference-implementation judgment:

<ReferenceExample pkg="@motebit/semiring" source="packages/semiring/src/agent-network.ts">

```typescript
import { projectGraph } from "@motebit/semiring";

const trustOnly = projectGraph(graph, TrustSemiring, (w) => w.trust);
// WeightedDigraph<number> — only trust edges, ready for TrustSemiring traversal
```

</ReferenceExample>

## Market integration: graphRankCandidates

The `@motebit/market` package's `graphRankCandidates` function is the primary routing entry point. It bridges the semiring algebra with the market's candidate scoring system:

1. Builds a `WeightedDigraph<RouteWeight>` from candidate profiles plus peer edges. Every peer edge declares what it **is** for this task: `kind: "evidence"` (a recorded delegation — it vouches, the task will not traverse it) or `kind: "traversed"` (a federation relay hop the task really takes).
2. **Trust** is evidence about the agent: the best transitive trust over _every_ edge, with the vouching path that attains it (`trust_evidence_path`).
3. **Execution metrics** — cost, latency, reliability, regulatory risk, hardware custody — describe work that will happen: `frontierPaths` over the graph restricted to hops the task will take (the direct hire, or a traversed relay path) gives, per candidate, the Pareto frontier of real planned execution routes. A delegation record's price and latency are a past job's, never this task's, so they never enter.
4. Normalizes additive accumulators (cost, latency, risk) to `[0,1]` via sigmoid mapping.
5. Applies a configurable composite function (default: weighted sum) to every planned execution route — evidence trust, that route's own execution metrics, that route's own custody boost — and keeps the winner.
6. Returns `RouteScore[]` whose `sub_scores` are the evidence trust and the chosen planned execution route's metrics.

Why the split: a relationship can vouch for an agent, but only hops the task takes can cost it money or time. Before this split (2026-09-14), hiring B directly with A's recorded delegation to B in the graph priced the hire with A's cost and latency added on.

Two rules keep the graph and the dispatcher in agreement. **Only dispatchable hops enter execution ranking:** a candidate discovered through a federation peer carries `reachable_via`, gets no direct edge, and its own metrics sit on the peer → agent leg. **Dispatch consumes the selected route:** the relay forwards to the peer the planned route names, never to one chosen independently. The route reported at selection time is the _planned execution route_; who actually took part is established afterwards by receipts.

<ReferenceExample pkg="@motebit/market" source="packages/market/src/graph-routing.ts">

```typescript
import { graphRankCandidates } from "@motebit/market";

const scores = graphRankCandidates(
  selfId,
  candidates,
  {
    required_capabilities: ["web_search"],
    max_budget: 0.1,
    currency: "USD",
  },
  {
    weights: { trust: 0.3, cost: 0.2, latency: 0.15, reliability: 0.15, regulatory_risk: 0.2 },
    maxCandidates: 5,
    explorationWeight: 0.1,
  },
);
```

</ReferenceExample>

### Explained routing

`explainedRankCandidates` extends `graphRankCandidates` with both paths a decision rests on. `routing_paths[0]` is the **planned execution route** — the hops the task will take, whose composed execution metrics the score reports (`["agent-xyz"]` for a direct hire; `["relay-a", "agent-xyz"]` for a federated one) — and the remaining entries are the non-dominated planned-route alternatives the policy weighed, best first. `alternatives_considered` is the size of that frontier. `trust_evidence_path` is the vouching chain, through every edge kind, that justified the trust value:

<ReferenceExample pkg="@motebit/market" source="packages/market/src/graph-routing.ts">

```typescript
import { explainedRankCandidates } from "@motebit/market";

const explained = explainedRankCandidates(selfId, candidates, requirements);
// explained[0].routing_paths → [["relay-a", "agent-xyz"], ["agent-xyz"]]
//   [0] = the planned execution route whose cost/latency/custody sub_scores report (via relay-a)
//   [1] = the direct route, viable but not chosen under this policy
// explained[0].alternatives_considered → 2
// explained[0].trust_evidence_path → ["agent-abc", "agent-xyz"]
//   the vouching chain behind sub_scores.trust — evidence, not execution
```

</ReferenceExample>

This flows end-to-end: the relay returns `routing_choice` on task submission, `PlanEngine` attaches it to the delegation step summary, and it is signed into the execution ledger manifest — an audit trail from semiring algebra to cryptographic proof. It is only worth signing because it is exact: the transcript names routes that exist and each route's own metrics, so a verifier can recompute them from the same edges. A component-wise summary would have signed a route that does not exist. Read each path for what it is: `routing_paths[0]` is the planned execution route (the hops the task takes — direct, or via the federation peer named on it), `trust_evidence_path` is the vouching chain (recorded delegation history, discovery, peers) behind the trust value. Neither is a claim about who did the work; that is proven by receipts.

### Composite functions

The composite function is a policy choice that determines how semiring-computed values are combined for ranking. Two built-in options:

<ReferenceExample pkg="@motebit/market" source="packages/market/src/graph-routing.ts">

```typescript
import { weightedSumComposite, lexicographicComposite } from "@motebit/market";

// Default: weighted sum (all dimensions contribute proportionally)
// composite = trust * 0.3 + costScore * 0.2 + latencyNorm * 0.15 + ...

// Lexicographic: trust first, then reliability, then cost — exact over
// keys QUANTIZED to 1e-3. Each key is rounded to 0..1000 and packed in
// base 1001, so a trust gap of one quantum or more can never be outweighed
// by the keys below it; two trusts inside the same 1e-3 band are equal by
// policy and reliability decides. That band is the declared tie tolerance.
// (`trust * 1e6 + reliability * 1e3 + costScore` had no such contract: an
// unquantized reliability spanned the whole 1e3 band.)
// lexicographicOver(["costScore", "reliability", "trust"]) builds the same
// quantized order for any key priority — the relay's `cost` strategy uses it.
```

</ReferenceExample>

Custom composite functions can be passed via the `RoutingPolicy`:

```typescript
const policy: RoutingPolicy = {
  composite: (route, scores) => {
    // Trust-or-nothing: if trust < 0.5, score is 0
    if (scores.trust < 0.5) return 0;
    return scores.trust * 0.5 + scores.costScore * 0.5;
  },
};
```

## Adding a new routing concern

Adding a new routing dimension requires only a new semiring definition — zero new algorithms:

```typescript
import type { Semiring } from "@motebit/protocol";

// Energy cost: accumulates along chains, pick the greenest route
const EnergySemiring: Semiring<number> = {
  zero: Infinity,
  one: 0,
  add: (a, b) => Math.min(a, b),
  mul: (a, b) => a + b,
};
```

Add the dimension to `RouteWeight`, add it to the record semiring, and the existing traversal algorithms handle the rest.
