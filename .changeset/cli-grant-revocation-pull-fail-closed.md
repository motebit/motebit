`motebit --grant <id>` and `motebit serve --direct --grant <id>` no longer present a standing grant on a turn where a relay's revocation feed could not be read. A timeout, a network error, a redirect, a non-2xx answer or a body that is not the feed used to count as "nothing revoked", so a grant revoked on another machine still verified whenever the relay was unreachable. Now a failed pull presents no grant for that turn: in chat, money actions ask for approval; on a direct task they are refused. Each outage is announced once, in one line that names the failure and the relay's host (for example `HTTP 429 (relay.example)`), never a URL or an error's own text; it is announced again when a different relay starts failing, and after the relays have answered again.

Each turn the pull goes to every relay named by any source: the `--sync-url` / `--sync` flag, the `MOTEBIT_SYNC_URL` environment variable, the saved config's `sync_url` (re-read each turn), and the relay the session is currently connected to (in chat, `/connect <url>` moves it). All of them, not the winning one: a revocation posted to the config relay is seen by a session started with `--sync-url` for another relay. If any pull fails, the grant is withheld; the records are merged. `motebit grant revoke` propagates to the one named relay (`--sync-url` > `MOTEBIT_SYNC_URL` > config `sync_url`). With no relay named anywhere, or when every pull succeeds, nothing changes.

The cost: a stale or unreachable relay left in the config or the environment under a flag override now withholds the grant every turn until it is removed; N relays mean N pulls per turn, each against that relay's 30 requests per minute per-address limit; and an `http://` relay URL that redirects to `https://` withholds until the URL is corrected. Not covered: a relay that omits a revocation, or a wrong relay URL (the feed is unsigned).
