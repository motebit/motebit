The relay's half of the machine roster: it stores what the sovereign signed, serves it back unchanged, and reports beside it — never inside it — what it has observed about each machine's connection. Increment 1, part B of `docs/doctrine/machine-roster.md`; the law it implements landed in #697.

**Membership.** `POST` / `GET /api/v1/agents/:motebitId/roster` (`spec/machine-roster-v1.md` §11). Entries are schema-parsed, **verified under the key they name before they are held** — the entry id excludes the signature, so an unverified copy could squat a slot and turn the authentic one into a no-op — and stored as canonical JSON keyed by the law's id, so `INSERT OR IGNORE` _is_ the idempotent union. Ingest checks **integrity only**. A first draft also refused entries under keys the relay did not associate with the motebit; but its notion of a motebit's keys is mutable rows that a data loss erases, so that gate refused — forever, a 422 on every reconnect — exactly the old-key lines a surface re-presents after such a loss. The routes are first-person, which is the bound on who may write; whose key counts is the consumer's question. There is no freshness window. Enrolments and retirements are capped **apart**: under one shared cap, a roster filled by a daemon minting per start refused the retirement of a stolen machine. A partial presentation is a **422**, and a field that is present but not a list is a **400**, not "absent". The relay does not reduce the set; a consumer does, against a key chain it verified.

**Liveness.** One overwritten `last_seen_at` per machine — never a history — written through a single function shared by the socket's close hook, a five-minute flush in the supervised cleanup loop, and a flush before shutdown clears the connection map (a force-closed socket never reaches its close hook, so a deploy would otherwise leave every machine's value stale or null). **One predicate** decides both what is recorded and what `GET` reports as `socket_open`: the connection announces that it hosts unattended work, its signed token **proved** its device id, the device is enrolled, and its registered key is one the line was enrolled under. The relay keeps nothing about when an unenrolled device came and went, and a plain session on the same machine does not overwrite what the host last announced.

**Where the relay must know whether a machine is retired, it asks the law.** A retired machine is no longer recorded — its connection is still _reported_, live, so a surface can say "retired, but connected" — and its record is deleted 30 days later. "Retired" is `verifyHostRoster`'s verdict under the relay's own view of the key chain, never "some held retirement names its enrolment": a retirement under an older key names an enrolment without ending it, and honouring it let a stolen old key have an **active** machine's last-seen value deleted, which the privacy declaration says never happens. Where the relay cannot tell the chain, it keeps recording and prunes nothing. Served as `socket_open`, not `connected`: there is no heartbeat with a deadline yet.

**The socket.** `ConnectedDevice.deviceIdVerified` — the declared `device_id` equals the `did` of the signed token the connection authenticated with. `?device_id=` alone is a query string. And the relay's WebSocket route gets its first tests: it had none.

**Both routes are first-person**, and the privacy declaration says so: `DECLARATION_CONTENT.retention.machine_roster` names both tables, what is observable, the retention windows, and that a roster is never published, ranked, aggregated, or served to another identity. `PRIVACY.md` re-rendered.

Nothing consumes the roster yet. The many-machine refusals in `command-route.ts` still count live sockets; they move to membership with #687 and #681. Migration v41.
