`motebit serve --direct` no longer executes a served tool straight from the registry. Both task doors — the MCP `motebit_task` tool and the relay WebSocket dispatch — execute through the runtime's policy gate (`MotebitRuntime.executeToolGated`), and every task submitter is a foreign principal: an R4_MONEY tool runs only when a presented standing grant (`serve --direct --grant <id>`) was signed by this motebit's own identity, names the caller the transport verified (motebit id and key) as its delegate, covers the tool, and passes the grant's spend ceiling. Without one it is refused with a failed receipt, never queued (no human is on this path). A relay-dispatched task carries no verified caller identity, so no grant clears R4 there. A grant revoked after `serve --direct --grant` or `motebit --grant` starts stops authorizing on the next call.

Behaviour changes: a tool above the governance auto-allow band (for example R2+ under the default preset) is refused on the direct path, as it already was over MCP. A standing grant signed by any identity other than this motebit — a stranger's self-issued grant, or an operator-issued grant naming this motebit as delegate — no longer authorizes spending; the call pauses for approval (owner turn) or is refused (task). Only the owner can delegate the owner's money. Authority derives from the immediate issuer: a grant spends only when its delegator is this motebit's id AND its current identity key. That narrows self-grants too: after `motebit rotate`, a `motebit grant create` grant signed under the previous key no longer authorizes spending (rotation leaves stored grants untouched; authority flows forward, never back) — re-issue it with `motebit grant create`. `motebit grant list` marks each grant signed by a previous key, and `motebit rotate` prints one line when live ones exist.
