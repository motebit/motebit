A P2P settlement record names the worker the payment paid, the verifier checks the worker leg against that worker as admitted, and a failed payment is recorded as the payer's on the settlement row — never against the worker, never in any trust edge, never on anyone's `settlement_modes` (#959).

- **Payee.** `handleReceiptIngestion` signed every P2P `SettlementRecord` with `motebit_id` = the path agent. The runtime submits P2P tasks to the DELEGATOR's own endpoint, so every record named the payer. The payee is now the admitted, pinned worker (`p2pPayeeOf`: `target_agent`, else the executor relay's forwarded task worker), in the parent writer, `settleSubReceipt`'s P2P branch and the federated origin writer. A P2P receipt signed by anyone else settles nothing (the task stays open for the paid worker), and at the result route and the federated origin it is refused before it can overwrite the delivered result. Duplicate checks are task-keyed, so a sub-hop's row written first is seen and never re-written or dropped. Known residual, not changed here: a relay-mode row's `motebit_id` column is still the path agent while its signed body names the credited worker (pinned by a characterization test).
- **Admission decides the worker leg.** The admission branch stamps a `P2pAdmission` on the queue entry — `remote` for a relay originating a cross-operator task, else `local`, plus the worker-leg address the proof was validated against and its settlement-authority rung — and every writer freezes it onto the row (`p2p_worker_leg`, `p2p_worker_address`, `p2p_worker_address_rung`). It is never inferred from the payer-supplied proof or from a missing registered address: a worker on the discovery shelf (not revoked, not delisted) always takes the local branch whatever the proof; a delisted-but-not-revoked worker (a daemon that shut down and deregistered) takes the local branch for a 2-leg proof, as main queued it, and the federated plan for a 3-leg one; a revoked registration is never local. A local worker is paid at its registered address (a worker with no registered address stays P2P-ineligible, as on main), a local proof carrying `b_fee_*` is refused 400 before admission, `remote` is recorded from a built federated plan together with its planned executor relay (recorded before the forward, so a lost response cannot strand an accepted task; cleared only by a 4xx refusal that is not a 409 `duplicate`, which means the executor already holds the task), a P2P task's federated result is accepted only from that planned executor, and `presenter: "submitter"` on a cross-operator task is refused 400. Stated cost: a federated-origin task already in flight at deploy (no admission record on its queue entry) settles `unverifiable` rather than `verified`; production has no external federation peers, so this affects zero rows. A pre-#959 federated-origin row is backfilled `remote` only where durable data shows it (no archived receipt + the queued forward shape). The state-export settlement summary excludes `unverifiable` rows as it excludes `failed` ones.
- **Verifier.** The worker leg matches only an exact-amount transfer to the payee's derived-bound address or its own registered address as admitted. A worker leg this relay owns but cannot check — no bound address, a `remote` row with no fee leg, or a legacy row naming its own payer with no archived self-signed receipt — is the new terminal status `unverifiable` (never `verified`, names no one). A self-delegation admitted now verifies normally. `getSettlementStatsByMode` reports `unverifiable_count`.
- **Attribution.** `downgradeP2pTrust` is removed. A failed leg is the payer's obligation, recorded on the settlement row (`failed`, the leg, the reason) and in a warn log; no trust edge moves and no `settlement_modes` change.
- **Historic rows (migration v48).** Signed/anchored records are not rewritten. `relay_settlement_payee_corrections` records the true payee beside a row that named its payer, derived from the unique signer of the archived receipt whose `result_hash` equals the record's `receipt_hash`; corrected rows the old verifier failed on the worker leg return to `pending`. Declared in the transparency declaration and `PRIVACY.md`.
- **Out of scope, filed as #965.** Pre-existing federation gaps the review found are not changed here: a planned executor peer can still deliver an unsigned or self-keyed receipt; the executor relay does not check a forwarded proof's worker address, amount or payer at `onTaskForwarded`; and the origin's export counts `remote` rows whose worker leg the origin never saw paid.
