Honest tool-receipt status and the repo-task run (governed repo change, milestone B build step 2).

- Every `ToolInvocationReceipt` the runtime signs now carries the call's real status. Scope: the receipt-signing paths are the streaming AI loop (`sendMessageStreaming` and the turns built on it), the approval resume/refusal/supersede/void/expiry paths and `invokeLocalTool`; the non-streaming `sendMessage`, `executeToolGated` (MCP direct and relay dispatch) and the attached-surface `tool_call` frame still execute tools without signing any tool receipt (a single signing choke point is follow-up work). The ai-core loop sets `outcome` on every `tool_status` done chunk (`completed` only for `ok: true`; `failed` for a throw or `ok: false`; `denied` for a policy, money-meter or offering refusal, which now carries its args and decision time). On those paths, every proposed call that is not executed gets a signed `denied` receipt whose result names why, where these used to get none: AI-loop refusals, human refusals on the approval resume, suppressed re-proposals, expired approvals, an approval request superseded by a later one in the same response (`SUPERSEDED_BY_A_LATER_APPROVAL_REQUEST`), an approval voided by a new user message (`VOIDED_BY_NEW_MESSAGE` — a record that the call never ran, not a refusal: it enters no refusal brake, so re-proposal still re-prompts the human), and `invokeLocalTool` refusals. Approved calls executed on the resume path get their own receipt. A done chunk without an `outcome` (a legacy hand-built stream) gets no receipt.
- `RuntimeConfig.toolReceiptSink` (`ToolReceiptSink`, `InMemoryToolReceiptSink`): a durable, fail-closed record of every tool receipt those paths sign, awaited in call order before the turn continues. A rejection, a missing signing key or a signing fault stops the turn.
- **What consumers of the in-session buffer (`getRecentReceipts`) and `onToolInvocation` now see:** a receipt for every terminal tool call, including refused and failed ones, each with its real `status` — so a receipt arriving no longer means an act happened (check `status === "completed"`). Counts of receipts grow by the refused and failed calls, and buffer slots (50) are shared with them. With a durable sink configured, both are fed only after the durable append succeeded. Audited consumers: web `wireReceiptSignPulse` (fixed: pulses only on `completed`); web `/receipts` (already renders ✓ / ✗ / ⊘ by status); `cmdTrust` and the panels trust controller (count and list _signed receipts_, a neutral claim — unchanged); desktop and web receipt buses (fan-out only).
- `runRepoTask`: the ephemeral, no-interior run of a repo task — authority checked before the first model call and on every tool call by `@motebit/verifier`'s shared repo-change rules (the same implementation `verifyRepoChange` runs; failures carry its repair codes), a frozen two-tool registry (`repo_read_blob`, and `repo_write_path`, which stages content as blobs in git's object store through the `RepoChangeStager` port and never writes the worktree) built only from the verified scope (the write handler also refuses a directory/file conflict by the verifier's `repoPathPrefixConflict`; `RepoTaskAuthorityBundle.spent` is judged by `checkRepoChangeSpent`, and `RepoTaskAuthorityBundle.agents` — the repository's agent pins — by `checkRepoChangeParties`) and asserted by handler identity on every model call (authority is checked once more immediately before every stage, so a tick that expires during the write's own lookups stages nothing; a call that names no tool is never dispatched and is signed `denied` under the fixed name `repo_task_unnamed_tool`, so the bundle stays verifiable), a system prompt that is a pure function of scope, runtime version and model (its digest recorded), and receipts signed by the agent into the durable sink.
- ai-core: the system prompt no longer carries any line of a multi-line user message (the `[User]` line is omitted at the source instead of filtered line by line). `wrapExternalData` and `ToolCallOutcome` are exported.
