A device's own events reach the relay: the sync push cursor moves only as far as the relay acknowledged (#914; `spec/memory-delta-v1.md` §3.6, 1.6). This is the ignored-package half; the published `motebit` half is in the sibling changeset.

- `@motebit/sync-engine`:
  - `SyncEngine.sync()` used to push one batch after its push cursor and then set the cursor to the local max clock read after the pull. An event appended while the sync awaited its pull was never pushed, and a backlog larger than `batch_size` — every restart, since the cursor lived in memory — pushed its first batch and skipped the rest, silently.
  - The push cursor (`getCursor().last_version_clock`) now moves only after an acknowledgment, and only past a clock whose every local event was acknowledged or pulled from that relay (`ackedPushCursor`, exported). This relies on every local append taking a clock above every stored event (an atomic `appendWithClock`); the Tauri and Expo stores assign clocks non-atomically, so a concurrent append there can land at or below the cursor and is never pushed — a loss main shares, tracked in #964. The local read has no `limit`, because IndexedDB and the in-memory store do not return `limit`-bounded reads in clock order.
  - A sync drains the backlog `batch_size` at a time, up to `MAX_PUSH_BATCHES_PER_SYNC` (50) batches, and continues on the next sync.
  - The push cursor is persisted in the store that already keeps the pull cursor, under a new `push:`-prefixed key (`pushCursorKey`, exported): `push:<seqCursorKey>` for a seq remote, else `push:#<motebit_id>`. There is no schema change and no key rename. The first sync after upgrading has no push cursor yet, so it re-pushes the local log once, bounded per sync; the relay stores each `event_id` once. That re-push also delivers events that earlier versions skipped.
  - Events the engine pulled from a relay are not pushed back to it.
  - A `sync()` called while one is running joins it.
  - The pull side is unchanged: the fallback `after_clock` is still the local max after the last sync.
  - `WebSocketEventStoreAdapter.append` now resolves when the relay's `ack` for the frame carrying the event arrives. It used to resolve on send, or on queue while offline. Each push frame carries a `push_id`; one frame is on the wire at a time until the relay is seen echoing `push_id` in its acks, then up to 16, each ack credited to the frame it names (an ack that names none is credited to the oldest, which is why only one may be in flight then). A `push refused` error rejects the frames on that socket, and so does a socket that closes before the ack. `pushAckTimeoutMs` (new, default 15 000 ms, counted from the frame's send) is a deadline for ADAPTATION only (round 7): a frame that misses it stays in flight on its open socket and still resolves when its ack arrives; the next frame is made smaller. The socket is dropped only when it is dead — nothing inbound (no ack, no event, no reply) for 64 deadlines since the frame was sent — and then the frame's appends reject. An append of an event whose frame is still in flight joins that frame's ack; it is never sent twice. `disconnect()` (a token refresh, mobile's rebuild) no longer abandons frames on the wire: the retired socket drains — it hears only the answers to its frames and closes when the last is answered, when it closes itself, or when it is dead. Once acks of two frame sizes have arrived, frame size follows the link's measured time per event (an upper estimate from ack times: time over the fastest ack, per extra event) so a frame's transmission fits 4 ack deadlines; before that a miss halves the next frames. A relay slow to ack therefore no longer shrinks frames to one event. A socket's catch-up after a connect runs one at a time per local store and relay stream while the running one is receiving bytes (a second would fetch the same pages over the same link at once); a catch-up queued behind it whose adapter was disconnected meanwhile is skipped, and one that finds the running catch-up only waiting on a slow relay starts at once. An event queued while offline stays queued, once per `event_id`, and goes out on the next connection or through `takePendingEvents`; its append rejects at the deadline. `disconnect()` and `takePendingEvents()` reject the appends they strand. The returned promise is marked handled, so a caller that does not await it raises no unhandled rejection.
  - `HttpEventStoreAdapter`: a request has two deadlines: its credential and first byte within `requestTimeoutMs` (new, default 20 000 ms), and no gap in its body longer than `bodyIdleTimeoutMs` (new, default `requestTimeoutMs`), reset on every chunk. The total body time is not bounded. Round 7: a missed deadline never ends an attempt. A push that misses it hands its slot on, so the next push overlaps it (at most 8 overlapping). Otherwise a miss adapts only on evidence: while the link is carrying other bytes of this relay stream, a silent attempt is queued behind them and nothing happens; else a small probe (the clock) asks whether the relay is answering right now, and only if it is — while this request is not — a second attempt starts beside the first (at most 8; the first to complete wins, the rest are ended). A relay slow to answer everything is simply waited on. Pull pages are sized from answered pages: once pages of two sizes have been answered, the per-event estimate (the time over the fastest page, per extra event — an upper estimate) sizes the next pages to arrive within 16 deadlines. Before that, a page doubles after a full page or one with no miss, and halves (down to ONE event) on a miss the probe shows is the page's own — or on any miss while the link has never answered, or shows no progress before a whole body (React Native). An attempt is given up only after 64 deadlines of SILENCE — no byte for it and none on its link — never for its total time, so a slow transfer that keeps arriving always completes. The deadline stretches of round 4–6 are gone: nothing is cut off, so nothing needs stretching. The probe's answer is not progress for the stall watchdog (it shows the relay is up, not that the cycle's work moved). An abort is classified by a flag the adapter sets before it calls `abort()` (owner / silence cap / superseded), never by `signal.reason`, which React Native's `abort-controller@3.0.0` does not carry. Pushes start in call order, one at a time while the relay answers in time; a failed push fails the pushes still waiting for a slot at once. `onActivity(listener)` (new; forwarded by `EncryptedEventStoreAdapter`) reports each attempt, retry, re-auth, headers and body chunk. A response with no body stream (React Native's fetch is whatwg-fetch, which buffers the body and exposes no `body`) is read whole as text.
  - `SyncEngine` abandons a cycle that makes no progress for `stall_timeout_ms` (new, default 60 000 ms) and whose transport reports no live work (`hasLiveWork()`, new on the HTTP and socket adapters and forwarded by `EncryptedEventStoreAdapter` and `liveAdapter`: an attempt not silent past its cap, or a frame in flight on the current socket) — a request slower than its deadline is live, never abandoned: the status turns `error`, the cycle's caller and every joined caller get an empty result, and the next `sync()` starts afresh; the abandoned cycle's late status writes are ignored, and it can only ever write an acknowledged cursor. Progress is every sign of life: each push settling, each pull page (`pullBySeq` gains `onPage`), each HTTP attempt and body chunk — a slow but working cycle is never abandoned. Pulled events are noted as held by the relay as each page is applied, so even a concurrent cycle never pushes them back. A status listener that throws is reported (`console.warn`) and passed over; it never breaks a cycle, the watchdog, or the next sync.
  - `EncryptedEventStoreAdapter.append` hands pushes to its inner adapter in call order, although the encryptions run concurrently, so the relay receives a device's events in clock order — which a client still pulling by clock relies on.
  - The socket coalesces a batch into ONE frame: an append does not send at once; the frame goes when no further append has arrived for 15 ms, 100 ms after the first, or when 500 events are queued. An event's ack deadline starts when its FRAME is sent (while not connected, from the append). Frames carry up to 500 events (the relay sets no per-frame cap; its socket server keeps the `ws` default 100 MiB payload limit). Push frames are paced at 50 per 10 s — half the relay's 100 messages per 10 s — and the budget is shared per (socket URL, device id) across every adapter in the process, because the relay's limiter key is `ws:<motebit_id>:<device_id>` (a token refresh's second adapter draws on the same budget; two processes of one device each pace themselves). The relay's `{type:"error", message:"Rate limit exceeded"}` while a push frame is in flight fails that frame at once, spends the window, and replaces the socket so a late ack is never credited to the next frame. A 5000-event first-sync backlog completes in one sync as 50 frames, with no rate-limit refusal. A frame not acked in time makes the NEXT frame half its size, down to one event (the late frame itself is never re-sent); the frame size grows back by doubling after full frames are acked, up to the size known to fit, and probes past it after 8 full frames there.
  - During an outage a socket sync now ends `error` after the 15 s ack deadline, where it used to report idle. The status is honest; the surfaces' "Sync cycle failed" copy for it is a follow-up.
- Also in `@motebit/sync-engine`: `liveAdapter(() => current)` (new) is the surfaces' socket indirection — it forwards to whichever adapter is current and forwards `onActivity`, following a token-refresh swap. Desktop, web and spatial now use it; their hand-built wrappers dropped the socket's wire activity, so the stall watchdog abandoned a slow but live cycle.
- Also in `@motebit/sync-engine` (#914 round 7): `SyncEngine.sync()` hands every batch of the sync to the adapter at once, so a batch never waits for the previous batch's answer. It waits for the answers up to `push_patience_ms` (new, default `sync_interval_ms`) — past that, only when the transport reports live work — and then ends: an answer still coming is not a failure. The pull is waited on the same way: a pull still arriving continues, its pages land as they come, the next sync joins it rather than starting another, and reports it. Pushes stay in flight across syncs; a later sync joins one rather than sending it again, and each acknowledgment moves the persisted push cursor when it arrives, between syncs too (serialized, in clock order, only past whole acknowledged clock groups, persisted before anything is forgotten). A transport without `hasLiveWork` has its unanswered pushes sent again by the next sync. An event the relay's own stream has shown this device (any pull page, by any adapter over the same local store: the sync, a socket catch-up) counts as acknowledged, so a late ack that never arrives costs no re-push of an event the relay is known to hold.
- Also in `@motebit/sync-engine` (#914 round 6): what a link has taught the transport — the push frame size and ceiling, the pull page size — is kept per relay stream for the life of the process (keyed by socket URL + device id, or by relay origin + identity), never per adapter instance, so mobile, which rebuilds its socket and catch-up adapters every sync cycle, keeps learning a slow link instead of starting over. When the stall watchdog abandons a cycle, the cycle's requests on the wire are aborted (`abortInFlight`, forwarded by `EncryptedEventStoreAdapter` and `liveAdapter`), so they never hold the push slot against the next cycle.
- Excluded, accepted in review: a self-hosted relay older than #868 serves only the clock pull and ignores `limit`, so a timed-out pull cannot shrink its page there. A relay older than this change does not echo `push_id`, so against it the socket keeps one frame in flight (as before round 7).
- Known, not changed: the engine's record of events pulled from the relay (`knownRemote`) is cleared when `connectRemote` switches relays, but a cycle already running against the old relay can still record events it pulls after the switch. Those are then treated as held by the NEW relay and not pushed to it. It takes a relay switch while a sync runs. Not a regression — main never pushed events it had pulled. Out of scope here.
- `@motebit/relay`: one additive wire change — the socket `ack` echoes the push frame's `push_id` when the frame names one (a string of at most 64 characters); a frame without one gets the unchanged ack, so older clients see nothing new, and a newer client against an older relay keeps one frame in flight. Tests: `sync-push-interleaving-914.test.ts` enumerates every ordering of append / sync / append-during-pull / lost push / restart / crash-before-cursor-write (and token refresh on the socket) across the HTTP raw, HTTP E2E and socket E2E doors, against the served relay. It also re-pushes under a signed device token (#846) with E2E envelopes (#928) and checks each event is stored once, first write kept, with no refusal recorded. A 5000-event backlog over the socket completes in one sync with no rate-limit refusal. The `push_id` echo is tested on a raw socket.
- `@motebit/sync-engine` tests (#914 round 7): a differential liveness harness (`liveness-harness-914.ts`, `sim-net.ts`, eight shard files) runs the real engine and adapters over a simulated link — uplink time per event × relay answer latency × lifecycle (a persistent socket with token refresh, a socket and catch-up rebuilt every 30 s as on mobile, HTTP every 30 s) × AbortController flavour (Node, React Native) × backlog — against a model of main's transport (fire-and-forget socket, unbounded HTTP), with fake timers. Per cell it asserts the branch delivers at least as many events as main, everything whenever main does, that the push cursor never passes an unacknowledged event, that no socket frame re-sends an event still in flight in another frame, and that an acknowledgment always moves the cursor (a quiet L + 15 min after the horizon, the cursor has passed every event the relay held at the horizon). `pnpm test` runs the CORE cells (each red at some point of the design); `ZZ914_FULL=1` runs all 730.
- `@motebit/desktop`, `@motebit/web`, `@motebit/spatial`: tests only. The fake relay in `sync-refresh-socket.test.ts` now acks push frames as the real relay does, and the tests wait for the ack.
