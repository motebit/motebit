**Breaking wire change for relay-to-relay federation — deploy both relays of every federated pair together** (no dual-stack window; production has 0 active peers). Every signed federation message names the relay it is for, and a relay acts only on messages addressed to its own key (relay-federation@1.5 §3.5, Inc 6 of docs/design/identity-authority-writers.md).

- `POST /federation/v1/discover`, `/task/forward`, `/task/result` and `/settlement/forward` take the request's own fields plus `message`, a v2 signed message of kind `discover` / `task-forward` / `task-result` / `settlement-forward` (sibling changeset `crypto-federation-work-kinds.md`) addressed to THIS relay by id and by key, committing to every other field by digest. Before, these bodies were signed over canonical JSON naming no recipient: a body one relay signed for a second verified at ANY relay that peers the signer within ±5 minutes (a captured forward was queued at a third relay; a captured settlement forward wrote a settlement row there).
- One producer, `signFederationRequest` (`signDiscoverBody` stamps `sender_relay` and delegates), used by every sender: the three discover senders (task routing, the marketplace fan-out, the re-forward — now one message per peer), both task-forward sites, result delivery and its retries, the settlement forward and its retries (each attempt a fresh message). One verifier, `verifyFederationRequest`: recipient key, kind, recipient id — before any lookup; the body's `origin_relay` / `sender_relay` must be the envelope's sender; peer state; freshness; body digest; signature; single-use nonce (`relay_federation_nonces`; a replay is 409). `verifyPeerSignature` and `verifyDiscoverSender` are removed.
- A request without `message` (the 1.0–1.4 in-body `signature` + `timestamp`) is refused 400 by name. An unsigned discover is still accepted only under the operator's explicit `requireDiscoverSignature: false`.
- The per-peer rate limit on these four endpoints counts a request only once its signature verified, keyed by the verified sender (was the self-asserted `origin_relay`, before verification).
- A behavioural gate (`federation-route-registry.test.ts`) enumerates every route the booted relay registers under `/federation` (any method, any sub-router) against an explicit registry — an undeclared route is red — and drives every signed route with a correctly signed v2 message addressed to another relay's key and with the v1 body (no `message`): each must be refused 400 with no table changed and no outbound request. A static scan (`federation-signed-kinds.test.ts` over `federation-route-scan.ts`) keeps the call-site shape: each literal-path `/federation/v1/*` POST handler contains a call to the one verifier naming exactly one §3.5 kind or carries a stated exemption (propose, horizon witness, horizon dispute, and the named vote-request residual), every registry kind has a verifier site comparing the recipient to the relay's own key, and every outbound work request is signed by the one producer.
