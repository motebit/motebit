Identity enforcement gaps closed at the relay.

**Federation peering handshake v2 (`motebit/relay-federation@1.5`, spec §3.1).** v1's confirm signed the bare `relay_id:nonce:suite` — the same bytes every relay's public `/peer/propose` signed for any caller (a "self-propose" naming its own id), so every relay was a public signing oracle for its own confirm: a stranger could re-propose a suspended or removed peer's id at a target with the victim's public key and its own endpoint, carry the target's nonce to the victim's own propose, and replay the victim's signature to the target's confirm — row active, endpoint the attacker's, trust kept. v2 signs role-bound messages naming both parties: `motebit-federation-propose:v2:{responder}:{proposer}:{suite}:{proposer_nonce}` (a propose response) and `motebit-federation-confirm:v2:{prover}:{verifier}:{nonce}:{suite}:{endpoint_url}` (a confirm, carrying the endpoint the verifier stores). A relay mints its confirm only through the master-token `POST /api/v1/admin/federation/peer-confirm-signature`; a self-propose is refused. A propose writes NOTHING — its nonce is an HMAC this relay minted over the proposer's id and key, redeemed once by a confirm that verified (`relay_peer_handshake_nonces`) — so an unauthenticated propose can neither evict another party's proposal nor pre-plant a `pending` row that blocks a peer's own handshake. A known peer id stays bound to the key it peered under in every state (409 on another key); an endpoint change for an established peer is a confirm under its stored key whose signed `endpoint_url` is the new one. A request without `handshake_version: "v2"` is refused 400 by name (v1 fails closed, never as a bad signature). No third-party federation peers exist yet; the CLI (`motebit federation peer` / `mesh`) and both scripts move with it.

**Federation rate limits count a request against a peer only after its signature verified.** Every `/federation/v1/*` request is first counted per source (`federation.sourceRateLimitPerMinute`, default 300); the per-peer 30/min limit now runs after verification on heartbeat, confirm, remove, witness, vote-request, discover (signed sender only), task/forward, task/result and settlement/forward — keyed on the CLAIMED id, 30 junk heartbeats naming a peer made its real heartbeat 429 (→ missed heartbeats → suspension).

`/credentials/submit` admits a `hardware_attestation` claim only when it equals a claim the subject attached to its own device record (a request signed under that device's key), and a `secure_enclave` receipt must verify against that device's key.
