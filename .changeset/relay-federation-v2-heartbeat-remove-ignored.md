relay-federation@1.5 (`spec/relay-federation-v1.md`; docs/design/identity-authority-writers.md Inc 1b, decision D4). **Deploy both relays of a federated pair together** — there is no dual-stack window.

- `POST /federation/v1/peer/heartbeat` and `POST /federation/v1/peer/remove` take a v2 signed message (§3.5, `signFederationMessage` / `verifyFederationMessage` in `@motebit/crypto` — sibling changeset `crypto-federation-message-v2.md`): kind, sender, the ONE recipient, timestamp and single-use nonce under the signature, body bound by digest. The nonce is recorded in `relay_federation_nonces` in the same transaction as the write it authorizes. The v1 forms (`{relay_id}|{timestamp}|{suite}`; a signature over the bare `relay_id`) are refused with 400 by name and change nothing — a replayed v1 heartbeat had moved a suspended peer to active and spent the peer's rate limit. The per-peer limit now counts only requests whose v2 signature verified.
- The heartbeat answer is a signed `heartbeat-ack` committing to the request's nonce, and the sender counts a heartbeat delivered only when the ack verifies under the peer's stored key (the v1 response was never verified).
- Self-propose (`peer/propose` naming the receiving relay's own id) is refused with 400: its answer was this relay's signature over the step-3 confirm bytes for a caller-chosen nonce. The confirm is minted by the operator on the new master-token `POST /api/v1/admin/federation/peer-confirm-signature`.
- `GET /api/v1/admin/federation/peer-removal-signature` now requires `?recipient=<relay_motebit_id>` and returns `{ relay_id, message }` (a v2 `peer-remove` for that one peer) instead of a bare signature.
- The peering handshake moves to the v2 envelope (cold review F1): `POST /federation/v1/peer/confirm` takes `{ message, nonce }`, `message` a v2 `peer-confirm` from the proposer to THIS relay over `{ nonce, endpoint_url }`, verified with the body rebuilt from the pending handshake (its nonce, the endpoint its propose named) and its envelope nonce recorded with the write; the 1.0–1.4 `{ relay_id, challenge_response }` is refused with 400 by name. A confirm minted for another relay or another endpoint is refused — before, a counterparty that answered a propose with another relay's nonce could carry the proposer's confirm there and activate it at its own endpoint. `peer/propose`'s `challenge` is a v2 `peer-challenge` (an object, was a hex string). `POST /api/v1/admin/federation/peer-confirm-signature` now requires `recipient` and returns `{ relay_id, nonce, endpoint_url, message }`, signing only this relay's configured federation endpoint.
- `peer/heartbeat` and `peer/remove` check kind and recipient before looking up the sender, and answer an unknown sender 403 (was 404), as §3.5 states. The federation circuit breaker suspends a peer through the guarded peer-row writer (compare-and-set, never toward `active`).
- The handshake binds keys, not only ids (cold review R1, R2; relay ids are not self-certifying). The `peer-confirm` body is `{ nonce, endpoint_url, recipient_public_key }`, rebuilt by the recipient from its OWN key, so a confirm minted for an identity that claimed this relay's id under another key is refused; the `peer-challenge` body adds `proposer_public_key`; `POST /api/v1/admin/federation/peer-confirm-signature` requires `recipient_public_key` and echoes it. `peer/propose` writes no `relay_peers` row: it records a pending handshake (key, endpoint, nonce) beside the table, and a row is born only from a confirm verified under that key. A never-confirmed row an earlier build wrote confers no authority — it pins no key, is 403 to `peer/remove`, and is replaced by the next verified confirm — so a stranger's propose-then-remove under its own key no longer locks the real relay out, and a re-propose for a never-confirmed id is no longer 409.
- Every v2 message names its recipient by KEY (cold review round 3, F1–F4; supersedes the per-kind key fields above). The §3.5 envelope carries `recipient_public_key`, set from the key this relay verified the recipient under and checked against this relay's own key before any lookup (400 `wrong_recipient_key`). Bodies: `peer-confirm` `{ nonce, endpoint_url }`, `peer-challenge` `{ request_nonce, nonce, proposer_endpoint_url }`. Heartbeats and acks address the key on the peer's record, so a heartbeat to an id a stranger holds here under its own key verifies only at that stranger. `GET /api/v1/admin/federation/peer-removal-signature` takes `?endpoint_url=` (or `?recipient=`) and mints only for the ONE confirmed peer it resolves (404 none, 409 several), returning `{ relay_id, recipient, recipient_public_key, endpoint_url, message }`. No pending handshake is stored: the propose's nonce is the handshake (an HMAC over the relay_id, key and endpoint it named, valid 5–10 minutes), so `POST /federation/v1/peer/confirm` takes `{ message, nonce, public_key, endpoint_url }` (the key and endpoint the propose named) and the confirm mint also returns `public_key`; a propose spends no per-peer slot for any relay_id, and a confirm only once it verifies — no number of proposes evicts or locks out another proposer's handshake. The removed-peer cooldown also holds at confirm.
