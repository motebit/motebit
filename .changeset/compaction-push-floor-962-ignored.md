Compaction never deletes an event the relay has not acknowledged (#962). This is the ignored-package half; the published `motebit` half is in the sibling changeset.

- `@motebit/sync-engine`: `pushCompactionFloor(localStore, requested, { syncConfigured? })` returns the smallest of `requested` and every relay stream's acked push cursor. It reads the streams a `SyncEngine` connected over that store in this process, plus every `push:` cursor the store persists. Cursors are grouped by relay stream (new `relayStreamOfPushKey`): mobile's /sync cursor (`push:e2e:raw:`) and its live cursor (`push:relay:`), or a raw CLI cursor beside an E2E one, are one relay, and the highest of them counts, so a stale cursor no longer pins compaction. Distinct relays still take the lowest. With no stream it returns 0 when `syncConfigured`, else `requested`; an unreadable cursor gives 0 (fail closed). `connectRemote` now records its stream and persists a push cursor of 0 when none exists. `SyncSeqCursorStore` gains the optional `listSyncSeqCursorKeys(prefix)`.
- `@motebit/runtime`: `compact()` and the `stop()` compaction share `compactUpTo`, the one place that decides what is deleted, and it applies the floor. New `RuntimeConfig.syncConfigured` (a boolean or a provider, read at compaction time; a provider that throws counts as configured): a host with a relay configured compacts nothing until the relay acknowledges a push, even when no cursor was ever persisted (an enrollment write lost, a process that never connected).
- `@motebit/desktop`, `@motebit/mobile`, `@motebit/web`, `@motebit/spatial`: each passes `syncConfigured` from its relay URL setting; the desktop and mobile stores' cursor listing is tested over real SQLite.
- `@motebit/persistence`, `@motebit/browser-persistence`, `@motebit/desktop` (Tauri), `@motebit/mobile` (Expo): each event store implements `listSyncSeqCursorKeys`.
- Round 3: `SyncEngine.getLastError()` returns why the last cycle failed (a refused push, a stall), or null once one succeeds, because `sync()` never rejects and a refusing relay was silent. `MotebitRuntime.isSyncConfigured()` exposes the host's `syncConfigured` answer as compaction reads it, so each surface's wiring is tested at its construction seam. Desktop's `syncConfigured` is now read at compaction time and includes a relay started later in the session. Web saves the relay URL whenever sync starts, pairing included, and its `syncConfigured` treats unreadable storage as configured (new `isSyncUrlConfigured`).
- Round 4: `pushCompactionFloor` takes `motebitId` (the runtime passes its own), and only that identity's relay streams bound the floor. A restored or re-created identity on the same store used to be floored by the OTHER identity's acknowledged cursor, and compaction deleted events of its own that no relay had received. A `syncConfigured` provider that never settles now counts as configured after 3 s, so compaction deletes nothing instead of hanging. Each app now keeps its device registered until the relay accepts it: a relay that was unreachable, or had never seen the device, used to refuse every push for the rest of the session. Desktop registers with the signed `registerDeviceWithRelay`; its legacy `/identity` + `/device/register` calls never introduced the key. Desktop starts sync even when registration fails, and retries registration in the background with a backoff from 1 s to 60 s. Mobile registers before its first push. It no longer reports "idle" after a refused cycle, and a refused `/sync` no longer says "Synced". Web and spatial retry a refused registration with the same backoff. Spatial registers with the signed `registerDeviceWithRelay`. Without a token, spatial now reports an error instead of "connecting" forever, and its HUD shows "online" only once the connection succeeds. Every entry point's push is held by a behavioural matrix against a real served relay (`every-configured-surface-pushes-962.test.ts` in each app).
- Round 5: sync intent is a durable property of the DATABASE for an identity, never of the process that compacts. New in `@motebit/sync-engine`: `recordSyncIntent(localStore, motebitId)` writes a per-identity marker (`syncIntentKey`, `intent:sync#<id>`) next to the push cursors in the same cursor store. `readSyncIntent` returns `recorded`, `cleared` or `never`, and throws when the marker cannot be read. `clearSyncIntent` clears the marker, and only an explicit operator act may call it; an absent configuration never clears it. `pushCompactionFloor` reads the marker: with no relay stream, it returns 0 when this process is configured OR the database records the identity's intent, and a marker that cannot be read gives 0 (fail closed). `@motebit/runtime` records the marker when its `syncConfigured` is `true` (inside the constructor on a synchronous store, before any append) or when a provider actually answers `true`. It records the marker again before each compaction. A provider that throws or never settles still holds this process's compaction but records nothing durable. `init()` awaits the write, and `whenSyncIntentRecorded()` exposes it. Every surface that passes `syncConfigured` (desktop, mobile, web, spatial, the CLI) writes the marker through the runtime, and its stores need no schema change. Harness: the CLI matrix gains a cross-process dimension (two entry points on one `motebit.db`, both orders, the relay reachable later) and the round-4 reviewer's probe P6. The runtime file holds the same law over in-memory, SQLite and IndexedDB stores.
- Round 6: a pinned floor is never silent or doorless. New in `@motebit/sync-engine`: `syncFloorReport(localStore, motebitId)` returns the floor, what compaction asks for, the intent, and per relay stream its acked cursor, last acknowledgment time, retirement, whether it holds the floor, and how many events retiring it would free. `pinnedFloor(report, now?)` names the stream to report: it holds the floor, retiring it frees events, and it has acknowledged nothing or not advanced in more than 7 days (`PINNED_FLOOR_STALE_MS`). `retireRelayStream(localStore, motebitId, stream)` removes a stream from the floor as an explicit operator act, recorded under `retiredStreamKey`. A stream is never retired automatically, and `connectRemote` to that relay restores it. A retirement marker that cannot be read fails closed. `relayStreamOfUrl` / `relayUrlOfStream` map relay URLs to streams. Each acknowledgment records its time under `pushAckedAtKey`. `sanitizeRelayText` (with `RELAY_TEXT_MAX`) is now sync-engine's: it strips ESC sequences, C0/C1, DEL, bidi controls (U+202A to U+202E, U+2066 to U+2069), zero-width characters (U+200B to U+200F), the BOM and U+2028/U+2029, and it truncates by grapheme (`Intl.Segmenter`). Every adapter error built from relay text (HTTP status text, the socket's refusal message, pairing errors) carries the text sanitized, and `getLastError()` exposes only a sanitized message (the original is its `cause`). Known scope: the marker and the streams are per database (`MOTEBIT_DB_PATH` / `--db-path` opens another), and a desktop elected as a frontend constructs no runtime, so it records no marker. The doors are the CLI's, but they are not CLI-only by nature: web (and any surface with a relay-URL setting) can pin the floor too, since web's relay-URL panel connects whatever URL is typed and a typo-then-fix leaves a stream at 0 that holds compaction. That surface's notice and retire door are tracked as a follow-up; until then its storage grows, and no data is lost.
- Round 7: a floor pinned by TIED streams is reported. `RelayStreamReport` gains `tiedWith` (the other active streams holding the floor at the same clock) and `heldBackTied` (what retiring this stream and all of `tiedWith` frees: the gap to the next distinct stream). `heldBack` stays the single-stream count, so a stream tied with another reports 0 there. `pinnedFloor` now returns every stream in the tied set (`streams`) and the tied count (`heldBack`), and reports whenever that count is above 0 and every tied stream has acknowledged nothing or is stale; a tie that includes a stream acknowledging recently is not reported (new `PinnedFloor` type). The socket adapter hands every catch-up failure out sanitized (`onCatchUpError` and the default `console.warn` alike; the original stays the `cause`): a relay answering the catch-up pull 200 with a hostile non-JSON body made `res.json()` throw a SyntaxError quoting the body, and OSC/CSI/U+202E reached the console. The skipped-event default report is sanitized too. `sanitizeRelayText` also strips U+061C, U+2060 to U+2064 and the tag characters U+E0000 to U+E007F.

Stated cost: compaction waits for a relay acknowledgment. A relay that is configured but never reached (offline; spatial's default relay on an install that never connects) or that keeps refusing the push (a revoked device, a bad token) holds compaction, and the local event log grows until a push is acknowledged. Never deleting an unacknowledged event is the invariant; the growth is its price.
