A goal whose last run left a paid outcome unknown no longer re-fires into a second payment (#890). A plan step whose delegation ends undetermined (the relay never confirmed the submission) or whose process died mid-submit now stays held: its plan is resumed, never re-planned, and the step settles only from the relay's signed receipt for its task — completed or failed — without a second submission. The goal scheduler reports such a run as awaiting its result (`partial`, pointing at `/result`), not as a failure, so it no longer burns the retry budget or auto-pauses. A goal whose run hired through `delegate_to_agent` and left a payment owed in the paid-intent ledger is held until that result is retrieved or dismissed with `/result`. `motebit delegate --plan` prints "Awaiting result" for such a plan instead of nothing.

A plan is driven by at most one driver at a time: a goal scheduler's resume and a reconnect's recovery no longer both settle a held step and both submit the next one (the second yields `plan_busy`), and a plan step's relay Idempotency-Key is now derived from the plan, step and attempt, so overlapping submissions admit one task. Every goal run records its start before it can pay, so a run that pays and then dies still holds its goal.

A plan step held because its submission never left the device (offline at submit) is no longer wedged: resuming re-posts it (only through an adapter whose key is derived, never sovereign pay-forward) under the same derived Idempotency-Key while that key is inside the relay's idempotency window, and a 409 that names the task (#888) now hands over that task. Desktop "Run now" honours the owed-payment hold, and a run that paid after overrunning its wall clock still holds its goal.

A plan step's delegation now rotates to a new Idempotency-Key only on positive evidence that nothing was paid for the old one (a signed failed receipt, or a refusal before admission); a task the relay no longer knows (404) is unknown, never failed. The step remembers its rotation and clears its old task id when it rotates, so it settles only from its current task; and the relay answers an evicted task from its receipt archive for the agent whose key admitted it, within the idempotency window. A 5xx on submission is no longer read as a refusal.

Round 5: any relay response that names a task — whatever its status — is adoption of that task, never a refusal; a failed receipt is evidence only when bound to the current task and signed by the routed worker; the re-post window runs from the current key's first submission; and the relay archive answers only the receipt of the worker a task settled to (or its sole receipt), and the MCP forward keeps only the presented worker's receipt.

Round 6: the relay records who it handed each task to (and through which peer), and accepts a receipt for a task only from that executor, through that peer — at the result route, the MCP forward and the federation result. A federation peer can no longer answer a locally routed task with a failure signed by a key it invented, and a planner that adopted a task no longer pays again on such a forgery. The relay's archive answers an evicted task with its routed executor's own receipt (a settlement row naming the path agent no longer hides it), the origin archives a verified federated receipt, and a receipt nested in another task's tree can no longer displace a task's own receipt. Routes are kept 7 days (beyond the 24-hour idempotency window) and declared in the relay's transparency declaration.

Stated cost: a nested receipt the relay archived before this change still sits at its task's own key and blocks that task's top-level receipt from being archived. It is never served as the task's answer — the archive reads top-level receipts only — so such a task reads as unknown (the delegator holds rather than pays again), and its trust credit is skipped; only tasks squatted before the upgrade are affected.
