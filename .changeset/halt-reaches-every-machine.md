A halt reaches every machine, not the first that answers — issue #681.

The halt store is local and nothing replicates it, and the relay delivered first-wins. So a sovereign with a daemon on a laptop and a worker on a VPS had one machine stopped and one still working, under the stopped one's acknowledgement — which reads as "stopped" for a motebit that is still running. The act is idempotent and machine-local, so the delivery that matches what the person asked for is to all of them.

**Per machine, not per connection.** `motebit run` and `motebit serve` on one host are two peers sharing a device id, a database and one replay guard, and the envelope carries a single signature — so a second frame to the same host is refused as a replay by its own motebit. Within a machine, every connection is a candidate for that machine's one delivery: which of its sockets is alive is a different question from how many deliveries it should get.

**A broadcast is not a race.** `cmdResume` answers "Nothing is halted." synchronously when nothing is active, while the machine that actually holds the halt awaits its store — so the machine with the least to do reliably won, and a successful resume rendered as a no-op. Resolving on the first reply also returned before the other machines had acted at all. Every answer is gathered now, counted by machine rather than by reply, and a machine that does not answer is named — _silence is not a stop_.

**There is no grace window, because the relay cannot compute one.** Two attempts proved it: at three seconds the window armed on the machine with nothing to stop and reported the machine actually aborting work as silent; at twelve it was still under-measured, because `honorHalts()` awaits a nested loop over pending halts × registered stoppers, each under its own ten-second ceiling. Nothing bound the relay's constant to the runtime's, so any change to either silently re-opened the gap. The bound depends on interior work the relay has no view of by design, so it stops guessing: it waits for the machines it reached and composes at the request's own deadline.

**The relay does not synthesize a verdict about the interior.** An earlier revision AND-ed `data.acknowledged` across machines. That was a category error, and two ordinary paths showed it — `cmdResume` never emits `acknowledged` at all, so every successful multi-machine resume published `false`; and a goal-scoped halt is honourable only by the machine that owns the goal, so the conjunction was false about a goal that had been stopped. A composed reply carries transport facts (`sent_to`, `reached`, `answered`, `unreached`) and each machine's own `data` verbatim beside the device that sent it, and no `acknowledged` key: absent is the fail-closed reading, and "did my motebit stop" is answered by the per-machine replies or by `halt-status`, which is the command whose job that is. A single-machine motebit still receives the runtime's own reply untouched.

**Nothing heard is a timeout, and stays one.** Composing every expired request resolved a single-machine halt — every deployment that exists today — with an empty answer list: `undefined`, serialized as HTTP 200 with an empty body, so the CLI's 504 branch became a JSON parse error and the phone said "The runtime did not recognise halt — update it". The same holds for a broadcast nobody answered: an honest prose report at 200 still tells a script the halt succeeded.

Smaller, from the same rounds: the target list is assigned before the first send and the quorum re-checked once unreachable machines are known, so the ordering is an invariant rather than a property of today's transport; the summary counts machines _reached_, because "Sent to 2 runtimes" above a line reading "dev-1: not reached" contradicts the report it introduces; an unreachable machine is named rather than dropped from the accounting; a folded undeclared bucket is reported, since two connections declaring no device id might be two hosts; and halt ids are machine-local, which the composed detail now says, pointing at `resume all`.

**Written against the multi-runtime harness rather than by reading.** The same change was attempted inside the return-view PR and withdrawn after ten review rounds that never converged, because nothing in the repo could express what a runtime does with a forwarded frame. Every claim above is a test that fails when the behaviour regresses — including the ones that only exist because three review rounds found the behaviour wrong.

Found in the harness itself along the way: it had been running against a stale build in which `handleCommandResponse` was not exported, so every reply threw and the loop never closed — and nine tests passed anyway, because most assert on runtime-side state. The wire reports its own faults now and the suite asserts there were none. It also could not sequence two deliveries, so the test for "the second process refuses as a replay" raced envelope verification; `deliver()` is awaitable.

**A partial broadcast is not a success, and no longer answers like one.** A halt that reached two machines and heard from one returned HTTP 200 with honest prose — so `motebit halt --remote && <next step>` proceeded while a machine was possibly still running, and every consumer had to remember to compare `answered` against `sent_to`. That is one more value with two opposite safe defaults, the shape this arc has already paid for twice. A partial now carries a non-2xx and the composed body with it, so a caller that forgets gets an error rather than a false success, and nothing is lost by the status. The CLI's sentence for it stops asserting "the runtime received this command", which on a partial is demonstrably untrue of at least one machine.

Composition is also reached when the only thing to say is that a machine was never reached: keyed on answers alone, a broadcast where one machine was dead and the other wedged rejected as a plain timeout, and the CLI printed "Delivered, no answer yet" about a machine the relay knew it never reached — verbatim the conflation this change exists to remove.

Smaller: the internal `__undeclared__` bucket key no longer reaches a consumer through `answers[].from` either, having already been rendered in `unreached`; and the deadline is overridable through relay config the way `drainGraceMs` already is, because with no grace window the silent-machine paths would otherwise cost thirty seconds apiece on a suite this repo already fights for CI time.

Two things the tests were not doing, found in the same round. The goal-scoped test asserted only that both device ids appeared and that a field absent from _every_ composed reply was absent — it passed with goal scoping removed entirely; it now asserts the owner holds a goal-scoped halt and the other machine holds none. And the harness's in-memory halt store accepted a halt scoped to a goal it had never heard of, where the real store refuses exactly that, so the test measured the double rather than the system — the same trap the socket model fell into before it learned about `readyState`.

**Named, not fixed here:** `halt-status` is still delivered first-wins, so on a two-machine motebit it answers from one machine's local store. The client docstring pointed at it as the way to ask "did my motebit stop", which is advice this change cannot yet honour; that pointer is corrected, and composing `halt-status` belongs with the rest of the multi-machine story rather than smuggled into this one.
