Make the proxy → relay usage debit provable. Production evidence (2026-10-02): the operator's provider key spent $410.18 over three months while the relay recorded zero `fee` rows, ever.

- `@motebit/proxy`: new `billing.ts`. Motebit-cloud refuses at admission (503, `proxy.billing_unconfigured`) when `RELAY_PROXY_SECRET` or `RELAY_API_URL` is missing. The `https://relay.motebit.com` default and the silent `if (!secret) return;` are gone. `debitRelay` returns a typed outcome and always emits exactly one `proxy.debit_landed` or `proxy.debit_failed` event (reasons: `not_configured`, `no_billable_amount`, `unauthorized`, `rejected`, `insufficient_balance`, `bad_response`, `relay_error`, `unreachable`). A relay `200 {success:false}` no longer counts as landed. The debit now runs before the client stream closes, because work after the response may not run on the edge runtime. A client disconnect still bills the metered usage (it used to throw in `finally` and skip the debit), and the upstream is cancelled. The request's shape (messages present, non-empty, within the message limit) is validated before the `auto` routing classifier runs, so an invalid request never spends; once the classifier has spent, every later exit bills it exactly once (failure exits through one `settled` wrapper, the streamed turn by folding it into its own debit). The `X-Motebit-Routing-Reason` header is ASCII-only (the router's `→` made every streamed `auto` response throw). Successful streams carry `X-Motebit-Request-Id` (= the fee's `reference_id`). A deployed proxy (`VERCEL_ENV`/`VERCEL`) with no KV refuses (503) instead of running with no spend controls.
- `@motebit/relay`: when a debit exceeds the spendable balance, the relay now debits what is spendable (respecting the escrow hold) and reports the `shortfall`. Before, it recorded nothing, so the balance never drained and every new proxy token carried it again. `amount` must be an integer (400, not a 500), and a non-JSON body gets a 400. Refused debits are logged as `proxy-debit.unauthorized` with `relay_secret_unset` / `header_missing` / `secret_mismatch` (the secret value is never logged). `/proxy-token` refuses to mint (503) while `RELAY_PROXY_SECRET` is unset, because none of that token's debits could land. The debit now requires a non-empty `reference_id` (400 without), so idempotency cannot be bypassed. The `x-relay-secret` check and every master-token comparison (`isMasterToken`, `dualAuth`, the agent-route, pairing, task and WebSocket doors) go through `secretEquals`, a constant-time compare over SHA-256 digests, instead of `===`.
