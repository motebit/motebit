One P2P `payment_proof` admits at most one task, and only its payer may submit it (#918; `spec/delegation-v1.md` §3.3, 1.4). The only reuse guard read `relay_settlements.p2p_tx_hash`, which exists only once a task settled, so the same unsettled proof under a new `Idempotency-Key` admitted and dispatched a second task on one payment. Admission also never asked who paid: a tx hash is public once it lands, so anyone could submit someone else's payment.

Client-visible changes:

- **A proof is admissible only from its payer.** The relay reads the transaction from the chain at submission (`getTransaction`, the p2p verifier's adapter) and requires its payer (the single source of its transfer legs) to be the submitter's identity-derived Solana address: the key the caller's signed token verified under, or, for the operator's master token acting for a body `submitted_by`, a key the relay holds for that identity. A non-payer gets `403 TASK_P2P_PROOF_NOT_PAYER` before any admission write (nothing claimed, key freed). When the chain cannot be read (no `SOLANA_RPC_URL`, an RPC error, or the transaction not visible at confirmed commitment yet) the answer is `503 TASK_P2P_PROOF_UNVERIFIED`, retryable, nothing admitted. **A relay with no `SOLANA_RPC_URL` now refuses every P2P submission.**
- **The same proof under any other key is refused.** `409 TASK_P2P_PROOF_ALREADY_ADMITTED` when the proof's tx hash is bound to an admitted task. The body carries that task's `task_id` only to the operator (master token), or to a caller whose verified token is the claim's submitter when that submitter was itself token-verified at admission. A submitter the operator asserted, or a peer forwarded, is never shown the task. A proof whose task already settled keeps `409 TASK_P2P_PROOF_REPLAYED`.
- **The same proof under the same key is unchanged.** It is the #888 replay of the first answer.
- **A refusal before admission spends nothing.** The binding is written inside the admission transaction, so any refusal before it, or a rollback inside it, leaves the proof unbound, and a corrected retry under any key is admitted once.
- **The federated 502s no longer invite a new key.** After a federated forward is refused or times out, the proof is spent on the admitted task named in the 502 body. The retry is the same-key replay, or polling that task's result. **The cost:** when the executor relay refused the forward, the task never runs and the payment is a paid failure: not reversed, and not reusable for another task (docs/doctrine/paid-failure-recourse.md). A new task needs a new payment.
- **The payer read is bounded.** A payer read slower than 8 seconds answers 503 `TASK_P2P_PROOF_UNVERIFIED` instead of holding the request (the underlying RPC call is not aborted; the adapter takes no signal).
- **The executor relay binds too.** `POST /federation/v1/task/forward` answers `409 {status: "rejected", reason: "p2p_proof_already_admitted"}` when a peer forwards a proof already bound to a different `task_id`. The executor does not check the payer (it holds no key for the origin's submitter; it trusts the origin relay's signed forward).
- **Schema change.** Migration v47 adds `relay_p2p_proof_claims` (tx hash, task id, submitter, whether the submitter was token-verified, time), backfilled from queued tasks and settled proofs. Rows are never deleted. Listed in the transparency declaration and PRIVACY.md.

Runtime (`@motebit/runtime`): the P2P submit loop treats `409 TASK_P2P_PROOF_ALREADY_ADMITTED` as final, like `TASK_P2P_PROOF_REPLAYED` (never retried; ends `payment_admission_unconfirmed` with the payment's lock kept). When that 409 carries a `task_id`, the relay has named this payment's task to its own verified submitter, so the client hands over to it (records it, polls its result) instead of ending unconfirmed. `403 TASK_P2P_PROOF_NOT_PAYER` ends `payment_not_admitted`; `503 TASK_P2P_PROOF_UNVERIFIED` is retried like any 5xx.
