**A task served by several bodies of one identity runs at most once.** The relay hands a task to every serving socket of an identity (the CLI daemon, the desktop app, a browser tab, a phone), and its claim grants exactly one of them — but every body used to send `task_claim` and run the task at once, so each serving body executed it. `motebit run` and `motebit serve` now route task frames through the shared `TaskClaimCoordinator` (`@motebit/runtime`, used by every surface): claim, run only on the relay's grant, drop the task on `task_claim_rejected`, and renew the claim's lease while running. A granted claim means the task may have started, so it is never handed to a second body: a claimer that dies, is partitioned, or runs out of a phone's background budget leaves the task claimed and **undetermined** — the delegator's poll reports `undetermined: { reason: "claimer_lost" }` instead of a pending or failed task — and only that body's own late signed result resolves it. A result from any other device of the identity is refused — under a device token, or under the master token by the receipt's signed `device_id` (verified first) — and the claim is read in the same synchronous turn that writes the answer, so a claim that lands while a non-claimer's result is being ingested still refuses that result (it used to be accepted beside the grant: two executions), while a claim that arrives after an answer is taken is refused.

**Every presenter takes the same grant, and nothing granted is ever lost or re-run.** The relay's own MCP forward now takes the task's grant before its first request (a body reconnecting mid-forward is no longer handed the same task — it ran twice), and the submitter's chosen presentation (`presenter: "submitter"`) is granted at admission (the dispatch token is the grant; reconnect recovery no longer adds a second presenter beside it). A forward that never sent `tools/call` — or whose `tools/call` connection was refused — releases the grant and presents the task to the bodies connected now; one that sent it and got no receipt leaves the task undetermined (`forward_unanswered`). A body whose `task_claim` was lost with its socket re-claims when the task is presented again (it used to sit Pending to its TTL with the body connected). At its TTL an unanswered task is never silently deleted: a never-granted task expires visibly (`expired: { reason: "never_claimed" }` on the poll), and a granted one is undetermined, kept with its allocation hold — never refunded as stale — until the executor's signed result settles it. The planner reads `undetermined` and ends the step undetermined at once, without retrying or demoting the worker's trust, and reads `expired` as a conclusive not-run (a new task for the step). The runtime's delegation poller and `retrieve_task_result` read both too: `undetermined` ends the hire at once with `TASK_UNDETERMINED` — the work may have run, do not hire again — instead of polling to a timeout that invited a second paid hire. Not closed: there is no operator reconciliation for an undetermined task yet (its hold stays locked, flagged `undetermined`); an incidental dispatch token (no `presenter: "submitter"`) is not a grant; bodies that predate the claim protocol run every presentation; federation forwards are not yet grants at the origin; under the master token the signed `device_id` is the identity key's assertion, so devices sharing one key can name each other (`docs/doctrine/task-admission.md` § "Stated limits").
