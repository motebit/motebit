# Money invariants

One page. Every rule the money path must hold, where it is enforced, and what proves it. This page adds no new rule — it consolidates [`spec/dispute-v1.md`](../../spec/dispute-v1.md) §7.3/§7.5, [`settlement-rails.md`](settlement-rails.md), [`task-admission.md`](task-admission.md), [`memory-never-confers-authority.md`](memory-never-confers-authority.md) and the dispute harness laws L1–L17 (header of `services/relay/src/__tests__/dispute-conservation-harness.test.ts`) into one list, so a reviewer (internal, property-test author, or external auditor) checks one surface instead of five.

**Status vocabulary.** _Exhaustive_ = a harness enumerates every interleaving/sequence up to a bound and checks the rule after every step. _Gated_ = a static drift gate fails CI on violation. _Example_ = scenario tests only. _Gap_ = named here, not yet proven; each gap is a property-test target (one PR per rule).

## How this page is used

1. **Property tests** (next): one PR per _Gap_ or _Example_ row, starting with M1 and M4 — fast-check over random operation sequences with injected faults (crash between steps, duplicated delivery, reordered retries, clock jumps), asserting the row after every step. Promotion: _Example_ → _Exhaustive_ when the generator covers the row's whole alphabet.
2. **Reconciliation**: `reconcileLedger` plus a read-only checker for each row, run against a **snapshot** of the production database (never the live one), reporting to a file. Operator-authorized only; reports violations, fixes nothing.
3. **External review**: this table is the scope document — each row names the code to read and the test that claims to prove it.

A new money path is not done until it has a row here. A row's _Status_ changes only with the test or gate that justifies it.
