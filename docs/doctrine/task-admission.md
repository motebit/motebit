# Task admission — priced work enters through the relay's gate

A worker that charges for its work must not do that work for a caller whose payment nobody saw. Transport authentication answers _who is calling_; it says nothing about _whether this task was paid for_. Before this arc the two were conflated: a first-party atom accepted any relay-registered identity's signed bearer and ran `motebit_task` straight into the provider call, while the relay's settlement gate (`TASK_P2P_PROOF_REQUIRED`, balance holds, carve-outs) protected only the relay path. The relay verified the money; the worker never learned that it had. Every priced atom was, to a stranger with a free identity, an unmetered inference endpoint.

## The primitive

The relay mints, per task, a signed **task dispatch token**: an audience-bound token on the canonical mint seam (`mintAudienceToken`, `@motebit/crypto`) with

- `aud = "task:dispatch"` (a `TokenAudience` registry append, never a new token shape),
- `mid` = the worker the task is dispatched to,
- `sub` = the relay task id (the standard JWT subject claim, added to `SignedTokenPayload` as an optional, audience-specific claim),
- `digest` = hex SHA-256 of the admitted prompt — the token admits _this work_, not any work under this task id,
- a short `exp` (`TASK_DISPATCH_TOKEN_TTL_MS`) and a CSPRNG `jti`.

The relay prices the submission before minting. An unlisted capability against a priced worker prices at the worker's ceiling, never at zero, so `required_capabilities: ["bogus"]` cannot clear the P2P gate for free and walk away with an artifact the worker will honor.

It is minted only after submission has cleared the relay's existing gates, so it is the relay's signed statement that _this task, for this worker, passed the settlement checkpoint_. It confers nothing else: no scope (that is the delegation token's job), no money movement (the ledger's), no trust (the trust graph's). Records-vs-acts: it is a record of an admission decision, presented at the act.

## Where it flows — one presenter per admission

- **Relay → worker (MCP forward).** `forwardTaskViaMcp` attaches `dispatch_token` beside `relay_task_id` on every `motebit_task` call, for every dispatch site (pinned paid worker, scored local worker, capability fallback). Each forward mints a token bound to the worker it goes to.
- **Relay → submitter, only when the relay did not dispatch.** If nothing routed the task (no WebSocket, no reachable MCP endpoint, no federation), `POST /agent/:worker/task` returns `dispatch_token` bound to the intended worker (`target_agent`, else the URL agent) and the submitter presents the task directly. If the relay routed it, the response carries no token: the relay is the presenter and the submitter polls for the receipt. Two presentations of one admission would race at the worker, so the relay never hands out two.
- **Submitter → relay, chosen up front (`presenter: "submitter"`, delegation spec §3.1 1.2).** A sub-delegator that will call the atom itself — the Researcher, web-search, code-review reading a diff — says so at submission. The relay runs every settlement gate and routes nothing; the response always carries the token and the submitter is the one presenter. Before this field existed the same submission was routed by the relay (any registered worker with the capability) AND presented directly by the submitter with no token: two presentations of one admission, one of them unadmitted. `openRelaySubTask` (`@motebit/molecule-runner`) is the one way a molecule opens such a task; it signs as the molecule (`task:submit`), never with an operator secret, and returns the relay's refusal instead of swallowing it.
- **Worker.** `McpServerAdapter` with `taskAdmission` set verifies the token against the pinned relay key _before_ the agent loop starts, checks `digest` against the prompt it was given, then binds `relayTaskId` to the token's `sub` (a caller-supplied `relay_task_id` that disagrees is refused, not trusted). One `sub` admits **one completed execution, with at most one in flight**: the admission is recorded in a durable store (`molecule-runner` persists `admitted-tasks.json` under the data dir) and marked complete only when the run produced a receipt. A run that died or timed out without a receipt may be re-presented by the delegator's honest retry (an intent-stable idempotency key replays the same token); a second presentation while a run is in flight, or after a receipt exists, is refused. A store without completion tracking keeps the strict one-admission rule. A second instance on a separate volume is not covered; that is the trigger for moving the record into the shared database.

## Who enforces, and the default

`@motebit/molecule-runner` exposes `taskAdmission: "relay" | "open"` (config, else `MOTEBIT_TASK_ADMISSION`). Five first-party workers opt in to `"relay"`: code-review and research (the two that spend on inference, 2026-09-12) and auditor, clerk, and web-search (2026-09-13, once the one-presenter arc gave every first-party direct caller a token to carry). read-url stays open behind the named money blocker below. `MOTEBIT_TASK_ADMISSION=open` is the operator escape hatch. The relay key is the pinned `relayPublicKeyHex` / `MOTEBIT_RELAY_PUBLIC_KEY` (the money seam already carries one) when configured; an empty value is unset, a malformed value stops the boot. Otherwise the worker uses the same trust-on-first-use-with-succession primitive every delegator surface uses for the P2P treasury key (`getOrPinRelayKey`, `@motebit/runtime`): the first fetch persists a pin under the data dir, a later key change is honored only when the relay's signed succession chain roots at that pin, and an unreachable relay answers with the pin. An unresolved key denies every task; it never opens the door.

**The default is `"relay"` when priced (flipped 2026-09-13).** `resolveTaskAdmission` returns admission for any listing with a `unit_cost > 0` that is relay-registered, and for a listing it cannot read (fail closed: unreadable is treated as priced). An unpriced or relay-less molecule stays open. Reopening a priced service is an explicit operator act — `taskAdmission: "open"` or `MOTEBIT_TASK_ADMISSION=open` — and the boot log names it as one. The unit tests name this default.

**How the trigger was met.** Every first-party direct caller of a priced atom now carries the relay's token: the Researcher binds every free-lane hop as the one presenter and fails honestly on refusal (its paid P2P lane is relay-dispatched); web-search binds its read-url enrichment the same way; code-review binds its read-url hop the same way. The last blocker was money, not plumbing — read-url was priced and code-review has no payer seam, so the relay refused the unpaid hop. **Decision (2026-09-13): read-url is unpriced.** It is an internal utility atom whose value is already priced into the molecules that call it (research $0.25, code-review $0.20); a separate price created an unpayable internal hop that kept admission open on the atom, which cost more than the price earned. A price may return when an external payer exists — the listing shape and the P2P path are unchanged. With read-url at zero cost, every first-party hop into it binds through the relay under the zero-cost carve-out and arrives with a token, so read-url enforces admission too. All six priced-or-formerly-priced first-party workers now run relay-admitted; summarize is unpriced and open by the default rule.

The relay itself never accepts `task:dispatch` inbound. It is a statement the relay makes, not one it consumes.

## The relay authenticates as itself

Before this arc the relay's MCP forward carried its **master token** as the bearer to every registered worker endpoint — including a stranger's. Two free identities (one registers an endpoint, one submits a task needing its capability) were enough to receive the relay's admin credential. That is the same class of defect as the side door, one layer down: transport auth reused an operator secret where a per-task, per-worker artifact already existed.

The relay authenticates with a signed token of its own, never with the dispatch token. A worker configured with `relayTrust` (or `taskAdmission`: one pin, two checks) treats the caller as its relay only when the bearer is an `mcp:call` token that verifies under the PINNED relay key, with `sub` = this worker, inside the `mcp:call` window, and a `jti` it has not accepted before — the same law as any caller token (`spec/auth-token-v1.md` §7.3), with the pinned relay key in place of a caller-key lookup. The relay mints one per HTTP request of its forward (`mintRelayMcpBearer`). A token that claims to be the relay (its `did` is the pinned key's did:key, or it verifies under that key) and fails any check is refused with a `relay bearer:` reason; it never falls through to the caller path. Relay bearers are remembered in a replay store of their own, never the callers' store, so caller traffic cannot starve relay forwards and no per-caller quota caps the relay's rate (#981 round 2). Single use holds per store: after a worker restart, or on another instance of a multi-instance worker without a shared `relayReplayStore`, a captured relay bearer can be accepted again within its 60 s lifetime. `molecule-runner` sets `relayTrust` for every relay-registered molecule regardless of admission posture. The relay **never sends its master token to a worker**; a forward without a dispatch token or a bearer minter is refused before any socket opens (`task.mcp_forward_refused`, `no_dispatch_token` / `no_relay_bearer`). Workers on an older `@motebit/mcp-server` answer 401 until upgraded, which the forward logs loudly rather than silently retrying with another credential.

**A dispatch token is an admission record, never a transport bearer** (#981). Until 2026-09-29 the worker accepted the dispatch token itself as the relay's bearer. The relay hands that same token to a submitter whenever the submitter is the presenter (`presenter: "submitter"`, or any task it did not route), so a submitter — or anyone the token leaked to — could present it as `Authorization: Bearer motebit:<dispatch_token>` and be served as `relay:<did>` at Verified trust: a credential handed to one principal authenticated as another. The worker now refuses a `task:dispatch` bearer with a 401 whose reason names the fix; the token travels only as the `motebit_task` `dispatch_token` argument. A direct presenter authenticates as itself (its own `mcp:call` token) and is served as itself. Proof: `services/relay/src/__tests__/dispatch-presenter-981.test.ts` (a real relay against a real worker: presenter × door × outcome), tampers in `packages/mcp-server/tamper/dispatch-presenter-981.mjs`.

## The worker authenticates as itself

The mirror image of the section above, closed 2026-09-13. Every call a worker makes TO its relay — `bootstrap` → `register` → `heartbeat` → `listing` → `deregister`, the budget-binding `POST /agent/:id/task` on a sub-delegation, and the caller-key lookups the inbound verifier falls back to — is authenticated by a short-lived, audience-bound token signed by the worker's **own identity key** (`RelayAuth` in `@motebit/mcp-server`, minted per call by `makeAuthTokenMinter` in `molecule-runner`). The audiences are the existing ones: `admin:query` for the registration family, `market:listing` for the listing, `task:submit` to open a task. A fresh identity is introduced to the relay through the public, rate-limited, hijack-guarded `POST /api/v1/agents/bootstrap` (same id with a different key ⇒ 409) so the relay holds a key to verify the first signed call against. Key lookups themselves are public protocol artifacts (relay CLAUDE.md rule 6) and need no bearer at all.

Before this, every first-party worker read `MOTEBIT_API_TOKEN` — the relay **operator's master credential** — from its environment and presented it as the bearer on all of the above. The token bypasses rate limits and unlocks identity and device registration, every admin route, sync, state, and execution. A compromised worker container was therefore a compromised relay, and the blast radius was invisible to every test because nothing was wrong except the blast radius. `check-worker-no-master-token` now fails on any `MOTEBIT_API_TOKEN` read outside the relay and on any `apiToken` field on a worker-side config surface, so the secret cannot come back through the plumbing. `molecule-runner` warns loudly at boot if the variable is still set, so a stale deployment secret is visible until an operator removes it.

The CLI sibling closed the same day (#656): `motebit run` and `motebit serve` register through `apps/cli/src/relay-registration.ts` — bootstrap → register → listing → heartbeat → deregister, each call signed by the motebit's own device key for the route's audience, a fresh token per heartbeat, and never the operator's sync token or an unauthenticated request. No first-party surface presents an operator secret as its own credential anymore.

**2026-09-15 — the alias.** Two days after #649 unset `MOTEBIT_API_TOKEN` on every worker, `fly secrets list` still showed the relay's master token on all seven production workers under the name `MOTEBIT_AUTH_TOKEN` (digest-identical to the relay's own secret): the slate deploy script set the operator's token twice, once as the outbound relay bearer and once as the worker's static inbound bearer, and the retirement grepped the variable, not the value. The closure is structural on both sides. Hand-out: `scripts/deploy-archetype-slate.ts` gives a worker only `MOTEBIT_RELAY_PUBLIC_KEY` (its task-admission pin), and `check-worker-no-master-token` fails any `scripts/deploy-*.ts` line that writes the operator token into a worker secret map under any name. Intake: no first-party worker reads `MOTEBIT_AUTH_TOKEN` or accepts a static inbound bearer; inbound auth is the relay-signed dispatch token or a caller-signed token, verified — never compared to a shared string. Lesson for the next secret retirement: enumerate every hand-out site of the VALUE (deploy scripts, workflows, `.env` templates, scaffolds) and compare digests across apps; a variable name is one alias among several.

## Named gaps, carried with the flip trigger

- **A leaked dispatch token at the admission door (open, #992).** A dispatch token names the worker, the task and the prompt, but not its PRESENTER. A third party holding a leaked copy can present it as the `dispatch_token` argument under its OWN transport bearer; the worker cannot tell it from the submitter, admits it, and returns the result to the third party. The single-use rule bounds it to one execution, which the rightful submitter then loses. It cannot earn relay trust (#981 closed that). Closing it needs a presenter claim on the token (`SignedTokenPayload` / `mintAudienceToken` in `@motebit/crypto`), minted by the relay from the VERIFIED submitter and checked by the worker against the transport caller. The #981 harness carries this cell as an expected failure (`it.fails("GAP: …")`), which turns red the day it closes.
- **Federation.** A task forwarded to a peer relay is delivered by that relay over WebSocket only (`federation-callbacks.ts`); it never MCP-forwards, and the origin relay's token is signed by a key the executor's workers do not pin. An HTTP-only priced worker behind a peer relay was already unreachable through federation; admission does not change that. The executor relay minting its own token for federated dispatch is part of the flip.
- **Retry under an intent-stable idempotency key — CLOSED (both halves).** A retried submission (same caller × target × prompt within the relay's 24-hour idempotency window) replays the original response, token included. Worker half (2026-09-13): a replayed token is re-admitted when the earlier run produced no receipt and nothing is in flight — one completed execution per admission (§ Worker). Relay half (2026-09-14, `refreshDispatchTokenOnReplay`): when the replayed token is expired or within a minute of its 15-minute TTL and the task still has no receipt, the relay mints a fresh token for the same task id, prompt digest, and worker, so the retry presents a live admission of the same work. A task that already produced a receipt is replayed untouched — its delegator belongs at the result, not at a second admission. A task that has aged out of the queue is replayed untouched too; the worker then refuses honestly.

## Who may answer — the mirror of who may present

Admission decides who may present a task; the routing record decides who may answer it. The relay records the executor of every hand-off before the hand-off (and, for a federated forward, the peer it went through), and a receipt for the task is accepted only from that executor, through that peer (#890 round 6, `services/relay/CLAUDE.md` rule 28). One admission ⇒ one presenter ⇒ answers only from those it was presented to: a delegator that reads a signed failed receipt as permission to pay for the work again must only ever read one from the worker it paid.

## One task, one body — many bodies of one identity

An identity serves from several bodies at once (the CLI daemon, the desktop app, a browser tab, a phone), and the relay hands a broadcast `task_request` to every serving socket of the identity. Presentation to all bodies is still ONE presentation of the admission: the relay's claim (`services/relay/src/task-claim.ts`) grants exactly one body (`task_claimed`) and answers the rest `task_claim_rejected`, and a body executes only on the grant. The body half is ONE protocol every surface uses — `TaskClaimCoordinator` (`@motebit/runtime`): claim, wait for the grant, drop on a rejection, ignore a task already held. A leased claim (`lease: true`) is renewed (`task_claim_renew`) while the task runs; a claimer that dies or whose renewals stop reaching the relay loses the claim when the lease lapses (`TASK_CLAIM_LEASE_MS`), and the task is re-presented to the identity's bodies — still answered once: while a verified device holds the claim, a result from any other device of the identity is refused (409 `TASK_CLAIMED_BY_OTHER`), and the answer stays write-once (`answerTask`). A claim made without `lease` (a client that predates it) never lapses. Proof: `services/relay/src/__tests__/one-task-one-body.test.ts` (two and three real bodies; racing claims; a claimer that disconnects or stops renewing).

## What this does not do

- It does not verify payment at the worker. The worker trusts its relay's admission decision, exactly as it already trusts the relay for discovery and settlement records. A worker that wants to verify the chain itself keeps that option open through the same `sub` (the task id joins the relay ledger and the onchain proof).
- It does not close the proxy's snapshot-balance window or the relay's verify-after-dispatch for P2P proofs. Those are the relay's own gates; this arc makes the worker refuse work that never reached them.
- It does not replace the worker's inbound verifier. A worker still needs its static bearer or signed-caller verifier for DIRECT callers; the relay itself is authenticated by its own relay-signed `mcp:call` token, never by the dispatch token (§ "The relay authenticates as itself"), and the worker authenticates to the relay with its own key (§ "The worker authenticates as itself").

## Companion law

[`paid-failure-recourse.md`](paid-failure-recourse.md) says an agent must not advertise what it cannot currently perform. The mirror obligation is here: an agent must not _perform_ what was never bought. Together they make the trust graph a fair recourse — nobody is scored on free work they were tricked into, and nobody pays for a promise the worker could not keep.
