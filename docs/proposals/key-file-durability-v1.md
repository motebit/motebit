# Key-file durability v1 — the class inventory is the contract

**Status:** build 3. Lane A (TypeScript: `@motebit/core-identity`, `@motebit/surface-kit`, the `motebit` CLI, `create-motebit`, `@motebit/tools`) merged as #761. Lane B (desktop) is #763: the desktop key store ships **file-only** (`~/.motebit/dev-keyring.json`, founder split 2026-09-25), and enabling the OS keychain is its own arc, [#764](https://github.com/motebit/motebit/issues/764). Supersedes the withdrawn builds #757, #759, #760 and #762.

**Why this document exists.** Two builds of the key-file fix were withdrawn because each review sampled another pre-existing member of the class that neither build had listed. The founder's decision: an exhaustive written INVENTORY is the contract. Below is that inventory, read on origin/main `b1436c85` and build 2 `48ebeec3`, with a STATUS per MUST-FIX item.

## The three rules

- **R1 — absence is not damage.** Only ENOENT of the name itself reads as absent. A file that exists but cannot be read, does not parse, has the wrong shape, or is a symlink whose target is missing is DAMAGE, never "nothing there".
- **R2 — key material is never destroyed.** Damaged or replaced key material is preserved as the actual old bytes (a byte copy, owner-only, symlinks resolved) on Linux and macOS; otherwise the operation refuses.
- **R3 — writes are atomic and owner-only.** 0600 from creation, fsync of the file and its directory, rename, symlink target resolved; a group- or world-readable key file is narrowed on ANY load, including a load that is about to report the file damaged.

## Founder and PE rulings (recorded here as the doctrine for this class)

1. **A retired key** (a key replaced by a rotation) is erased ONLY after the relay has accepted the succession, or for an identity with no relay configured. Before relay confirmation it is kept (a 0600 copy).
   - `motebit rotate` always resolves a relay (the default relay when none is configured), so it erases the retired key only when the relay recorded the succession or already held the new key; when the relay holds no key for the identity (unregistered) the retired key is kept as `config.json.clobbered-<time>`.
   - `create-motebit rotate` never talks to a relay. It REFUSES an identity with a relay configured (`sync_url`, a pinned `relay_public_key`, or `MOTEBIT_SYNC_URL`) and points at `motebit rotate`. For any other identity it rotates but KEEPS the retired key (`config.json.pre-rotation-<time>`, 0600): it cannot rule out that `motebit` registered the identity with the default relay, so it never erases blind.
   - The desktop and mobile rotation commits (items 27, 29) follow the same ruling in their lanes. The desktop's `commit` ignores the kit's `relay` outcome and **always** keeps the retired key (`device_private_key.preserved-<time>` in `dev-keyring.json`): the ruling permits erasure after the relay confirms, and never requires it.
2. **`motebit.md` and other identity-binding material** (`_identity_file`, project/agent/export/snapshot `motebit.md`) are IN scope: written atomically, and a file that names ANOTHER identity (or cannot be read to tell) is kept as `<file>.clobbered-<time>` before it is replaced.
3. **`motebit relay up`** (item 14) is IN scope.
4. **Out of scope, tracked follow-ups:** operator volume files (item 30), mobile SecureStore (item 29), Windows ACLs (item 32); `shell_exec` and the desktop's arbitrary-path `runtime_host_*` IPC as _capabilities_ (see OUT-OF-SCOPE).

## Lanes

- **Lane A** (#761, merged): items 1–20, 28, and item 31 for the CLI and create-motebit. It also owns the shared contract below.
- **Lane B** (desktop, #763): items 21–27 and the desktop side of items 1–6, 16 and 31. Its design, its state table and the split are in [Lane B: the desktop key store](#lane-b-the-desktop-key-store) below.

**Shared contract — the write-ahead port's preserve verb.** `packages/surface-kit/src/key-rotation.ts` `KeyRotationPorts.writeAhead.setAside(): Promise<void>` — "move the current write-ahead out of the active slot WITHOUT destroying its bytes; resolves when durable; throws on failure (the caller must stop)". The kit calls `setAside` at step 1c (a write-ahead for another identity, or naming neither local key), in `mintFresh` (every branch: relay current, unregistered, no relay configured), and on `refused`. It calls the delete verb `clear()` only for a write-ahead whose key the kit has CONFIRMED the relay holds (or no relay is configured) AND that `commit` has stored locally. `commit` is also told what the relay did (`relay: "recorded" | "already-held" | "none"`) so a surface can keep a retired key the relay never confirmed.

**Shared contract — the config lock.** Every writer of `config.json` that takes part (the CLI's `saveFullConfig`, create-motebit's `writeConfigFile` and its rotation commit) holds an advisory lock around its read-compare-replace:

- the lock file is `<CONFIG_DIR>/config.json.lock` (default `~/.motebit/config.json.lock`; `<agent>/.motebit/config.json.lock` for a scaffolded agent), created with `O_CREAT|O_EXCL` (`"wx"`), mode 0600, holding the holder's pid in decimal;
- a waiter polls every 20 ms for up to 5 s, then refuses the write ("locked by another motebit process"; nothing changed);
- a lock is stale when `kill(pid, 0)` answers ESRCH, or when its mtime is older than 30 s. A waiter breaks it ATOMICALLY: it renames the lock to a private tombstone (one waiter wins), and if the tombstone's inode is not the one it judged stale (another waiter already broke it and took a fresh lock) it links it back under the lock name and does not proceed on it. **Stated limit (decisive review of #761):** this narrows the stale-break race but does not close it. If a third process creates the lock name between a breaker's rename and its link-back, two holders can overlap, and the first to finish removes the other's lock. A breaker that races a holder's exit can also link back an orphan lock, which causes up to 30 s of refusals, never a loss. The config compare-and-swap still refuses any stale identity write, so the worst case is main's (lockless) behaviour narrowed. Closing it fully needs `flock`/`fcntl`, a tracked follow-up;
- the holder unlinks it when done; within one process the lock is re-entrant (create-motebit's rotation holds it across its whole multi-file commit).

Lane B's Rust `update_config` (field-level merge + compare-and-swap) can adopt the same file and protocol in a follow-up to close the residual window between its final re-read and its rename.

## The stopping rule

A build is withdrawn only for a **regression against main**, or for a **miss from its slice** (a site the inventory lists in the slice that the build does not close). A pre-existing member of the class newly found OUTSIDE the slice is recorded as a tracked follow-up here, never a withdrawal.

## Lane B: the desktop key store

**What ships:** the desktop keeps its secrets in `~/.motebit/dev-keyring.json`: plaintext, 0600 (Unix; Windows is best-effort), ssh-key-level protection. Main has always done this, because main's keychain crate had no backend (Finding B-0). **The OS keychain is not used.** Turning it on is its own arc, [#764](https://github.com/motebit/motebit/issues/764); see [The split](#the-split-file-only-now-the-keychain-as-its-own-arc) below.

Three builds failed on the same question: what to do when a real keychain cannot be read, or answers "not found" when it should not. The laws below (K1 to K6) are the design the keychain arc inherits. The store code in `apps/desktop/src-tauri/src/key_store.rs` is written to them, and every law has a test that fails when the law is removed. Those tests run against an in-memory keychain. In the shipped build the store's keychain is `NoKeychain`, whose every read is _unavailable_, so only rows 1a and 2 of the state table can occur. Row 1b (the K3 brake) is the arc's, and is inert in the shipped build.

1. **Record the before-state** on the old version:

4. **Check the files.**

5. **Relaunch.**
   - `motebit_id` is unchanged, with no divergence banner.

9. **Rule out silent drops (criterion e).** On both an ad-hoc and the signed build, after a restart, a key the app wrote reads back through `security` from a separate process.
10. **Re-sign with a different identity.** The access prompt appears, and denying it fails closed, as in step 6.
11. **Lock the keychain while the app runs.** The Mac equivalent of criterion c. No read comes back as absent.

The rest of this section is the keychain design, as the arc inherits it.

**Key material** means `device_private_key`, `pending_rotation`, `pending_identity_switch`, and every `*.preserved-*` copy of them.

### Laws

- **K1: no blind keychain mutation.** Within one operation, the store may set or delete name N in the keychain only after a successful keychain read of N. NotFound counts as a successful read that found nothing. A read error means no keychain mutation of N in that operation. The store then either writes the file (K2 "unavailable") or refuses.
- **K2: unavailable is not unreadable.** A failed keychain read is classified by `key_store::classify`, using keyring 3.6.3's own error mapping:
  - **Unavailable** means there is no store to ask. The operation runs in file-only mode (main's behavior). Unavailable is exactly:
    - macOS: `NoStorageAccess` (errSecNotAvailable, ReadOnly, NoSuchKeychain, InvalidKeychain).
    - Windows: `NoStorageAccess` (ERROR_NO_SUCH_LOGON_SESSION).
    - Linux: `PlatformFailure` wrapping either shape of "nothing to ask", both observed live in Docker:
      - no session bus: `secret_service::Error::Unavailable`;
      - a session bus on which nothing owns `org.freedesktop.secrets` (i3, sway or xfce without gnome-keyring; KeePassXC closed): the bus daemon's standard `org.freedesktop.DBus.Error.ServiceUnknown` (or `NameHasNoOwner`), reaching the store as `Zbus(MethodError(..))`, `Zbus(FDO(..))` or `ZbusFdo(..)`.

      Both are matched on types (the downcast `secret_service::Error`, zbus's `fdo::Error` variants, and the D-Bus error name field), never on message text. Every secret-service call goes to `org.freedesktop.secrets`, so "destination has no owner" can only mean that name.
  - **Read failure** means everything else: denied, cancelled, locked, a D-Bus fault, or a Linux `NoStorageAccess` (Locked, Prompt, NoResult). A read failure refuses the whole operation and is never read as "absent".
  - The two platforms use the variants in opposite senses. On Linux, "locked" is `NoStorageAccess`; on macOS, "cancelled" is `PlatformFailure`. So the classification is per platform, never per variant name.
- **K3: the index is a hint, and a one-way brake.** `keychain-index.json` lists names seen in the keychain. It is written after a verified keychain write. It never decides that a key **exists**: the keychain is asked for every name. It can only make the store more conservative.
  - Suppose the keychain is **unavailable** and a key-material name is listed in the index, or appears in a `dev-keyring.json.keychain-migrated-*` copy (the migration evidence that survives a lost index; never the CLI's `dev-keyring.json.migrated-*`, which is not keychain evidence). **Arc-only:** in the shipped file-only build the brake is inert.
  - Then `get`, `set` and `delete` of that name **refuse**: "stored in the OS keychain, which is unavailable; unlock or start your keyring". They never read it as absent and never write a file value that would become a second candidate.
  - A damaged index or migrated copy counts as evidence.
- **K4: preserve before replace.** Before key material is overwritten with a different value, deleted, or set aside, the store keeps the old value as `<name>.preserved-<time>` in the store that held it, and reads that copy back to verify it. A write refuses if the keychain holds a value the write neither read (as `previous`) nor is writing.
- **K5: one value or a refusal.** If the keychain and the file hold different values for a key-material name, a read is an error. It never picks one silently.
- **K6: first launch mints only over a proven absence.** A first launch writes a key only through `set`, so K1, K2 and K4 hold. A config that names an identity is checked through `get`, where a read failure is an error, so no new identity is minted over a key that could not be read.

### Named cases

- **Double fault** (a keychain write refused, then the confirming read errors). If the successful pre-read found K, a refused write returns an error and the file is not written: a file value would conflict with K under K5. If the pre-read found nothing, a refused write falls back to the file, and no second read is needed. If the post-write verify read errors, the operation returns an error and does not touch the file. K was already preserved (K4) before the write, and the keychain holds either K or NEW. Tests: `double_fault_refused_write_with_a_held_value_refuses`, `double_fault_verify_read_error_refuses_and_keeps_the_old_value`.
- **Shared keychain, moved `~/.motebit`.** The keychain belongs to the OS user, not to the directory.
  - With the config gone, first launch mints a new identity. `set` finds the old K (row 9), preserves it as `device_private_key.preserved-*`, then writes the new key.
  - If the old `~/.motebit` (whose config names the old identity) is later restored, the config names one identity while the keychain holds the other's key. Nothing is lost: the old key is preserved. Detecting that mismatch (the private key does not derive the config's `device_public_key`) is lane A's item 1, in core-identity bootstrap. The desktop store does not guess.
- **First-launch mint while unavailable.**
  - **Key known to live in the keychain** (row 1b, arc only: the index or a `keychain-migrated` copy lists it). Suppose the config names the identity and the keychain is unavailable. `get` refuses, so `hasPrivateKey` rejects and bootstrap stops with "unlock or start your keyring". No divergence mint happens. When the keychain returns, the key reads normally.
  - **Key only ever in a keychain this directory has no record of** (row 1a with both the index and every `.keychain-migrated-*` copy gone, e.g. a fresh `~/.motebit` sharing the OS user's keychain). This is main's behavior: the name reads as absent. A mint writes the file only. K1 guarantees the keychain key is untouched. When the keychain returns, row 7 refuses (K5) instead of silently choosing one. Resolving that is lane A's item 1.

### Lane B follow-ups (not built here; tracked in #764)

- **Plaintext retention.** `dev-keyring.json.keychain-migrated-*` (the arc's migration) and the CLI's `dev-keyring.json.migrated-*` (`migrate-keyring`) keep the retired plaintext (0600) indefinitely. R2 requires the bytes to be kept. When to offer deleting them is a founder call.
- **Growth of preserved copies.** Every replaced key-material value adds one `*.preserved-*` entry, which is never pruned. Lane A's config-first bootstrap (#761) stops the once-per-launch growth F2 described: a refused binding write now happens before any key is stored.
- **K5 in-app resolution.** Rows 7 and 1b refuse, and the app offers no in-app way out beyond "unlock or start your keyring" (1b) or manual repair (7). Detecting which key matches the config (the private key derives `device_public_key`) is the desktop's adoption of core-identity's `probePrivateKey` (#764).

**The class (the founder's three rules)**

- **R1:** absence is not damage. Only ENOENT reads as absent.
- **R2:** damaged or replaced key material is never destroyed. It is preserved as the actual old bytes, owner-only, on Linux and macOS, with symlinks resolved; otherwise the operation refuses.
- **R3:** writes are atomic and owner-only (0600 from creation, fsync of the file and the directory, rename, symlink target resolved). A group- or world-readable key file is narrowed on **any** load, including a load of a damaged file.

#### Finding 0: the desktop never uses the OS keychain, so `dev-keyring.json` holds the device key on every install

**Resolved by the founder split (#763):** `dev-keyring.json` is declared the desktop key store, and the false comment is fixed. The keychain is its own arc (#764). Read below as the finding as it stood on main.

- `Cargo.toml:12` has `keyring = "3"`, with no features.
- In `Cargo.lock:2490-2497`, `keyring 3.6.3` depends only on `log` and `zeroize`. None of the `apple-native`, `windows-native` or secret-service backends is compiled in.
- keyring v3 with no platform feature falls back to its **mock (in-memory) store**:
  - `set_password` returns Ok but nothing persists.
  - A fresh `Entry` answers `NoEntry`.
- **Consequence:** `keyring_get` always falls through to `~/.motebit/dev-keyring.json` (main.rs:501). `keyring_set` writes that file as the "authoritative" store (main.rs:526-528).
- The comment at main.rs:437-441 ("Signed prod builds take the Keychain branch on every call, the dev file never opens") is **false**.
- `~/.motebit/dev-keyring.json` is therefore the ONLY persistent copy of the following, all in **plaintext**:
  - `device_private_key` (hex Ed25519 seed; also the Solana wallet key)
  - `pending_rotation` (the write-ahead, carrying `new_private_key_hex`)
  - the operator PIN hash and attempts
  - BYOK API keys and the sync master token
- It is a first-class member of the class, not a dev-only fallback.
- Confidence: HIGH, from the lockfile dependency list. A runtime check on a signed build (`security dump-keychain` shows no `com.motebit.desktop` entries) was not performed.

#### Cross-cutting (desktop)

1. **The keychain is mock (Finding 0)**, so on every desktop install `dev-keyring.json` is a plaintext private-key file with R1, R2 and R3 all violated. Build 2 does not touch it. The CLI's `migrate-keyring` also reads `~/.motebit/dev-keyring.json` (CLI slice), so it is a shared file.
2. **Shared `config.json`, with no cross-process lock.** CLI `loadFullConfig`…`saveFullConfig` and the desktop's JS read-modify-writes can each revert the other's _changed_ fields:
   - Desktop reverts the CLI's new `cli_encrypted_key`, destroying the CLI's post-rotate key.
   - The CLI reverts the desktop's post-restore `motebit_id`/`device_public_key`.
   - Build 2's drop-guard catches only _removal_.
   - Tauri sync commands serialize the Rust calls inside the desktop, but not the JS read-then-write pairs.
3. **Divergence-mint is a class member by design** (core-identity index.ts:480-518). "The keystore has no key" is decided from an R1-violating probe, and it then overwrites the binding in the SHARED config. That includes the case where the CLI owns the identity: the first desktop launch on a CLI machine orphans the CLI identity.
4. **Flow interactions:**
   - restore→rotate, pairing→rotate and divergence-mint→rotate: C5, C6 or C1 leave `pending_rotation`, and C7 deletes it.
   - Desktop restore during CLI rotate: B-r2.
   - Desktop Settings Save during CLI rotate: C11 with B-r2.
5. **Crash windows.** Key-then-config ordering: C3 (core-identity 583-590), C5 (459 then 479), C6 (702 then 724) and C9 (61 then 73). Only C9 is bridged, by the write-ahead; C3, C5 and C6 have no write-ahead. The `dev-keyring.json` in-place truncate (A) is torn by any crash mid-write.
6. **Platforms:**
   - Windows: `dev_keyring_path` is HOME-only, so the device key cannot be persisted at all; no ACL narrowing; no dir fsync.
   - macOS: the root-owned backup stays 0644 (B-r1).
   - Linux: build 2's `preserve_aside` resolves via `canonicalize` before `hard_link`, which is correct. Cross-device (a symlink into another filesystem) gives EXDEV, which falls back to `copy_owner_only`: correct.

#### Cross-cutting (create-motebit slice)

1. **Version skew is the default:** create-motebit (Apache, `npx`-latest) and the `motebit` CLI (BSL, globally installed) release independently. Any R2 argument that relies on "all writers replace by rename" (the hard-link preservation in C3/C4) is false against the installed base. Either preserve by **copy** (bytes) wherever the live name survives, or accept only the link-then-immediate-rename cases.
2. **No cross-process lock on config.json.** create-motebit load→prompt→save (:788/:834→:1000; :1193→commit) races CLI rotate, CLI restore, and desktop settings or rotate. The stale write destroys a newer key. Build 2 did not address this. It needs compare-and-swap (re-read under a lock and compare `cli_encrypted_key`/`device_public_key` with the value first read) or refusal.
3. **Replace must be write-ahead-aware.** Any flow that changes `motebit_id` or the held key in a config dir (guided replace, agent `--force`, create-motebit rotate) must set aside (preserve, never clear) `pending-rotation.json` in that dir, or refuse while one exists. Otherwise surface-kit 1c or `mintFresh` later unlinks a key the relay may hold.
4. **create-motebit rotate is relay-blind.** It is the one rotation not routed through `surface-kit/key-rotation.ts` (#709 invariant I1). Combined with build 2's `rmSync(oldCopy)`, a registered identity loses the only key the relay accepts. This is outside R1-R3 as an I1 matter but squarely R2 for the old key.
5. **Identity-binding consistency (not R-class):** `~/.motebit/motebit.md` goes stale after create-motebit rotate or CLI rotate and is reused unverified (:956). Project `motebit.md` is written before the agent config. A's non-key fields merge into B's config, including A's plaintext `cli_private_key`.
6. **Damaged-file narrowing (b)** is identical in the CLI and desktop twins per #759. In create-motebit the fix is to call `tightenToOwnerOnly` in `readConfigFile` **before** any throw (on EACCES/parse/shape damage too), and to warn when chmod fails.
7. **Dangling symlink = ENOENT = "absent"** at C1/C2. `writeFileAtomic` then replaces the link. Consider `lstat`-first: a symlink whose target is missing is damage, not absence.

#### Cross-cutting (this slice)

- **X1 — core-identity `bootstrapIdentity` is the shared absence decider for every surface** (index.ts:479-587). ### X. Cross-cutting (whole inventory)

**X1: `bootstrapIdentity` is the one shared absence-decider, and it mints over what it could not read.**

- Location: `packages/core-identity/src/index.ts:468-600`.
  - `configStore.read() == null`, or `hasPrivateKey() == false` ⇒ first launch.
  - First launch runs `storePrivateKey` (overwrite), then `configStore.write` (overwrite).
- The `hasPrivateKey` contract is "must not throw; return false", so it folds _unreadable_ into _absent_.
- Per surface:
  - **CLI** (`identity.ts:234-242`): "no `motebit_id`" means absent even when `cli_encrypted_key` or `cli_private_key` is present. `storePrivateKey` then overwrites the key and deletes `cli_private_key`.
  - **Desktop:** the `dev-keyring.json` probe folds damage into `None`, which makes a divergence-mint. It also fires by design on a CLI-created identity: the first desktop launch orphans it.
  - **Mobile:** a keychain throw becomes `false`.
  - **file-stores (services):** any read error becomes `null`.
- Write order is key first (`:584`), then config (`:587`). A crash in between leaves a new key beside an old binding, and nothing verifies that derive(priv) matches the published key on load.
- A per-adapter fix leaves the contract open for the next adapter. The structural fix is a tri-state probe (`present | absent | unreadable`) in core-identity, plus "never mint over a store that holds a key".

**X2: Lost updates on the shared `config.json`: no lock, no compare-and-swap.** This is the largest member neither PR listed.

- The CLI, desktop and create-motebit all read the whole config, modify it, and write the whole object back.
- Build 2's `saveFullConfig`/`writeConfigFile`/`write_config` preserve only _damaged_ bytes. A **readable** config whose `cli_encrypted_key` differs from the caller's snapshot is replaced unpreserved. The desktop drop-guard catches only a _removed_ identity field, not a _changed_ one.
- Triggers, all realistic:
  - A `motebit` REPL is open (snapshot `index.ts:517`) and `motebit rotate` runs in another terminal. Any later `/model`, `/connect` or `/mcp …` (`slash-commands.ts:752/918/1504/1543/1553/1563`), or `persistMotebitPublicKeys` (`config.ts:174`, `index.ts:881`), writes back the pre-rotation key.

- Consequence: the relay holds B (rotation committed, write-ahead already cleared), the config reverts to A, and B is gone.

**X5: Hard-link preservation keeps a _name_, not the _bytes_.**

- `preserveAside` (CLI, create-motebit, desktop Rust) links first. That is safe only when the live name is replaced by rename immediately afterwards.
- Where the live name survives, any **in-place** writer rewrites the "kept" bytes. Two cases:
  - create-motebit `commitRotation`'s `pre-rotation-` copy after a failed step;
  - a CLI restore that preserves the config and then exits at the write-ahead set-aside.
- In-place writers: the main-era or older installed CLI `saveFullConfig`, main-era desktop `write_config`, `write_file`/`undo_write` tools.
- create-motebit (npx-latest) and the installed CLI/desktop release independently, so version skew is the normal case.
- Related gaps:
  - When the chmod on the backup fails (a root-owned inode on macOS: no `protected_hardlinks`), the backup stays 0644. It should fall back to a user-owned 0600 copy.
  - No directory fsync for the backup's own dirent when `config.json` is a symlink into another directory, or when `setAsidePendingRotation`'s `unlinkSync` follows.
  - Whether APFS/ext4 can persist the unlink before the link without a dir fsync: **UNKNOWN**. Treat it as open.

**X6: Finding (b) is present in all three twins.** The damaged-file narrowing is missing in CLI `loadFullConfig`, create-motebit `readConfigFile` (`config-file.ts:67/73/76` throw before `:80`) and desktop `read_config` (tightens only on `Some`). **X7: Symlinks.**

- Build 2 is Linux-correct for a _resolvable_ symlink: realpath before link, and write at the real target.
- A **dangling** symlink reads as ENOENT, i.e. absent. `writeFileAtomic` then renames over the link itself, and `preserveAside`'s dangling-link refusal is never reached. This loses the binding; the key stays on the unmounted target.
- Outside build 2, none of these writers resolve symlinks: file-stores, molecule-runner, tools, dev-keyring, relay export. `writeFileSync` writes the target in place; `renameSync` replaces the link.

**X8: Platforms.**

- **Linux:**
  - `link(2)` does not follow symlinks (build 2 handles this).
  - With `protected_hardlinks=1`, a key file owned by another user makes `link` return EPERM. The fallback copy then gets EACCES, so the operation refuses; that is correct fail-closed.
- **macOS:**
  - `link` follows symlinks and succeeds on files owned by other users. Local tests therefore hide Linux bugs, and a root-owned backup keeps its mode.
- **Windows (support status UNKNOWN):**
  - chmod only toggles the read-only bit, and every `mode:` option is ignored, so "owner-only" relies on the `%USERPROFILE%` ACL. The adequacy of that ACL is UNKNOWN.
  - Directory fsync is impossible and swallowed.
  - `rename` over an open file can fail with a sharing violation; that is a refusal, not a loss.
  - The desktop `dev_keyring_path` is HOME-only, so with no `HOME` the device key cannot be stored at all.
- **Root-owned files** (an earlier `sudo motebit`/`sudo npx create-motebit`):
  - Reads fail with EACCES, which is correctly damage under b2.
  - Narrowing fails silently.
  - Preservation refuses on Linux and makes a 0644 link on macOS.

### OUT-OF-SCOPE (with reasons)

- **web/spatial IndexedDB and localStorage keystores** (`apps/web/src/encrypted-keystore.ts`, `browser-keyring.ts`, `key-rotation.ts`; `apps/spatial/src/encrypted-keystore.ts`, `browser-keyring.ts`): excluded by instruction. - **Hosted relay on Fly** (`relay_identity` in the production DB; `key-backup-store.ts:148-160` `--force-replace` DELETE): an operator machine; an explicit destructive flag that refuses by default.
- **`federation.ts:753`** plaintext→encrypted UPDATE: the same key re-encoded, so no bytes are lost.

- **CLI `~/.motebit/grants/*`, `skills/*`, `update-check.json`, `motebit.db`, runtime-host socket/lock files, `admitted-tasks.json`:** they hold no key or identity-binding material (verified: `packages/persistence/src` stores no private key).

  - These are _capabilities_ that can reach any file, not key-file code paths.
  - Their protection belongs to approval policy and an IPC allowlist, recorded as hardening. If build 3 elects "every capable deleter is guarded", they move into MUST-FIX.
- **`packages/ai-core/src/config-loader.ts`:** not exported, zero product callers (dead code), and it never writes.
- **OS keychain internals and the CLI macOS Keychain passphrase entry:** OS-managed and not files. The CLI entry holds a passphrase, not key bytes.
- **Browser-download exports from the desktop and web** (`motebit.md`, `motebit-export-*.json`): public content, written by the webview's download manager, not our code.
- **`.env` / `.env.example`:** user-written. They hold `MOTEBIT_PASSPHRASE`, a secret but not key material, and create-motebit never writes them. The shared passphrase is what makes the create-motebit agent (a) sibling trigger routine (X4).
