# Identity-authority writers — one writer per store, one proof for authority

Status: DESIGN (2026-10-08). Docs + a measurement script only; no production code is changed by this lane.
Census: [`identity-authority-inventory.generated.md`](identity-authority-inventory.generated.md), produced by [`scripts/inventory-identity-authority.ts`](../../scripts/inventory-identity-authority.ts) (re-run it; `--check` exits 1 when the committed census is stale).

## Owner decision points

Each one is a choice this design cannot make for the owner. Each has a recommendation, and the increment plan (§7) assumes the recommendation unless the owner rules otherwise.

| D1  | **May a paired device move money?** That means setting `settlement_address`, `sweep_threshold` or a listing's `pay_to_address`, or requesting a withdrawal. | **No, not as a device.** Money authority is a signature by the identity's _current key_ over the specific change (§3.2). ## 0. Why this document exists

A pre-declared stop rule fired on 2026-10-08. Two fix branches, `fix/875-key-pop-v2` and `fix/identity-enforcement-gaps`, have each had three review rounds. Every round found another **authority-bearing identity field writable by a party that never proved the identity's current key**, which later regains authority. Patching doors one at a time does not converge. The class is closed by construction instead: **a census of every writer, a single writer per store, and a runtime capability that only a proven-current-key verifier can mint.** This is the same move that closed the answer class (`answerTask` + `issueAnswerCapability`, `services/relay/CLAUDE.md` rule 28) and the allocation-money class (`moveAllocationMoney`, rule 29).

The precedent that already exists, and why it is not enough: `BoundIdentity` (`services/relay/src/identity-binding.ts:70`) is a runtime capability with an ES private field and a module-private mint. Every per-identity write helper reads its owner through `unwrapBound`. It is minted by `bindCaller` (`identity-binding.ts:127-138`), and `bindCaller` proves only **"the caller's token verified under _some_ key on file for this id"**. That key is from a device row or a registry fallback (`auth.ts:98`, `auth.ts:160-163`). A device row is written by doors that never proved the identity's key (§1.3), so `BoundIdentity` answers _whose row is this_. It never answers _who may redirect this identity's money or keys_. This design adds the second capability. It does not weaken the first.

## 1. Inventory

### 1.1 Method

`scripts/inventory-identity-authority.ts` parses every non-test `.ts` file under `services/relay/src`, `packages/persistence/src`, `packages/runtime/src`, `packages/mcp-server/src`, `packages/virtual-accounts/src` and `packages/core-identity/src` (220 files) with the TypeScript compiler API.

- **Schema.** It reads every `CREATE TABLE` and `ALTER TABLE … ADD COLUMN` in string and template literals. A table is identity-keyed when a column names an identity, peer relay or caller (`KEY_COLUMN`).
- **Writers.** It finds every INSERT, REPLACE, UPDATE, DELETE and upsert `DO UPDATE SET`, including `SET ${sets.join()}` lists built from sibling `"col = ?"` literals and module- or constructor-level prepared statements, which it resolves to their uses. It also counts every `setAgentTrust(…)` call.
- **Reach.** It computes route reach with a name-based reverse call graph, resolving import aliases, to depth 6.
- **Proof per door.** It parses the transport auth from the relay's own tables (`MASTER_TOKEN_CARVE_OUTS`, `middleware.ts:357`; `PUBLIC_AGENT_ROUTES`, `agents.ts:493`; the `bearerAuth` prefixes; `/agent/*/task` dualAuth). It raises that proof only by unconditional in-handler checks: caller = path, operator-only, or the handler's own signature check on a door with no transport auth. Conditional checks are listed as "also seen" and never counted.
- **Limits.** Its aperture limits are in its header. Its proof column is a **lower bound checked by hand** in §1.3.

## 3. The single writer

### 3.1 Shape

There is one module per store, each with **one exported writer function**, and each writer takes a **runtime capability** that only that store's verifier can mint. "Runtime capability" means the `BoundIdentity` construction: a class with an ES private field, a constructor demanding a module-private symbol, and a writer that does a private-brand check (`#cap in x`) and throws on anything else. A brand type is not enough: #860 forged v3's brand six ways in ordinary TypeScript, as recorded in `scripts/check-identity-authority-writers.ts` part 3.

### 3.2 What "proven current key" means

**`proveCurrentKey`** verifies a signature over the domain-separated bytes:

```
"motebit/authority/v1\n" ‖ JCS({ motebit_id, field, value, relay_id, ts, nonce })
```

The signature must verify under **the current key** of the id (defined per id class below), `ts` must be within ±5 min, and `(motebit_id, nonce)` must be unseen. The replay store is 875's `key-proof-replay.ts` with migration v59, reused as-is. The signature binds the _field and value_ and the _relay_. A captured authority signature therefore cannot be replayed to set another field, another value, or the same field on another relay.

| Id class                                  | Current key                                                                                                                                                                                                                                                                                                       |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sovereign (`claimsSovereignId`, from 875) | The head of the lineage rooted at the genesis key `K₀` with `id = deriveSovereignMotebitId(K₀)` (`identity-keys.ts:268`), extended only by recorded successions verified link by link. ### 3.3 Operator

`OperatorAct` writes only these changes:

- `delist`
- `revoke`
- `restore` (rule 22: the operator's restore-listing and a verified migration arrival are the only lifts)
- `clear_pay_to` (NULL)
- `freeze_money_fields`
- E-op on an id with **no** row at all (`recordOperatorServiceKey`)

It writes nothing that sets or redirects a key, guardian, pay-to, endpoint or sweep. `agents.ts:1998-2006` already refuses any device token on revoke-listing and restore-listing. This keeps that rule and makes it a type.

### 3.4 Worker trust store

`KeyAdoption` is minted for `(remote_id, key)` only on one of these:

- (a) `remote_id = deriveSovereignMotebitId(key)`
- (b) a `verifySuccessionChain` from the record's adopted key to `key`, with recovery honored only under the record's pinned guardian (the fix branch's `successionLinks` rule, reused)
- (c) operator config (`knownCallers`)

A relay-served key without (a)–(c) **never authenticates** (D6). The caller gets the same answer as for an unknown caller, and the mismatch is logged. `VerifiedReceipt` is minted only when the receipt verifies under the record's adopted key. A keyless record therefore accrues interaction counts but its `trust_level` is held at FirstContact. That closes W2 without discarding history: counts keep, the level is capped, and the level is recomputed on adoption. `relayConfirmedCallers` is deleted (W3).

These stay outside the authority writer:

- peer forward statistics and circuit-breaker state (`task-routing.ts:931-974`)
- settlement snapshots (`allocation-escrow.ts:403`)

- the intake ledger

Each is derived from an artifact that already passed its own chokepoint (rule 28 `admitReceipt`, rule 29 `moveAllocationMoney`). The gate (§4) registers them as derived writers with the column they are derived from.

## 4. Gate: a new writer outside the single writer fails

Ranked by strength (`docs/doctrine/composition-preserves-enforcement.md`: reduce the seams above prove-the-remainder):

1. **Database guard, at execution.** `installAuthorityGuards(db)` follows the precedent of `installFreezeMoneyGuards` (`freeze.ts:349`). It is TEMP and per connection. The relay opens its database only in `index.ts` (rule 30), and the guard is installed after every schema mutation.
   - It creates `temp.authority_window(open INTEGER)`.
   - It creates `BEFORE INSERT` and `BEFORE UPDATE OF <authority columns>` triggers on every table in §2, plus `BEFORE DELETE` on rows carrying one. Each trigger fires `RAISE(ABORT, 'AUTHORITY_WRITE_OUTSIDE_WRITER')` unless the window is open.
   - `writeAuthority`, `writeOperatorAct` and `writePeer` open the window inside their synchronous better-sqlite3 transaction and close it in `finally`. An `await` between open and close is a compile-time shape the static gate (3) refuses.
   - Any other writer, now or future, aborts in tests and in prod.
   - The authority column set is **exported from `identity-authority.ts`**. A boot assertion throws if a declared column is missing, the same as `FREEZE_MONEY_COLUMNS`.
2. **Door harness, at execution.** `authority-doors.test.ts` enumerates every registered route from the Hono router, as `master-token-carve-outs-855.test.ts` already does, and drives each route three ways:
   - (a) with a token from a **planted device row** for victim V
   - (b) with V's paired-device token
   - (c) unauthenticated

   Bodies come from a corpus that names every §2 field. The test snapshots every authority column of V before and after and asserts they are byte-identical. With the triggers dropped, the same harness must go red against main's doors #3–#6 (a severed-guard proof, per rules 21, 22 and 28).

3. **Static.** `check-identity-authority-writers` (#159) gains part 5: a SET list, INSERT column list or upsert `DO UPDATE SET` naming an authority column, in any spelling it already reads, outside `identity-authority.ts`, `peer-authority.ts` or a registered derived writer fails, with a repair instruction naming `writeAuthority`. Its aperture is the census script's (relay + persistence + runtime + mcp-server).
4. **Worker.** The runtime wraps every `AgentTrustStoreAdapter` it is given. `setAgentTrust` refuses a write that changes `public_key` or raises `trust_level` unless the call carries a capability the `trust-authority.ts` WeakSet issued. This is proven by a forgery test, as `identity-binding-forgery.test.ts` is.
5. **Census freshness.** `npx tsx scripts/inventory-identity-authority.ts --check` runs in `pnpm check`, so a new authority writer shows up as a diff in review even before the static gate names it.

### 5.2 Gaps

- **G1. Self-propose is a confirm oracle.** Anyone obtains our signature over `${ourId}:${N}:${suite}` for any chosen N (`federation.ts:1771`). That is exactly the confirm message (`:1865`). The attack: propose to P as R with R's real key and the attacker's endpoint, collect P's nonce, have R self-sign it, then confirm at P. R's traffic on P then goes to the attacker. The fix branch's v2 refuses self-propose and binds confirm to both parties and the endpoint (`federationConfirmMessage`).
- **G2. Heartbeat request and response share bytes and name no recipient.** Any peer of R can POST to R and receive `R|now|suite`, which is a valid heartbeat _from R_ to every peer for 5 minutes. A replayed heartbeat keeps a dead or impersonated R `active`, and a flood of replays resets `missed_heartbeats` (`federation.ts:1935`). The response is never verified.
- **G3. Peer remove signs the bare `relay_id`.** It has no tag, recipient, expiry or nonce. One signature, served in the clear by the admin route, removes R at **every** relay, forever, including after a re-peer.
- **G4. No recipient binding** on discover, task forward/result, settlement forward or VoteRequest. A message signed for B is replayable to C within the window.
- **G5. No nonce at the signature layer** anywhere in federation. Idempotency is downstream and per message kind.
- **G6. Type confusion.** The agent and federation settlement anchors are signature-interchangeable. The identity-log anchor, proxy token and withdrawal receipt carry no type.
- **G7. A horizon witness signature equals the issuer's signature.** The witness response's `motebit_id` is unsigned.
- **G8. Revocation events have no freshness and no recipient.** They are replayable to any peer of the signer forever. Only the `revocation:` prefix separates them.

### 5.3 Proposal: one registry, one verify helper

There is a closed registry `FEDERATION_MESSAGE_KINDS` in `@motebit/protocol` (the eight-artifact registry pattern, `docs/doctrine/registry-pattern-canonical.md`). Each kind fixes five properties:

- **signer role:** origin relay, executor relay, or proposer
- **verifier role**
- **freshness window**
- **replay rule:** single-use nonce, or idempotent by a named id
- **peer state required:** active, or the handshake for propose/confirm

Every federation signature is over:

```
"motebit-fed/v2\0" ‖ kind ‖ "\0" ‖ JCS({ kind, sender, recipient, ts, nonce, body_sha256 })
```

`verifyFederationMessage(db, kind, envelope, sig, { self })` is the **only** federation verifier, and it mints `PeerProof` (§3.1). It checks, in order:

1. kind ∈ registry
2. `recipient === self.relay_id`
3. |now − ts| within the kind's window
4. the signer key: `relay_peers.public_key` of `sender` in the kind's required state, or for `confirm` the key bound by the stored proposal
5. the signature
6. the nonce is consumed in `relay_federation_nonces(sender, nonce, expires_at)`, in the same transaction as the write it authorizes

Kinds and how each gap closes:

- **`heartbeat`, `heartbeat-ack`** — the ack signs the request's nonce (closes G2).
- **`peer-propose`, `peer-confirm`** — taken from the fix branch's `federationProposeMessage` and `federationConfirmMessage` and their HMAC nonce, then re-expressed as registry kinds (closes G1).
- **`peer-remove`** — names its recipient and carries ts and nonce. The admin route mints it for one named recipient (closes G3).
- **`discover`, `task-forward`, `task-result`, `settlement-forward`, `vote-request`** (close G4 and G5).
- **`revocation-event`** — gains a recipient and ts (closes G8).

Relay-issued artifacts that a third party verifies (anchors, receipts, tokens) adopt the `spec`-tag pattern the transparency family already uses (closes G6). Agent and federation anchors get distinct `spec` values. Horizon witness responses sign `{cert_hash, witness_id}` under their own kind (closes G7).

Migration follows D4: one deploy window during which v2 is signed and v1 is verified **for heartbeat only**. `peer-remove` v1 and self-propose are refused from the first deploy.
