### Invariants (frozen 2026-10-08)

These two sentences are the contract every increment is checked against. They are frozen verbatim; a change to either is an owner decision, not an edit.

- **I1.** No authority-bearing identity state may be created, redirected, or strengthened unless the write passes through the canonical authority writer and proves control of the identity's current key.
- **I2.** Operator and recovery paths may reduce authority without that proof, but may never create or redirect authority.

## 0. Why this document exists

A pre-declared stop rule fired on 2026-10-08. Two fix branches, `fix/875-key-pop-v2` and `fix/identity-enforcement-gaps`, have each had three review rounds. Every round found another **authority-bearing identity field writable by a party that never proved the identity's current key**, which later regains authority. Patching doors one at a time does not converge. The class is closed by construction instead: **a census of every writer, a single writer per store, and a runtime capability that only a proven-current-key verifier can mint.** This is the same move that closed the answer class (`answerTask` + `issueAnswerCapability`, `services/relay/CLAUDE.md` rule 28) and the allocation-money class (`moveAllocationMoney`, rule 29).

The precedent that already exists, and why it is not enough: `BoundIdentity` (`services/relay/src/identity-binding.ts:70`) is a runtime capability with an ES private field and a module-private mint. Every per-identity write helper reads its owner through `unwrapBound`. It is minted by `bindCaller` (`identity-binding.ts:127-138`), and `bindCaller` proves only **"the caller's token verified under _some_ key on file for this id"**. That key is from a device row or a registry fallback (`auth.ts:98`, `auth.ts:160-163`). A device row is written by doors that never proved the identity's key (§1.3), so `BoundIdentity` answers _whose row is this_. It never answers _who may redirect this identity's money or keys_. This design adds the second capability. It does not weaken the first.

## 1. Inventory

### 1.1 Method

`scripts/inventory-identity-authority.ts` parses every non-test `.ts` file under `services/relay/src`, `packages/persistence/src`, `packages/runtime/src`, `packages/mcp-server/src`, `packages/virtual-accounts/src` and `packages/core-identity/src` (220 files) with the TypeScript compiler API.

- **Schema.** It reads every `CREATE TABLE` and `ALTER TABLE … ADD COLUMN` in string and template literals. A table is identity-keyed when a column names an identity, peer relay or caller (`KEY_COLUMN`).
- **Writers.** It finds every INSERT, REPLACE, UPDATE, DELETE and upsert `DO UPDATE SET`, including `SET ${sets.join()}` lists built from sibling `"col = ?"` literals and module- or constructor-level prepared statements, which it resolves to their uses. It also counts every `setAgentTrust(…)` call.
- **Reach.** It computes route reach with a name-based reverse call graph, resolving import aliases, to depth 6.
- **Proof per door.** It parses the transport auth from the relay's own tables (`MASTER_TOKEN_CARVE_OUTS`, `middleware.ts:357`; `PUBLIC_AGENT_ROUTES`, `agents.ts:493`; the `bearerAuth` prefixes; `/agent/*/task` dualAuth). It raises that proof only by unconditional in-handler checks: caller = path, operator-only, or the handler's own signature check on a door with no transport auth. Conditional checks are listed as "also seen" and never counted.
- **Limits.** Its aperture limits are in its header. Its proof column is a **lower bound checked by hand** in §1.3.

## 3. The single writer

### 3.1 Shape

There is one module per store, each with **one exported writer function**, and each writer takes a **runtime capability** that only that store's verifier can mint. "Runtime capability" means the `BoundIdentity` construction: a class with an ES private field, a constructor demanding a module-private symbol, and a writer that does a private-brand check (`#cap in x`) and throws on anything else. A brand type is not enough: #860 forged v3's brand six ways in ordinary TypeScript, as recorded in `scripts/check-identity-authority-writers.ts` part 3.

### 3.2 What "proven current key" means

**`proveCurrentKey`** verifies a signature over the domain-separated bytes:

```
"motebit/authority/v1\n" ‖ JCS({ motebit_id, field, value, relay_id, ts, nonce })
```

The signature must verify under **the current key** of the id (defined per id class below), `ts` must be within ±5 min, and `(motebit_id, nonce)` must be unseen. The replay store is 875's `key-proof-replay.ts` with migration v59, reused as-is. The signature binds the _field and value_ and the _relay_. A captured authority signature therefore cannot be replayed to set another field, another value, or the same field on another relay.

| Id class                                  | Current key                                                                                                                                                                                                                                                                                                       |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sovereign (`claimsSovereignId`, from 875) | The head of the lineage rooted at the genesis key `K₀` with `id = deriveSovereignMotebitId(K₀)` (`identity-keys.ts:268`), extended only by recorded successions verified link by link. A recovery link counts only under a guardian set under a standing key (875 `sovereignLineage` + v60 `recoveryLinkStands`). |
| Legacy (non-sovereign)                    | The `identity_keys` holder **only when its evidence row exists**: E-link, E-mig, E-op, or E-main with 875's v58 `relay_registry_key_evidence`. With no such holder there is **no current key**, and money and recovery fields are frozen (D2).                                                                    |
| Rotated                                   | Only the chain head. A retired key never mints, consistent with `applySuccession`'s refusals (rule 21, #775).                                                                                                                                                                                                     |
| Devices                                   | **Never.** A device row is not evidence for any authority field. A device whose key _equals_ the current key signs as the identity. That is the D1 recommendation.                                                                                                                                                |
| Relay operator                            | Never mints `ProvenKey`. It mints only `OperatorAct` (D3).                                                                                                                                                                                                                                                        |

Consequences:

- `departureFrom` (`succession-apply.ts:271`) loses its device-row fallback for any id that has a current key, and `proveSuccession` departs only from the current key (closes rows 11–16).
- `healRegistryKey` is deleted (row 7).
- `verifySignedTokenForDevice` still authenticates _requests_. It no longer implies authority over §2 fields.
- `bindCaller` stays the `BoundIdentity` minter for informational rows.

### 3.3 Operator

`OperatorAct` writes only these changes:

- `delist`
- `revoke`
- `restore` (rule 22: the operator's restore-listing and a verified migration arrival are the only lifts)
- `clear_pay_to` (NULL)
- `freeze_money_fields`
- E-op on an id with **no** row at all (`recordOperatorServiceKey`)

It writes nothing that sets or redirects a key, guardian, pay-to, endpoint or sweep. `agents.ts:1998-2006` already refuses any device token on revoke-listing and restore-listing. This keeps that rule and makes it a type.

### 3.4 Worker trust store

`KeyAdoption` is minted for `(remote_id, key)` only on one of these:

- (a) `remote_id = deriveSovereignMotebitId(key)`
- (b) a `verifySuccessionChain` from the record's adopted key to `key`, with recovery honored only under the record's pinned guardian (the fix branch's `successionLinks` rule, reused)
- (c) operator config (`knownCallers`)

A relay-served key without (a)–(c) **never authenticates** (D6). The caller gets the same answer as for an unknown caller, and the mismatch is logged. `VerifiedReceipt` is minted only when the receipt verifies under the record's adopted key. A keyless record therefore accrues interaction counts but its `trust_level` is held at FirstContact. That closes W2 without discarding history: counts keep, the level is capped, and the level is recomputed on adoption. `relayConfirmedCallers` is deleted (W3).

## 4. Gate: a new writer outside the single writer fails

Ranked by strength (`docs/doctrine/composition-preserves-enforcement.md`: reduce the seams above prove-the-remainder):

1. **Database guard, at execution.** `installAuthorityGuards(db)` follows the precedent of `installFreezeMoneyGuards` (`freeze.ts:349`). It is TEMP and per connection. The relay opens its database only in `index.ts` (rule 30), and the guard is installed after every schema mutation.

### 5.2 Gaps

- **G1. Self-propose is a confirm oracle.** Anyone obtains our signature over `${ourId}:${N}:${suite}` for any chosen N (`federation.ts:1771`). That is exactly the confirm message (`:1865`). The attack: propose to P as R with R's real key and the attacker's endpoint, collect P's nonce, have R self-sign it, then confirm at P. R's traffic on P then goes to the attacker. The fix branch's v2 refuses self-propose and binds confirm to both parties and the endpoint (`federationConfirmMessage`).
- **G2. Heartbeat request and response share bytes and name no recipient.** Any peer of R can POST to R and receive `R|now|suite`, which is a valid heartbeat _from R_ to every peer for 5 minutes. A replayed heartbeat keeps a dead or impersonated R `active`, and a flood of replays resets `missed_heartbeats` (`federation.ts:1935`). The response is never verified.
- **G3. Peer remove signs the bare `relay_id`.** It has no tag, recipient, expiry or nonce. One signature, served in the clear by the admin route, removes R at **every** relay, forever, including after a re-peer.
- **G4. No recipient binding** on discover, task forward/result, settlement forward or VoteRequest. A message signed for B is replayable to C within the window.
- **G5. No nonce at the signature layer** anywhere in federation. Idempotency is downstream and per message kind.
- **G6. Type confusion.** The agent and federation settlement anchors are signature-interchangeable. The identity-log anchor, proxy token and withdrawal receipt carry no type.
- **G7. A horizon witness signature equals the issuer's signature.** The witness response's `motebit_id` is unsigned.
- **G8. Revocation events have no freshness and no recipient.** They are replayable to any peer of the signer forever. Only the `revocation:` prefix separates them.

### 5.3 Proposal: one registry, one verify helper

There is a closed registry `FEDERATION_MESSAGE_KINDS` in `@motebit/protocol` (the eight-artifact registry pattern, `docs/doctrine/registry-pattern-canonical.md`). Each kind fixes five properties:

- **signer role:** origin relay, executor relay, or proposer
- **verifier role**
- **freshness window**
- **replay rule:** single-use nonce, or idempotent by a named id
- **peer state required:** active, or the handshake for propose/confirm

Every federation signature is over:

```
"motebit-fed/v2\0" ‖ kind ‖ "\0" ‖ JCS({ kind, sender, recipient, recipient_public_key, ts, nonce, body_sha256, suite })
```

`verifyFederationMessage(db, kind, envelope, sig, { self })` is the **only** federation verifier, and it mints `PeerProof` (§3.1). It checks, in order:

1. `recipient_public_key === self.public_key` (shipped in round 3, §5.4: an id alone names no relay)
2. kind ∈ registry; `recipient === self.relay_id`
3. |now − ts| within the kind's window
4. the signer key: `relay_peers.public_key` of `sender` in the kind's required state, or for `confirm` the key bound by the stored proposal
5. the signature
6. the nonce is consumed in `relay_federation_nonces(sender, nonce, expires_at)`, in the same transaction as the write it authorizes

Kinds and how each gap closes:

- **`heartbeat`, `heartbeat-ack`** — the ack signs the request's nonce (closes G2).
- **`peer-propose`, `peer-confirm`** — taken from the fix branch's `federationProposeMessage` and `federationConfirmMessage` and their HMAC nonce, then re-expressed as registry kinds (closes G1).
- **`peer-remove`** — names its recipient and carries ts and nonce. The admin route mints it for one named recipient (closes G3).
- **`discover`, `task-forward`, `task-result`, `settlement-forward`, `vote-request`** (close G4 and G5).
- **`revocation-event`** — gains a recipient and ts (closes G8).

Relay-issued artifacts that a third party verifies (anchors, receipts, tokens) adopt the `spec`-tag pattern the transparency family already uses (closes G6). Agent and federation anchors get distinct `spec` values. Horizon witness responses sign `{cert_hash, witness_id}` under their own kind (closes G7).

Migration follows D4 as ruled: **no dual-stack window**. From the first deploy of Inc 1, v1 `heartbeat`, v1 `peer-remove` and self-propose are refused with a fail-closed error naming the v2 message, and the relay signs only `heartbeat` v2 and `peer-remove` v2. Inc 1 ships those two kinds plus the self-propose refusal, and — after the F1 cold review — the handshake's `peer-challenge` and `peer-confirm` (§5.4); the rest of the registry (discover, forward, result, settlement, vote, revocation) lands in Inc 6 on the same envelope and helper. Both relays of a federated pair must be deployed together, because an Inc-1 relay refuses an older relay's v1 heartbeats and an older relay cannot verify v2.

### 5.4 Shipped in Inc 1b (relay-federation@1.5)

- **The helper.** `signFederationMessage` / `verifyFederationMessage` in `@motebit/crypto` (`packages/crypto/src/federation-message.ts`) are the one producer and the one verifier. Envelope `{ kind, sender, recipient, ts, nonce, body_sha256, suite: "motebit-jcs-ed25519-hex-v1" }`, exactly those seven fields; signed bytes `"motebit-fed/v2\0" ‖ kind ‖ "\0" ‖ JCS(envelope)`; `body_sha256` = hex SHA-256 of JCS(body); ±5 min. The verifier is pure and returns a named refusal; the relay records `(sender, nonce)` in `relay_federation_nonces` inside the same transaction as the write (`consumeFederationNonce`, `federation.ts`), and refuses a seen nonce with 409.
- **`heartbeat`** (request `{ message, agent_count, revocations? }`, body `{ agent_count, revocations }`) and **`heartbeat-ack`** (response `{ message, agent_count }`, body `{ request_nonce, agent_count }`). The sender counts a heartbeat delivered only when the ack verifies under the peer's stored key and answers its own nonce. Closes G2.
- **`peer-remove`** (request `{ message }`, body `{ action: "remove" }`), minted by the master-token `GET /api/v1/admin/federation/peer-removal-signature?recipient=<id>` for one recipient. Closes G3.

- **v1 refused by name.** A heartbeat or removal without `message` is a 400 naming the v2 message, before any lookup, counter or rate-limit slot. The per-peer limit on these two routes counts only requests whose v2 signature verified (replays are 409 before the limit).

### 5.5 Relay ids are not self-certifying (deferred, with a trigger)

A relay's `relay_motebit_id` is a random UUID minted at `initRelayIdentity`; nothing binds it to the relay's Ed25519 key. So an id names a relay only by convention: a relay's `/federation/v1/identity` can claim any id under any key, and a relay that has never peered an id cannot tell its first claimant from its owner. 1.5 binds keys wherever both sides already hold one — the confirm commits to the recipient's key, the key pin refuses a second key for a confirmed id — but the first handshake for a never-peered id is first-come by key: whoever confirms it first, under its own key, holds the id at that relay (the harness counts these states and exempts them from I-live, by name).

The deeper fix is to derive the relay id from the key (as `deriveSovereignMotebitId` does for agents), so the id itself commits to the key and every verifier checks it offline. Deferred, not built: it changes every relay's id (a federation-wide migration — peers re-peer, `relay_peers`, settlements and anchors keyed by the old id), and nothing today makes a first-come squat on a never-peered id valuable: discovery and routing reach only peers an operator chose. **Trigger:** the first of — open peering (a relay that accepts a propose from a party its operator did not name), a third operator in the mesh, or any routing/settlement decision that trusts a relay id it has not itself peered.

**Decided (founder, 2026-10-11): self-certifying relay ids are the NEXT step after the envelope's recipient-key binding (§5.4, round 3).** Three cold-review rounds on this branch found the same class each time — a peer-authority message naming its recipient by an id that is not self-certifying — and the recipient-key binding closes it for every message whose signer holds a verified key, but not the first-come hold on a never-peered id. Not implemented on this branch; it is the next lane.

### 7.1 Shipped ahead of Inc 3: guardian recovery requires provenance (2026-10-11)

A cold review found row 9 live on main as a full takeover: a paired device's token (its own key) registered a guardian G it controls (the attestation is G's own signature, so it is self-made) and then posted `signGuardianRecoverySuccession(G, K0 → K_att)` to `/rotate-key`, which a recovery reaches without the caller check. The identity's key became K_att, and its money destinations followed. Founder-approved 2026-10-11 as a narrow fix on main, closing the paired-device guardian plant before Inc 3:

- **Provenance** (migration v58, `relay_guardian_evidence`, the same table this lane's step2 branch plans as its v60 — its create is then a no-op): `/agents/register` records `(motebit_id, guardian, set_under_key, evidence)` only when the request proved the identity's CURRENT key — `holder`: the bearer was verified by the device row holding exactly the `identity_keys` key, read before any write in the request; `sovereign`: the same request recorded E-sov under the bearer's possession of the genesis key. A paired device's own key, the master token (D3), a legacy id with no held key (D2) and the v42 backfill's transplant record nothing. The guardian is still stored and served as before (register answers byte-identically).
- **Enforcement** (`guardianProvenance`, `identity-keys.ts`): `/rotate-key` and the register door's succession branch accept a recovery only when the guardian on file is exactly the one the latest evidence row names — so a guardian the owner replaced cannot be revived by replaying its old attestation. Otherwise 403 `GUARDIAN_NOT_PROVEN` (recorded as `succession:guardian_not_proven`), naming the fix: re-set the guardian with the identity key.
- **Existing guardians:** none has provenance before v58; the census's Q4 now lists exactly the unproven ones (`provenGuardianOf`, the same rule). Prod measured Q4 = 0, so no legitimate user is affected.
- **Harness:** `services/relay/src/__tests__/guardian-recovery-provenance.test.ts` (setter × recovery signer × identity kind, the exact repro, and a differential set: every non-guardian-recovery `/rotate-key` and register request answers as on main).
- **Legacy ids:** a non-sovereign id with no held key can never get guardian evidence (no holder, and `recordFirstIdentityKey` refuses its id), so `/agents/register` refuses to set its guardian (400 `GUARDIAN_REQUIRES_SOVEREIGN_IDENTITY`, before any write; an operator registration that records E-op in the same request is not refused), and `GUARDIAN_NOT_PROVEN` tells such an id that recovery is not available rather than naming a re-set that cannot work. Prod Q4 = 0, so no existing user is affected.
- **Migration numbering (coordination with the step2 branch):** this branch takes migration **v58** for `relay_guardian_evidence`, with **LATEST-ROW-ONLY** semantics — only the guardian the identity's latest evidence row names is proven, so an earlier guardian cannot recover once replaced, even if it was itself set with provenance. The `design/identity-authority-step2` branch must renumber its migrations after this (v59+), drop its duplicate `guardian_evidence` DDL, and adopt the latest-row semantics. It must also adopt D3 — a guardian the operator sets (the master token) carries no evidence — where its design text currently counts a guardian set "or by the operator" as proven.
- **Not closed here (Inc 3):** a device token can still REPLACE a proven guardian with an unproven one — that disables recovery until the owner re-sets it (a reduction, never a takeover); and the census reads the evidence writer as reachable by a device token, because the proof is decided inside the handler, not by the door's middleware.

**Do not merge either branch whole.** 875 guards the register door only. Its R2 test proves register and leaves sweep-config, listing and withdraw open. `identity-enforcement-gaps` overlaps it in nine files (`federation.ts`, `credentials.ts`, `index.ts`, `transparency.ts`, `test-helpers.ts`, `PRIVACY.md`, `services/relay/CLAUDE.md`, and two federation authority tests), and its D6 behavior is the opposite of this design's. The self-contained pieces listed above port cleanly. The route rewrites are redone through the writer, because a fourth round of per-door patching is exactly what the stop rule forbids.
