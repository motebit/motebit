# Milestone ledger: verifiable agent authority

The one durable record of the founder-authorized engineering program toward motebit's NIST-aligned end state (direction of 2026-10-27; standards map in [`docs/doctrine/nist-alignment.md`](../doctrine/nist-alignment.md)). Each milestone lists its owner, dependencies, acceptance tests, the evidence so far, its GO/NO-GO and the next task. Every change to this file is a reviewed PR. Evidence cites a commit, PR or run id, with the decisive log values copied inline, because GitHub deletes run logs after their retention period.

**Stopping condition.** An independent verifier can establish which agent acted, under whose authority, within what limits, with what outcome, and whether revocation worked.

## Evidence levels

Every piece of evidence carries exactly one level, the strongest it has reached. A claim is never stated above its level. Independent verification and operational demonstration are separate axes: a live observation by the operator is demonstrated but not independently verified. A live observation with no run id to re-check (a terminal result, a review state GitHub later rewrote) is marked **observed live, no run id** and does not count as operationally demonstrated.

| Level                          | Meaning                                                                                                                                                                    |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **implemented**                | The code or configuration is on `main`.                                                                                                                                    |
| **tested internally**          | A test, tamper suite or review run by the motebit operator shows it. Unbriefed cold reviews count here: the reviewer is still the operator's agent.                        |
| **independently verified**     | Checked by a party outside the motebit operator, without privileged access. None yet; milestone F creates the first.                                                       |
| **operationally demonstrated** | Observed live in the real environment, with real accounts and real enforcement (for milestone A: GitHub's ruleset, merge queue and identities), and recorded with run ids. |

## Guarantees and their limits

The repository autonomy properties hold **only while the configured GitHub protections and the privileged accounts are intact**. They are enforced by GitHub's ruleset and identity controls, not by motebit's own protocol; motebit-native enforcement is milestone B. With those protections intact:

- A machine-only approval cannot authorize a T1 change.
- A T0 change can merge on a machine-only approval only while the founder-controlled switch `AUTONOMY_T0` is exactly `on`.
- The agent's operating credentials cannot change repository protections or approve the agent's own work.
- Since the contract step (#1184, on main as `6e73f089e`), the `merge_group` run is the **deciding** authorization check: it judges the final integration commit against the approvals that exist when the queue builds it. A PR-level `autonomy-tier` result reflects the PR as of its last open, push or edit, and can be stale.

## A. Repository autonomy

**Goal.** Agents develop, review and, for T0 changes only, merge without the founder approving each one, while GitHub refuses anything beyond their tier.

**Mechanism.**

- Classifier [`scripts/classify-autonomy-tier.ts`](../../scripts/classify-autonomy-tier.ts): deny by default. T0 is a closed allowlist of reader-facing docs and bench prompts with no CODEOWNERS owner; everything else is T1.
- Required check `autonomy-tier` ([`.github/workflows/autonomy-tier.yml`](../../.github/workflows/autonomy-tier.yml), [`scripts/autonomy-tier-verdict.ts`](../../scripts/autonomy-tier-verdict.ts)). It is pinned to GitHub Actions (app 15368) in ruleset `main-protection` (13909292).
- The ruleset requires the merge queue ([`merge-queue.md`](merge-queue.md)), has an empty bypass list, requires code-owner review, and dismisses stale reviews on push.
- Identities ([`agent-identity-boundary.md`](agent-identity-boundary.md)):
  - `motebit-agent` publishes PRs.
  - `motebit-reviewer` is the machine reviewer. It has Write access and 2FA. Its only token (scopes `public_repo`, `read:org`, held only by the founder) was deleted on 2026-10-28 for matrix row R1, so the reviewer holds no credential today. Issuing a new one is a founder decision.
  - The founder (`hakimlabs`) is the code owner.
- Verdict rules:
  - A founder approval counts only on the PR's current head.
  - A machine approval binds on any commit for as long as GitHub reports its state as `APPROVED`, which only ever narrows what passes.
  - A dismissal ends it. GitHub rewrites a dismissed review's state to `DISMISSED`, whether a person dismissed it or a push did (`dismiss_stale_reviews_on_push`). So the verdict no longer sees that approval (matrix M6). #1193 corrected the script's comments, which had said the approval binds "for good".
  - Separately, a dismissed approval no longer counts toward GitHub's own required approval.

**Findings.**

1. **A dismissal ends a machine approval (M6).** The verdict script's claim that a machine approval binds "for good" is false: once GitHub rewrites a dismissed review's state, the verdict no longer counts that approval. This is not an authorization hole. A merge still needs an approval GitHub counts, and any such approval is visible to the verdict as `APPROVED`. #1193 corrected the claim in the script comments.
2. **Removing access does not stop a review being submitted (M7, observed live, no run id).** On a public repository, a reviewer without access can still submit an `APPROVED` review, with author association `NONE`. GitHub did not count it toward the required approval. So "an approval was submitted" is not evidence of authority.
3. **Restoring access brings old approvals back (M7).** Re-adding a collaborator makes all of their earlier approvals count again, including any submitted while they had no access. **Operating rule:** after restoring a reviewer, dismiss its standing approvals before anything is queued.
4. **Re-run timestamps.** `gh run rerun` keeps the run's original `createdAt`: run 40633462122 attempt 2 keeps 04:38:31Z but judged a review from 05:13:01Z. Cite a re-run run by run id **and attempt**. Separately, the M3 and R3 queue runs (both attempt 1) were missed by the operator's recorder and were read from the run logs directly.

**CI noise seen during the matrix (not authorization defects).**

- A test-coverage shard on #1192 hit the job timeout after all of its tests passed. Run 40640231205 was cancelled; the re-run passed.
- The e2e Playwright install sometimes takes nearly 10 minutes.
- Runs of the same event on the same PR share a concurrency group, so a push followed by an edit cancels the earlier run. A cancelled run counts as a failure until it is re-run.

**GO/NO-GO.** The matrix passed every row it ran. Every one of those denied what it should deny, and the one intended merge (M3) went through. The M7 T0 variant was not run (above). **A is closed.** Standing T0 autonomy is still NO-GO:

- `AUTONOMY_T0` stays `off` until the founder decides. Turning it on needs its own reviewed design first.
- The reviewer has no credential.
- Any future restore of reviewer access follows finding 3.

## B. Governed repo change

**Goal.** For one repository change made by an agent, an independent party holding a clone and an offline verifier can establish which agent acted, under whose authority, within what limits, with what outcome, and that the landed commit is that outcome. The model can be swapped without changing any of that. B adds evidence and a verifier, and **no merge authority**: governed changes merge under A's tier rules, and `AUTONOMY_T0` stays `off`.

**Mechanism.** The design of record is [`docs/proposals/governed-repo-change-v1.md`](../proposals/governed-repo-change-v1.md) (#1198, merged 2026-10-29T01:24:19Z as `17784c5a0`, frozen after six cold-review rounds and a confirmation round):

- The founder signs a one-landing `StandingDelegation` whose `subject_binding` reaches a task scope: exact paths, base branch and task.
- The agent runs with no host interior and exactly two frozen tools built from that scope. It signs every tool call, and an `ExecutionReceipt` recording the exact entries changed.
- The evidence lands in the same squash commit as the change. Protected `main` is the custody boundary for pins, revocations and spent grants. That is custody, not proof of immutability; the trust assumptions are in the design.
- The protocol is [`spec/repo-change-v1.md`](../../spec/repo-change-v1.md), and the verifier is `verifyRepoChange` in `@motebit/verifier`.

**Acceptance tests (from the design).**

- B1: a governed change verifies in CI and offline on a fresh clone against a trusted tip.
- B2: the same task with a second provider.
- B3: a path outside the scope fails `authority`.
- B4: a foreign signer fails `identityBinding`.
- B5a: a re-spelled tick fails `integrity`.
- B5b: a reused grant fails `authority`.
- B6: a landed revocation fails `revocation`.

Each records the run id, event, policy SHA, head and landing commits, evaluation time and every axis.

**Founder decisions** (accepted with #1198):

- writes are bounded by the signed scope, with no per-write approval;
- creating agent identity A and signing the first grant with F are authorized, and confirmed with the founder at the moment of each key operation;
- the first task is one T0-allowlisted docs file.

**Deferred, with triggers.**

- **Review attestation.** Reuse or extend the existing attestation model ([`evals-as-attestations.md`](../doctrine/evals-as-attestations.md), `EvalAttestation`) to bind reviewer identity, reviewed commit, policy version and review outcome. Trigger: step 6 identifies a concrete requirement, or F introduces an independent verifier. Signed provenance does not establish review correctness. No implementation before the trigger.
- **A release before F.** `@motebit/verifier` on npm is 1.14.2 (2026-10-19) and has no repo-change verification. An outsider can verify a governed change from public packages only after a release that follows step 4. The founder decides when to publish.
- **Canonical-spelling predicates.** `@motebit/crypto` does not export its canonical public-key predicate and `@motebit/verifier` does not export its canonical-UUID rule, so the step-3 CLI reaches each by signing a throwaway artifact under an erased ephemeral key. Trigger: the next change to either package's public surface exports them, and the CLI calls them directly.
- **Unicode case aliases in the T0 exclusions.** Exclusions fold ASCII case only, as before #1214, so `docs/x/ſKILL.md` (U+017F) is allowlisted. Folding harder (NFKC, as `repoPathCaseCollision` does) narrows A's classifier. Founder decision.
- **`scripts/differential-vs-main.ts` reports green on zero observations.** When the probe fails on both sides it prints "0 DIFF" and exits 0, against its own header. Trigger: the next change to that script, or any gate that relies on it.
- **The receipts directory is checked before it is created.** `motebit repo-task run` checks `--output` against the repository, then creates it after the git reads. A symlink planted in that window, at a not-yet-existing part of the path, would be followed; that needs write access outside the repository. Closing it means creating the directory first and checking its real path. Trigger: the next change to the run command's output handling.
- **Independence of author and reviewer.** The `motebit-agent` and `motebit-reviewer` accounts are distinct, but one operator runs both on one machine. Assigned to C.
